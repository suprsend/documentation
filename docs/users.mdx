A User in SuprSend represents the recipient of your notifications. They are used to recieve notifications, or in complex use cases, act on the notifications as well before recieving them.

## Types of Users

There are 2 types of users, based on the type of notification trigger you'd like to use:

1. **Recipient:** User who will receive the notification, and get notifed.
2. **Actor:** (optional) Who performs action on notifications, based on which recipient will be notified. This happens in case of cross-user notifications.

<Note>
  In case of cross-user notifications, actor is required. This happens in case the actual reciepient of the notification is different from the one who'd perform the action to it.
  
  E.g. in a comment section, the recipient is the person who'd receive the notification, and the actor is the one who'd performed the action (commented).

  **Important:** You can pass the actor only in case of cross-user notifications!
</Note>

## What's included in a User Profile?

A user profile in SuprSend includes the following:

- `distinct_id`: Unique identifier for every user.
- **Channel Information**: Contact details, and tokens required for delivering notifications across different channels: Email, Phone numbers, Slack, Device tokens, etc.
- **Properties**: Custom attributes for each user including: name, age, location etc.
- **Preferences**: User's notification preferences for different channels, set by them on your UI.
- **Workflow Conditions**: Conditions that determine workflow triggers for that user.
- **Lists**: Groups/segments the user belongs to (in-case of bulk import, or bulk sync)

## Syncing Users in SuprSend

Syncing user data with SuprSend, means adding your user data to SuprSend platform. It's the first step to creating a user profile in SuprSend.

This could essentially be done between your application and SuprSend's platform, easily in a number of ways, based on how the user-data is being stored.

<Accordion title="Why Sync Users?">
  1. Maintains consistent user data across your application and SuprSend.
  2. Eliminates the need to pass complete user information in every workflow trigger
  2. Keeps user notification preferences updated with that on your platform.
</Accordion>
<Accordion title= "When do you need to sync users with SuprSend?">
  You must synch users to the SuprSend platform whenever:

    1. new user signs up on your platform.
    2. user updates their profile on your platform.
    3. any user update their notification preferences on your platform.
</Accordion>

You can sync users in following different ways, based on the type of data storage you possess:

1. **Via your Frontend Application System**

   This is when the any end-user lands and signs up on your platform, or updates their profile there.

4. **Via Database**

   This method can only be chosen for Broadcasting, or for Syncing Lists (in order to Broadcast notifications).
   In this methods, you'd need to manually export the user data from your database, and import it to SuprSend.

5. **Via SuprSend console:** (For testing purposes)

   This is for testing and manual operations. You can create/ update users manually in the SuprSend console.
   It could be achieved by accessing the [SuprSend dashboard](https://app.suprsend.com), and creating user(s) manually, or updating profile or related information.

<Note>
Whenever a user is created/ synced on the SuprSend Platform, it's represented by a unique identifier called as `distinct_id`. 

#### Guidelines on how to choose a `distinct_id`

1. It should be unique for every user.
2. Character limit allowed: 255 characters.
3. Must include only strings values.
4. Case Sensitivity: (It's recommended to use lower-case strings)
5. Couldn't be changed once set, hence immutable.
6. In case of a user with internal primay ID on your platform database, SuprSend allows one-to-one mapping of User data.

</Note>

## Triggering Notifications to Users

  There are 4 ways by which you can send and trigger notifications to users, after syncing and creating them to SuprSend:
    
### 1. Sync Users Upfront:

  In this case, you'd only need to pass the `distinct_id` of the user to the trigger the notification. SuprSend will automatically fetch the user profile from trigger.
      
### 2. Inline Identification for Recipients:

  In this way of triggering notification, you need to send the entire recipient's payload to workflow trigger.
  Therefore, a user profile is created/ updated during the trigger. [Know how this is done](/docs/trigger-workflow#identifying-recipients-inline)
  
    **Note:** This is useful for dynamic user information.
    
### 3. Anonymous Notifications to the Users:
      
  By implementing this, only the bare minimum user data would be required for delivery (like email or phone number). Hence, user profile won't be created on the SuprSend platform, and the delivery information is only used transiently for only the current notification.
  
  Here's how you can achieve this in your trigger:
    - In the **recipient** object, add `"is_transient": true`.
    - You can also use this for **actors** by setting `"is_transient": true` in the actor object.
  
  **Example Payload:**
  ```json
    {
      "workflow": "your_workflow_slug",
      "actor": {
        "is_transient": true,
        "name": "actor_1"
      },
      "recipients": [
        {
          "is_transient": true,
          "$email": ["abc@example.com"],
          "name": "recipient_1"
        }
      ],
      "data": {
        // your notification data
      }
    }
  ```
  This approach works across all SDK implementations ([Python](/docs/python-trigger-workflow-from-api#sending-notification-to-anonymous-user), [Node.js](/docs/node-trigger-workflow-from-api#sending-notification-to-anonymous-user), [Java](/docs/java-trigger-workflow-from-api#sending-notification-to-anonymous-user), [Go](/docs/go-trigger-workflow-from-api#sending-notification-to-anonymous-user)) with slight syntax variations.

### 4. Cross-User Communication:

  You can send notifications to users based on another user's actions, with the help of the method called Cross-User Communication. In this, you need to pass the information of the actor and the recipient (both) in the workflow trigger. 
  
  SuprSend will automatically fetch the user profile of the actor and the recipient.

  This is a helpful use case for scenarios like:

    - Notifying document owners when someone comments.
    - Sending alerts when one user mentions another.
    - Group chat notifications, etc.

  Here's how this works:
    <Steps>
      <Step title="Specify an Actor" stepNumber={1} titleSize="p">
        Actor is the one who triggers the action. Hence, we use `$actor` properties in notification templates to reference the information of acting user.

        You need to pass the `distinct_id` of the actor in the actor object.

        For instance,

        ```json
        "actor" : {
          "distinct_id" : "actor_1",
          "name" : "Actor 1",
          // Other info if required
        }
        ```
      </Step>
      <Step title="Define the Recipient">
        Recipient is the one who recieves the notification finally. Pass the `distinct_id` of the recipient in the recipient object.

        Example:

        ```json
        "recipient" : {
          "distinct_id" : "recipient_1",
          "name" : "Recipient 1",
          "$email" : [
              "recipient_1@example.com"
          ]
        }
        ```
      </Step>
    </Steps>

  A sample skeleton structure of the implementation could be:
  ```json
    {
        "workflow": "sample_notif",
        "actor": {
            "distinct_id": "sample_actor",
            "name": "John Doe",
            // other actor properties
        },
        "recipients": [
            {
              "distinct_id": "sample_recipient",
              "$email": ["document.owner@example.com"],
              "name": "Jane Doe"
            }
        ],
        "data": {
            "first_name": "User",
            "invoice_amount": "$5000",
            "invoice_id":"Invoice-1234",
            "spend_amount":  "$10",
            // sample notification data
        }
    }
  ```
Hence, in this method, you essentially involve multiple users (actor and recipient) in the trigger.
