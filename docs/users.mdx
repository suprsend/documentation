A User in SuprSend represents the recipient of your notifications. They recieve notifications, or in complex use cases, act on the notifications before recieving them.

## Types of Users

Based on the type of notification trigger, users in SuprSend can be of 2 types:

1. **Recipient:** User who will receive the notification, and get notified.
2. **Actor:** (optional) Who performs action on notifications, based on which recipient will be notified. This happens in case of cross-user notifications.

<Note>
  To trigger cross-user notifications, an `actor` is mandatory. In this, the end-reciever of the notification is different from the one who will act to it.
  
  E.g. in a comment section, the recipient is the person who'd receive the notification, and the actor is the one who'd performed the action of commenting.

  **Important:** You can pass the actor only in case of cross-user notifications!
</Note>

## What's included in a User Profile?

Creating a user profile on SuprSend requires certain attributes, out of which `distinct_id`  is the mandatory unique identifier for any user. 
This unique identifier is useful **to represent and access an entire user profile,** including it's channel information, properties, preferences, etc.

It's used to perform different operations like updating, merging, deletion, etc. 


| Attribute                    | Description                                           | Purpose                               |
|------------------------------|-------------------------------------------------------|---------------------------------------|
| `distinct_id` (mandatory)    | Unique identifier for every user                      | to represent the user                 | 
| `email`                      | Email address of the user                             | for email notifications               |
| `phone`                      | Phone number of the user                              | for SMS notifications                 |
| `name`                       | Name of the user.                                     | customize notifications               |
| `preferred_timezone`         | User's timezone                                       | notify in convenient timezone         |
| `preferred_language`         | User's language                                       | notify in suitable language           |
| `properties`                 | Custom attributes of each user (age, location etc.)   | store additional user information     |
| `preferences`                | Notification preferences opted by user.               | store notification preferences        |
| `lists`                      | Groups/segments the user belongs to                   | to store user's subscriptions         |
| `channel info`               | Includes push tokens, user_id, Webhook URL, etc.      | for channel notifications             |
 
<Tip>
We recommend using the internal primary id of users in your systems - to be same as SuprSend's `distinct_id`. 

On the other hand, while creating a new user, or updating the existing ones, there are some specific rules to assign `distinct_id` to a user profile.
</Tip>

<Icon icon="memo-circle-info" iconType="solid" size={20} /> [What does SuprSend do with your Data?](/docs/privacy-with-suprsend)

### Guidelines on how to choose a `distinct_id`

1. It should be unique for every user.
2. Character limit allowed: 255 characters.
3. Must include only strings values.
4. Case Sensitivity: (recommended to use lower-case strings)
5. Due to it's immutable nature, it cannot be changed once set.
6. In case of a user with internal primay ID on your platform database, SuprSend allows one-to-one mapping of User data.

## Syncing Users in SuprSend

By syncing user data with SuprSend, it means adding your user data to the SuprSend platform, to further send them notifications. It's the first step to creating a user profile in SuprSend.

This could be done between your application and SuprSend's platform, easily in a number of ways, based on how the user-data is being stored.

<Accordion title="Why Sync Users?">
  1. Syncing helps you maintain consistent user data across SuprSend and your application.
  2. It eliminates the need to pass complete user information for each workflow trigger.
  2. Keeps user notification preferences updated with that on your platform.
</Accordion>
<Accordion title= "When do you need to sync users with SuprSend?">
  You must synch users to the SuprSend platform whenever:

    1. new user signs up on your platform.
    2. user updates their profile on your platform.
    3. any user update their notification preferences on your platform.
</Accordion>

You can sync users in following different ways, based on the type of data storage you possess:

### 1. Via your Frontend Application System

   This is when a new user signs-up on your platform, or updates their existing profile there.
   Use our [Frontend SDKs](/sdk/overview#frontend-sdks-client-side) to sync the user data to SuprSend.

### 4. Via Database

   This method can only be chosen for **Broadcasting**, or for **Syncing Lists** (in order to Broadcast notifications).
   
   You would need to manually export the user data from your database (`CSV`, `XML`, etc.) and upload it to SuprSend platform.
   
   <Warning>
   Syncing users via database is not recommended for large datasets. Reason: it's limited use case, repetitiveness, and manual efforts. 
   </Warning>

   This method is for testing and manual operations. You can create/ update users manually in the SuprSend console.
   Steps to do this includes:
    - Accessing the [SuprSend dashboard](https://app.suprsend.com), 
    - Manually Creating / Updating the user profile.

<Note>
Remember, anytime a user is created/ synced on the SuprSend Platform, it's represented by a unique identifier called as `distinct_id`. 

</Note>

## Triggering Notifications to Users

  There are 4 ways by which you can send and trigger notifications to users, after syncing and creating them to SuprSend:
    
### 1. Sync Users Upfront:

  In this case, you'd only need to pass the `distinct_id` of the user to the trigger notification. SuprSend will automatically fetch user profile from trigger.
      
### 2. Inline Identification for Recipients:

  In this way of triggering notification, you need to send the entire recipient's payload to the workflow trigger.
  Therefore, a user profile is created/ updated during that same trigger. [Know more on how this is done](/docs/trigger-workflow#identifying-recipients-inline).
  
    **Note:** This is useful for dynamic user information.
    
### 3. Anonymous Notifications to the Users:
      
  By implementing this, only the bare minimum user data would be required for delivery (email or phone number). Hence, user profile won't be created on the SuprSend platform, and the delivery information is used transiently for only the current notification.
  
  Here's how you can achieve this in your trigger:
    - In the **recipient** object, add `"is_transient": true`
    - You can also use this for **actors** by setting `"is_transient": true` in the actor object.
  
  **Example Payload:**
  ```json
    {
      "workflow": "your_workflow_slug",
      "actor": {
        "is_transient": true,
        "name": "actor_1"
      },
      "recipients": [
        {
          "is_transient": true,
          "$email": ["abc@example.com"],
          "name": "recipient_1"
        }
      ],
      "data": {
        // your notification data
      }
    }
  ```
  This approach works across all SDK implementations ([Python](/docs/python-trigger-workflow-from-api#sending-notification-to-anonymous-user), [Node.js](/docs/node-trigger-workflow-from-api#sending-notification-to-anonymous-user), [Java](/docs/java-trigger-workflow-from-api#sending-notification-to-anonymous-user), [Go](/docs/go-trigger-workflow-from-api#sending-notification-to-anonymous-user)) with slight syntax variations.

### 4. Cross-User Communication:

  You can send notifications to users based on another user's actions, with the help of Cross-User Communication. In this method, information of the actor and the recipient (both) needs to be passed in the workflow trigger. 
  
  SuprSend will automatically fetch the user profile of the actor and the recipient.

  This is a helpful use case for scenarios like:

    - Notifying document owners when someone comments.
    - Sending alerts when one user mentions another.
    - Group chat notifications, etc.

  Here's how this works:
    <Steps>
      <Step title="Specify an Actor" stepNumber={1} titleSize="p">
        Actor is the one who triggers the action. Hence, we use `$actor` properties in notification templates to reference the information of acting user.

        You need to pass the actor's `distinct_id` in the actor object.

        Example:

        ```json
        "actor" : {
          "distinct_id" : "actor_1",
          "name" : "Actor 1",
          // Other info if required
        }
        ```
      </Step>
      <Step title="Define the Recipient">
        Recipient is the one who recieves the notification finally. Pass recipient's `distinct_id` in the recipient object.

        Example:

        ```json
        "recipient" : {
          "distinct_id" : "recipient_1",
          "name" : "Recipient 1",
          "$email" : [
              "recipient_1@example.com"
          ]
        }
        ```
      </Step>
    </Steps>

  A sample skeleton structure of the implementation for Cross-User Communication could be:
  ```json
    {
        "workflow": "sample_notif",
        "actor": {
            "distinct_id": "sample_actor",
            "name": "John Doe",
            // other actor properties
        },
        "recipients": [
            {
              "distinct_id": "sample_recipient",
              "$email": ["document.owner@example.com"],
              "name": "Jane Doe"
            }
        ],
        "data": {
            "first_name": "User",
            "invoice_amount": "$5000",
            "invoice_id":"Invoice-1234",
            "spend_amount":  "$10",
            // sample notification data
        }
    }
  ```
Hence, in this method, you essentially involve multiple users (actor and recipient) in the Trigger Workflow.
