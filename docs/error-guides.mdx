This page covers errors that occur **during** workflow or broadcast execution — after the API request is accepted but before or during message delivery, including common causes and how to fix them. For errors that occur before execution starts (validation, auth, missing fields), see [API Request Errors](/docs/api-request-errors).

### What Workflow Execution Logs are
Workflow Execution Logs capture the full lifecycle of a workflow run — from trigger acceptance through each node (template rendering, branching, delays, fetches) to final delivery. They help you debug template rendering failures, missing variables, jq-expression errors, vendor configuration issues, and any error that occurs after the API request is accepted. Use the [idempotency key](/docs/logging) to trace a notification across log types.

## Errors

### `<channel>`: template rendering failed. error: `"<variable>"` not defined in [object Object]

**What does this mean:**
A [template](/docs/templates) used in your workflow references a variable (e.g. `{{name}}`, `{{link}}`) that was not passed in the [workflow trigger payload](/docs/trigger-workflow). This can happen on any channel — Email, Inbox, SMS, WhatsApp, etc. Because the variable is undefined at render time, SuprSend cannot render the template and the notification fails to send.

**How to fix it:**
- Open the failed workflow execution log and check which variable is reported as undefined in the error message, and which channel it occurred on.
- Open the template for that channel in your workflow and look for all variables wrapped in `{{...}}`. Every variable used in the template must be passed in the trigger payload.
- Update your trigger payload to include the missing variable:
```json
{
  "data": {
    "name": "John Doe",
    "link": "https://example.com/comment/123"
  }
}
```

- If the variable is optional and may not always have a value, update the template to handle the missing case using a conditional:
```handlebars
{{#if name}}Hi {{name}}{{else}}Hi there{{/if}}
```

- See [Trigger Workflow](/docs/trigger-workflow) for details on passing data in the trigger payload, and [Handlebars Helpers](/docs/handlebars-helpers) for conditional rendering in templates.

### override channels jq-expression `<expression>` resulted in empty channels

**What does this mean:**
The jq-expression configured in the **Override Channels** setting of a send node evaluated to an empty or invalid value at runtime. Because no valid channel could be resolved, the workflow execution stopped at that node and the notification was not sent.

**How to fix it:**
- Open the failed workflow execution log and check which workflow and send node this error occurred on.
- Go to the send node settings in your workflow and check the jq-expression configured under **Override Channels**. Verify that the key it references exists in your trigger payload and resolves to a valid, non-empty array.
- The expression must resolve to one or more valid channel values:
```json
["email", "sms", "whatsapp", "androidpush", "iospush", "webpush", "slack", "inbox", "ms_teams"]
```

- Test your jq-expression at [jqplay.org](https://jqplay.org) with a sample payload to confirm it returns the expected output before updating the workflow.
- If the channel value in your payload uses different naming conventions, use a jq-expression to transform it to match SuprSend's expected values. For example, if your payload has `"Email"` instead of `"email"`, use `.channels | map(ascii_downcase)`.
- If override channels is not needed, remove the jq-expression from the send node settings entirely to fall back to the channels configured in the workflow.
- See [Multi-Channel Delivery](/docs/delivery-multi-channel) for more details on configuring override channels.

### `"<variable>"` not defined in [object Object] (Data Transform node)

**What does this mean:**
The **Data Transform** node in your workflow references a variable (e.g. `{{timezone}}`) that is not present in the workflow trigger payload at the time the node executes. Because the variable is undefined, the data transformation fails and the workflow stops at that node.

**How to fix it:**
- Open the failed workflow execution log and check which variable is reported as undefined in the error message.
- Go to the **Data Transform** node in your workflow and check the expression referencing that variable. Every variable used in the expression must be present in the [trigger payload](/docs/trigger-workflow) or added to the payload by a preceding node (e.g. a [Fetch](/docs/fetch) node).
- Update your trigger payload to include the missing variable:
```json
{
  "data": {
    "timezone": "America/New_York"
  }
}
```

- If the variable is optional and may not always be present, add a fallback in your Data Transform expression using a conditional:
```
local timezone = std.objectHas(data, "timezone") ? data.timezone : "UTC";
```

- If the variable is expected to come from a preceding Fetch or Webhook node, verify that node is returning the correct data and the key name matches exactly.
- See [Data Transform](/docs/data-transform) for more details on writing transform expressions.

### JsonnetEvaluateError: RUNTIME ERROR: Field does not exist: `<field>` (Data Transform node)

**What does this mean:**
The **Data Transform** node in your workflow uses a **Jsonnet expression** that references a field (e.g. `itemsGrouped`) that does not exist in the workflow execution data at the time the node runs. Because the field is missing, the Jsonnet evaluation fails and the workflow stops at that node.

**How to fix it:**
- Open the failed workflow execution log and check which field is reported as missing in the error message. The error also includes a line and column reference (e.g. `6:36-56`) pointing to exactly where in your Jsonnet expression the failure occurred.
- Go to the **Data Transform** node in your workflow and check the Jsonnet expression at the referenced line. Verify that the field exists in your [trigger payload](/docs/trigger-workflow) or is produced by a preceding node.
- Update your trigger payload to include the missing field:
```json
{
  "data": {
    "itemsGrouped": []
  }
}
```

- If the field is optional and may not always be present, add a guard in your Jsonnet expression using `std.objectHas`:
```jsonnet
local itemsGrouped = if std.objectHas(data, "itemsGrouped") then data.itemsGrouped else [];
```

- If the field is expected to come from a preceding [Fetch](/docs/fetch) or another [Data Transform](/docs/data-transform) node, verify that node is executing successfully and the field name matches exactly — field names are case-sensitive.
- See [Data Transform](/docs/data-transform) for more details on writing Jsonnet expressions.

### tenant not found

**What does this mean:**
The `tenant_id` passed in the workflow trigger does not exist in the workspace. SuprSend could not find the tenant at workflow execution time, so the send node failed to process.

**How to fix it:**
- Search for the `tenant_id` on the [Tenants](https://app.suprsend.com/en/production/tenants/) page in the dashboard to confirm if it exists. Tenant IDs are case-sensitive.
- If the tenant doesn't exist, create it first from the dashboard or via API before triggering the workflow with that `tenant_id`. See [Tenants](/docs/tenants) for details on creating and managing tenants.
- If the tenant exists but the error still occurs, check if you are dynamically resolving the `tenant_id` using a jq-expression in the trigger override settings — verify the expression resolves to the correct tenant ID. See [Trigger Workflow](/docs/trigger-workflow) for more details.
- If tenant customization is not needed for this workflow, remove the `tenant_id` from your trigger payload — SuprSend will fall back to the default tenant automatically.

### evaluation of 'url' failed. invalid character 'h' looking for beginning of value

**What does this mean:**
The **Webhook node** in your workflow failed to evaluate the URL at execution time. The URL field is configured with a jq-expression to dynamically resolve the endpoint, but the expression is returning a raw string (e.g. `https://...`) instead of a valid JSON value. Because jq expects a JSON-encoded string (i.e. with quotes), a raw URL starting with `h` causes a JSON parse failure.

**How to fix it:**
- Open the failed workflow execution log and check the Webhook node where this error occurred.
- Go to the Webhook node settings in your workflow and check the jq-expression configured for the **URL** field.
- The jq-expression must return a **JSON string value** — ensure the expression wraps the output correctly. For example:

  **Incorrect** — returns raw string:
```jq
  .webhook_url
```
  if `.webhook_url` in your payload is `https://example.com` this may output a raw value depending on how it's used.

  **Correct** — ensure the payload value itself is a valid JSON string:
```json
  {
    "data": {
      "webhook_url": "https://example.com/endpoint"
    }
  }
```

- Test your jq-expression at [jqplay.org](https://jqplay.org) with a sample payload to confirm it returns the expected URL string.
- If the URL is static and doesn't need to be dynamic, hardcode it directly in the Webhook node URL field instead of using a jq-expression.
- See [Fetch](/docs/fetch) for more details on configuring dynamic URLs in HTTP nodes.

### User distinctId not found (Update User Profile node)

**What does this mean:**
The **Update User Profile** node in your workflow could not find a user to update because no valid `distinct_id` was available at the time the node executed. This commonly happens when the workflow is triggered with an [object](/docs/objects) as the recipient instead of a user — objects do not have a `distinct_id`, so the node has no user profile to update.

**How to fix it:**
- Open the failed workflow execution log and check the recipient that triggered this workflow execution. If the `distinct_id` shows a value like `__object:ObjectType:ObjectId`, the workflow was triggered with an object recipient, not a user.
- The **Update User Profile** node can only update user profiles. If your workflow fans out to both users and objects via [object subscriptions](/docs/object-subscriptions), add a **Branch** node before the Update User Profile node to check the recipient type and only route users to that node:
```
recipient.$type == "user" → Update User Profile node
recipient.$type == "object" → skip or route elsewhere
```

- If you intended to update a user profile, ensure the workflow is triggered with a user `distinct_id` as the recipient instead of an object.
- See [Update User Profile](/docs/update-user-profile) and [Objects](/docs/objects) for more details.

### subscription entry not found with pk: `<id>`

**What does this mean:**
During workflow execution, SuprSend attempted to process a subscriber as part of an [object subscription](/docs/object-subscriptions) fan-out, but the subscription entry no longer exists. This typically happens when a subscriber is removed from an object subscription between the time the workflow was triggered and the time the workflow node executed — a race condition between subscription deletion and workflow execution.

**How to fix it:**
- This error is usually transient and does not require any code changes. It occurs when a user unsubscribes or is removed from an object subscription while a workflow execution triggered for that subscription is still in progress.
- If this error is occurring frequently for the same object, check if there is a process in your system that is rapidly adding and removing subscribers from that object — this increases the likelihood of this race condition occurring.
- If you need to ensure notifications are only sent to currently active subscribers, consider adding a **Fetch** node before the send node to verify the subscription still exists at execution time, and use a **Branch** node to skip the send if it does not.
- See [Object Subscriptions](/docs/object-subscriptions) for more details on managing subscriptions.

### Request: `<METHOD>` `<url>`, Status: `<4xx/5xx>`, Message: `<response_body>` (Fetch node)

**What does this mean:**
The [Fetch node](/docs/fetch) in your workflow successfully made an HTTP request to the configured external API endpoint, but received a non-successful HTTP response (e.g. `404 Not Found`, `401 Unauthorized`, `500 Internal Server Error`). Because the request failed, the workflow stops at this node and any data expected from the Fetch node will not be available to subsequent nodes.

**How to fix it:**
- Open the failed workflow execution log and check the full error message — it includes the request method, URL, HTTP status code, and response body returned by the external API. This gives you the exact information needed to debug the issue on the external API side.
- Common causes and fixes based on status code:
  - **404 Not Found** — the resource referenced in the URL does not exist. Check if the ID or path being passed dynamically is correct and the resource hasn't been deleted.
  - **401 Unauthorized / 403 Forbidden** — the API key or authentication token configured in the Fetch node is missing, expired, or incorrect. Update the credentials in the node settings.
  - **500 Internal Server Error** — the external API is experiencing issues. Check the status of the external service and retry.
- If the URL is built dynamically using variables from the trigger payload, verify that all variables are present and resolve to the correct values. Test the full URL manually (e.g. using Postman) to confirm it returns a successful response.
- If the external resource may not always exist and the workflow should continue regardless, add a **Branch** node after the Fetch node to check the response status and handle the failure case gracefully instead of stopping the workflow.
- See [Fetch](/docs/fetch) for more details on configuring the Fetch node.

### SubscriberList Broadcast API: no active/preferred channels found for user

**What does this mean:**
The broadcast was triggered successfully, but for this specific user in the list, SuprSend could not find any active or preferred channel to deliver the notification on. This means either the user has no channel details (e.g. no email, phone, or push token) added to their profile, or the user has opted out of all channels included in the broadcast template.

**How to fix it:**
- Search for the `distinct_id` of the affected user on the [Users](https://app.suprsend.com/en/production/subscribers/) page in the dashboard and check if they have any channel details (email, phone, push token etc.) added to their profile. If not, update the user profile with the correct channel details before running the broadcast again. See [Users](/docs/users) for more details.
- If the user has channel details but has opted out of all relevant channels, check their [preferences](/docs/embedded-preference-centre) on the user details page. You can only send notifications to channels the user is opted into.
- If this error is appearing for a large number of users in your list, it may indicate a data quality issue — run a check on your list to identify users with missing channel details and enrich their profiles before broadcasting.
- Note that this is a **user-level error** — it does not affect delivery to other users in the same broadcast. Other users with valid channel details will still receive the notification.
- See [Broadcast](/docs/broadcast) for more details on running broadcasts to lists.

### SubscriberList Broadcast API: user has unsubscribed from channels `[<channel>]` for category: `<category>`

**What does this mean:**
The user in your broadcast list has explicitly opted out of the specified channel (e.g. `email`) for the notification category linked to this broadcast (e.g. `promotional-emails`). SuprSend respects user preferences and skips delivery for opted-out users. This is expected behavior and not an error in your broadcast setup.

**How to fix it:**
- This is generally **not something to fix** — SuprSend is correctly honoring the user's opt-out preference. Sending notifications to users who have unsubscribed would violate their preference and may have compliance implications.
- If you believe the user's preference was set incorrectly, you can check and update their preferences from the user details page in the dashboard or via the [Preference APIs](/reference/get-user-full-preference).
- If this error is appearing for a large number of users in your list, it may indicate that your list contains users who have already opted out. Consider filtering opted-out users from your list before running the broadcast to get a more accurate picture of deliverable recipients.
- Note that this is a **user-level error** — it does not affect delivery to other users in the same broadcast who are still opted in.
- See [Broadcast](/docs/broadcast) and [Preference Centre](/docs/embedded-preference-centre) for more details.

### Template did not render

**What does this mean:**
During broadcast execution, SuprSend failed to render the template for a chunk of users. Unlike variable-level rendering errors, this is a broader failure where the template could not be processed at all. This typically happens when the [template](/docs/templates) is in `draft` state, has been deleted, or has a structural issue that prevents it from rendering.

**How to fix it:**
- Open the failed broadcast execution log and check which template and workflow version was being used at the time of the broadcast.
- Go to the [template](/docs/templates) linked to your broadcast workflow and verify:
  - It is in **published** state — draft templates cannot be rendered during broadcast execution.
  - It has valid content and no structural errors in the template editor.
- If you recently made changes to the template, check if those changes introduced any issues — you can roll back to a previous version from the template version history.
- If the template was deleted after the broadcast was triggered, re-create and publish it, then re-run the broadcast.
- See [Broadcast](/docs/broadcast) and [Design Workflow](/docs/design-workflow) for more details.

### Error while fetching Vendor configuration

**What does this mean:**
During broadcast execution, SuprSend failed to load the vendor configuration for the channel being used in the broadcast. This is a broadcast-level error that affects entire chunks of users, not individual recipients. It typically happens when the vendor linked to the workflow is misconfigured, disabled, or has been deleted.

**How to fix it:**
- Go to the [Vendors](/docs/vendors) page in the dashboard and verify that the vendor configured for the channel used in this broadcast is active and correctly set up.
- Check if the vendor credentials (API key, secret, etc.) are still valid — expired or revoked credentials can cause vendor configuration failures.
- If you are using a **tenant-specific vendor**, verify that the tenant linked to this broadcast has a valid vendor configured for the channel. See [Tenant Vendor](/docs/tenant-vendor) for more details.
- If the vendor was recently deleted or disabled, re-configure it from the Vendors page and re-run the broadcast.
- If the issue persists, contact [SuprSend support](mailto:support@suprsend.com) with the broadcast ID and workflow slug so the team can investigate the vendor configuration on the backend.
- See [Broadcast](/docs/broadcast) for more details.

### Zero Users in this chunk for list_id: `<list_id>`

**What does this mean:**
During broadcast execution, a chunk of the broadcast had zero users to process for the specified list. This typically happens when the list is empty, or all users in a particular chunk have already been processed, filtered out, or removed from the list by the time that chunk was executed.

**How to fix it:**
- Go to the [Lists](/docs/lists) page in the dashboard and verify that the list referenced in the error (`list_id`) has active users in it.
- If the list was recently synced or updated, check if the sync completed successfully and users were added correctly. See [Lists](/docs/lists) for more details on managing list users.
- If this error appears only for some chunks but not others, it may be a transient issue with how users were distributed across chunks during broadcast execution — this does not necessarily mean the entire broadcast failed.
- If the list is intentionally empty (e.g. a test list), this error can be safely ignored.
- See [Broadcast](/docs/broadcast) for more details on running broadcasts to lists.
