[Amazon Athena](https://docs.aws.amazon.com/athena/latest/ug/what-is.html) reads Parquet files directly from S3 and bills per terabyte scanned, so it's a fast way to explore the data the [Amazon S3 v2.0 connector](/docs/amazon_s3_v2) writes—no warehouse to provision, no ingestion pipeline to maintain.

By the end of this guide you'll have a database named `suprsend_db` with three tables (`ss_requests`, `ss_workflow_executions`, `ss_messages`), and you'll have run your first query.

---

## Prerequisites

You'll need:

- The [S3 v2.0 connector](/docs/amazon_s3_v2#setup) running and writing Parquet files to your bucket.
- Access to the AWS account that owns the bucket, with permission to use Athena and read the bucket.
- An S3 location for Athena to store query results (a separate prefix or a different bucket).

Your connector must be configured with:

- **Path layout: `per_type`** — the tables in this guide point at one S3 prefix per data point (`<bucket>/workflow_executions/`, `.../requests/`, `.../messages/`), which only exists with `per_type`. It's the default for new connectors.
- **Compression: anything other than `lz4`** — Athena can't read `lz4`-compressed Parquet reliably (a generic Athena limitation, not specific to SuprSend). `snappy` (the default), `gzip`, `zstd`, `brotli`, and `none` all work.

You can view or change either setting from [Compression and path layout](/docs/amazon_s3_v2#compression-and-path-layout).

<Warning>
**On a connector created before these options existed?** It's running on `lz4` + `shared`, which this guide doesn't support. Edit the connector and switch to a non-`lz4` codec and `per_type`.

The change applies only to files written **after** the switch—existing files keep their original codec and folder. For the historical data you can either scope queries to the post-switch date range using the `year`/`month`/`day`/`hour` filters, or contact support to rewrite the files.
</Warning>

## 1. Set the Athena query result location

Open the [Athena console](https://console.aws.amazon.com/athena/) in the same region as your S3 bucket. The first time you use Athena in a region you have to set a result location:

1. Go to **Settings** → **Manage**.
2. Set **Location of query result** to a path you control, for example `s3://YOUR_BUCKET_NAME/athena-results/`.
3. Save.

---

## 2. Create the database

In the query editor, run:

```sql
CREATE DATABASE IF NOT EXISTS suprsend_db;
```

The rest of the guide uses `suprsend_db`. If you pick a different name, update the `CREATE EXTERNAL TABLE` statements below to match.

---

## 3. Create the external tables

Run each statement to register one external table per data point. They use [Athena partition projection](https://docs.aws.amazon.com/athena/latest/ug/partition-projection.html) on `year/month/day/hour`, so new hourly partitions are picked up automatically—you don't need `MSCK REPAIR TABLE` or a Glue Crawler.

Replace `YOUR_BUCKET_NAME` in `LOCATION` and `storage.location.template` with your bucket. If your connector writes under a path prefix (for example `staging/`), include it before the data-point folder—`s3://YOUR_BUCKET_NAME/staging/workflow_executions/`.

## 4. Run your first query

You're ready to query. The cardinal rule with Athena is to always filter on the partition columns (`year`, `month`, `day`, `hour`) where you can—Athena bills per TB scanned, so partition pruning is the main way to keep costs predictable.

```sql
SELECT *
FROM suprsend_db.ss_workflow_executions
WHERE year = '2026'
LIMIT 100;
```

Trace a single request across all three tables using the [linking columns](/docs/amazon_s3_v2#linking-different-data-points):

```sql
SELECT
  r.idempotency_key,
  w.execution_id,
  m.message_id,
  m.message_status
FROM suprsend_db.ss_requests       AS r
LEFT JOIN suprsend_db.ss_workflow_executions AS w
  ON w.idempotency_key = r.idempotency_key
LEFT JOIN suprsend_db.ss_messages  AS m
  ON m.wf_execution_id = w.execution_id
WHERE r.year = '2026'
  AND r.idempotency_key = 'YOUR_IDEMPOTENCY_KEY';
```

## Best practices

<AccordionGroup>
<Accordion title="Keep query cost under control">

- Always include partition filters (`year`, `month`, `day`, `hour`) in your `WHERE` clause—Athena scans only the matching folders.
- `SELECT` only the columns you actually need; avoid `SELECT *` in production queries.
- Athena bills per terabyte scanned, so partition pruning is the main lever for cost.

</Accordion>

<Accordion title="Working with string-typed columns">

Several columns are stored as `string` in Parquet even though they represent JSON, booleans, integers, or timestamps. Cast them explicitly in your queries:

- JSON columns (`payload`, `response`, `metadata`, `properties`, `webhook_data`, `execution_failure_reason`): `json_extract(column, '$.field')`.
- Integer-as-string columns (`vendor_fallback_level`, `wait_time_in_seconds`): `CAST(column AS BIGINT)`.
- Boolean-as-string columns (`vendor_fallback_applicable`, `is_smart`): compare against `'true'` / `'false'`.
- ISO timestamp strings (`success_achieved_at`): `from_iso8601_timestamp(column)`.

See the [table schemas](/docs/amazon_s3_v2#table-schema) for the full list of which columns this applies to.

</Accordion>

<Accordion title="Data freshness">

- The connector rewrites hourly Parquet files when data updates upstream.
- The next Athena query sees the new state automatically—no refresh, no `MSCK REPAIR TABLE`, no Glue Crawler.

</Accordion>

<Accordion title="Changing the connector's S3 path">

- If you reconfigure the connector to write to a different bucket or prefix, the existing tables stop returning new data.
- Drop and recreate each table with the updated `LOCATION` and `storage.location.template` to pick up the new path.

</Accordion>
</AccordionGroup>
