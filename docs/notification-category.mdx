Notification categories define the classification your workflow belongs to. Each workflow is assigned to a **sub-category**, which determines how users can control it and what rules apply.

Categories serve three main purposes:

<AccordionGroup>
  <Accordion title="Defining notification latency">
    We maintain separate notification queues for different notification categories to ensure that marketing and promotional notifications don't delay system or time-sensitive notifications.
  </Accordion>

  <Accordion title="Setting category-level preferences per-user and tenant">
    You can create sub-categories for different types of notifications and give your users and tenants the option to set their notification preferences at the category level.

    See more in the [dedicated section below](/docs/notification-category#setting-category-level-preferences-per-user-and-tenant).
  </Accordion>

  <Accordion title="Setting category-level rules or limits">
    You can set rules that apply to all notifications in a category. For example, you can set a rule that all notifications in the promotional category should only be sent between 10 AM - 5 PM, or set a limit that the max notifications in the category should not exceed 100k per day.
  </Accordion>
</AccordionGroup>

## Mental model

Notification categories use a functional hierarchy:

**Top-level category** → **Sub-category**

Sections are optional UI groupings inside a top-level category and are used to organize sub-categories.

| Level | What you need to know | Example |
|-------|---------------------|---------|
| **Top-level category** | Choose one of three: **System**, **Transactional**, or **Promotional**. This determines how fast notifications are sent and what rules apply. You can't create new ones. | Promotional |
| **Sub-category** | The actual notification type you assign to workflows. This is what users see and can opt in/out of. | Newsletter |

**Example structure:**

```
Promotional (top-level)
  └── Marketing (section)
      ├── Newsletter (sub-category) ← Use this in workflows, set preferences here
      └── Product Updates (sub-category) ← Use this in workflows, set preferences here
  └── Sales (section)
      ├── Deals (sub-category) ← Use this in workflows, set preferences here
      └── Price Drops (sub-category) ← Use this in workflows, set preferences here
```

<Note>
  **Workflows always reference sub-category slugs.** You cannot assign a workflow directly to System/Transactional/Promotional.
</Note>

When users visit their preference page, they see sub-categories (Newsletter, Product Updates, Deals, Price Drops) organized under sections. Top-level categories control delivery behind the scenes but aren't shown to users.

## Top-level categories

SuprSend has three top-level categories — **System**, **Transactional**, and **Promotional** — which define latency and queueing behavior. Sub-categories are always created inside one of these three.

**How it works:**
- Notification rules and latency priority are inherited from the top-level category
- Preference settings are defined at each sub-category level
- Top-level categories are not shown to users—only sub-categories appear on preference pages

<Warning>
  **Preferences only work with sub-categories:** User preferences apply to sub-categories you create (e.g., "Newsletter", "Product Updates"), not top-level categories (System, Transactional, Promotional). Use sub-category slugs in workflows for preferences to work.
</Warning>

### System

Essential notifications that users can't unsubscribe from. **Highest priority** in notification queues.

**Why it exists:** Ensures critical messages are always delivered immediately, regardless of user preferences.

**Common examples:** OTP, Forgot Password, Verification emails, Account security alerts

### Transactional

Notifications sent in response to user actions or transactions. **Second priority** in notification queues.

**Why it exists:** User-initiated actions require confirmation and updates.

**Common examples:** Delivery updates, Payment confirmation, Booking confirmation, Post shared/liked, Balance alerts, Account updates, Reminders

### Promotional

Notifications sent to promote products or bring users back to your platform. **Lowest priority** in notification queues.

**Why it exists:** Marketing messages shouldn't impact delivery of critical notifications.

**Common examples:** Newsletters, Announcements, Product updates, Sales/events, Deals and discounts, Price drop alerts

<Note>
Promotional notifications are sent in bulk and consume significant pipeline resources, which is why they have the lowest priority. Always use the promotional category for bulk messages and broadcasts to avoid impacting system and transactional notification latency.
</Note>

## Sections and Sub-Categories

<Tabs>
  <Tab title="Section">
    Sections are optional groups that organize related sub-categories on the preference page. Think of them as folders that help users find notifications more easily.

    **What sections do:**
    - Group related sub-categories together (e.g., "Billing" section with "Invoice Ready" and "Payment Reminder" sub-categories)
    - Make the preference page easier to navigate
    - Don't affect delivery, latency, or rules

    Sections are purely for UI organization and don't impact how notifications are sent.
  </Tab>

  <Tab title="Sub-category">
    Sub-categories are the actual notification types that users can control. This is what you assign to workflows and what appears on the preference page.

    **What sub-categories do:**
    - Define specific notification types (e.g., "Newsletter", "Invoice Ready", "OTP")
    - Are assigned to workflows using their slug (e.g., `newsletter`, `invoice-ready`)
    - Names and descriptions are rendered on the preference UI to help users understand what notifications they'll receive
  </Tab>
</Tabs>

## Default preferences

Default preferences determine how users receive notifications when they haven't set their own preferences. Configure these at the sub-category level when setting up categories.

**Preference modes:**
- **On**: Users receive notifications by default
- **Off**: Users must opt in to receive notifications
- **Can't Unsubscribe**: Users cannot fully opt out (required notifications)

When using **Can't Unsubscribe**, channel-level opt-in/out still applies unless channels are marked mandatory.

For detailed information on configuring default preferences, preference modes, and recommended defaults, see [Default Preferences](/docs/user-preferences#default-preferences).

## Setting category-level preferences per-user and tenant

You can create sub-categories for different types of notifications and give your users and tenants the option to set their notification preferences at the category level. Users can opt in or out of specific categories, and tenants can set default preferences that apply to all their users.

For details, see [User Preferences](/docs/user-preferences) and [Tenant Preferences](/docs/tenant-preference).

## Tags

Tags are used to filter categories on the preference page. Tags added at the section level are inherited by all sub-categories inside that section.

![Tags Within Preference Categories](/images/preference-tag-changelog.png)

You can filter categories using the tags query parameter in the [get user preference API](/reference/get-user-full-preference).

<Note>
  Tags do not affect delivery or rules — they only help with filtering and UI organization.
</Note>

## Category translations

<Note>
  This feature is only available for Enterprise plan customers.
</Note>

Translate category and section names and descriptions to display preference centers in users' preferred languages. This is essential for applications serving users across multiple countries and languages.

**Why it exists:** Users are more likely to engage with preference centers when content is in their native language. Category translations ensure your preference UI is accessible and understandable for international users.

**What gets translated:**
- Category names and descriptions
- Section names and descriptions
- All preference-related text visible to users on preference pages

When users access preference centers or fetch preferences via API with a `locale` parameter, they see content in their preferred language.

**How it works:**

English (`en`) is always available as the base language and is auto-generated from the category names and descriptions you define. It cannot be overridden.

If a translation is missing for a specific locale, the system automatically falls back in this order:
1. `locale-region` (e.g., `es-AR`)
2. `locale` (e.g., `es`)
3. `en` (English - always available)

**Example:** If a user requests preferences with `locale=es-AR` and a translation is missing, the system tries `es`, then falls back to `en` if needed.

Translations go live immediately after upload—no commit or publish required.

For step-by-step instructions on uploading and managing translations, see [Managing category translations](/docs/managing-notification-categories#managing-category-translations).
