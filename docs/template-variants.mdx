## Overview

A **variant** is an alternative content version of a template channel — same channel, different content. Variants let you serve different message content to different audiences without creating separate [templates](/docs/templates) or [workflows](/docs/workflows).

Common use cases:
- **Multi-tenant content** — each [tenant](/docs/tenants) sees notification content specific to their brand or product context.
- **Localisation** — different languages for the same notification. See [Multi-lingual Templates](/docs/multi-lingual-template).
- **A/B testing** — different message copy to test engagement.

Every template channel has a **default** variant. Additional variants are matched against conditions at send time — if conditions match, that variant is used. If no conditions match, the default variant is sent.

---

## The Variants Panel

Open the **Variants** tab in the left panel of the template editor. It has two sections:

**Open Tabs** — variants currently open in the editor. Each entry shows the channel icon, variant name, and language. Click any entry to switch to that variant's editor tab.

**All Variants** — all variants in the template, grouped by channel (Email, In-App Inbox, Slack, MS Teams, etc.). Expand a channel to see all its variants. Click a variant to open it in a new editor tab.

---

## Creating a Variant

Click the **+** icon next to the default variant tab to create a new variant. The variant creation modal asks for:

**Variant name and slug**
- Default name is auto-generated (Variant 1, Variant 2, …).
- The slug is auto-derived from the name at creation time. Once saved, changing the name does not automatically update the slug.
- The slug is used to fetch variant content via API — keep it stable.

**Conditions**
- Conditions determine when this variant is selected instead of the default.
- A default condition (`$recipient.language`) is pre-filled — you can change the value but not remove the condition type.
- To target a specific tenant, add a condition with `$tenant.id` — the value field becomes a tenant dropdown.
- For other condition keys, enter a fixed value or a variable.

---

## Variant Selection Logic

At send time, SuprSend evaluates all variant conditions against the [trigger payload](/docs/trigger-workflow) and recipient profile. The selection rules are:

1. **All conditions must match** for a variant to qualify.
2. If multiple variants qualify, the one with the **highest specificity** (most conditions matching) is selected.
3. If multiple variants have equal specificity, the one **created first** is selected.
4. If **no variant conditions match**, the **default variant** is sent.

## Editing a Variant

Click **Edit** on any variant to open it in the editor. Editing always happens on the **draft version** — the live version is never directly modified. Content auto-saves as you type.

Each variant is edited and published independently. Publishing one variant does not affect other variants in the same template.

---

## Publishing a Variant

Click **Publish Changes** in the editor to make the draft version live. You will be prompted for:

- **Version name** — auto-generated (V1, V2, V3…) but editable.
- **Version description** — optional.

Once published, the variant version becomes live immediately and is used in all subsequent [workflow](/docs/workflows) runs that match its conditions.

---

## Version History

Click the **History** tab in the left panel to view the version history of the template. Each version entry shows:

- Version number (V1, V2, …) and status (Live, Draft)
- Author and timestamp
- A per-channel, per-variant breakdown showing whether each was **Updated** or **Unchanged** in that version

**Rolling back a version**

Click any previous version to view its details. Select **Rollback** to make that version live immediately. A confirmation modal will appear:

> *"This action will make V1 version live with immediate effect."*

The live version is a pointer — rolling back moves the pointer to the selected version without deleting newer versions.

<Warning>
  For WhatsApp and SMS templates, rollback is only available for versions published after the current template system was introduced. Additionally, if the vendor auth of the active configuration doesn't match the rollback version, you'll see a warning that the template will re-enter approval state after rollback.
</Warning>

## Variant Actions

From the Variants panel or the variant tab menu (**⋮**), each variant supports:

| Action | Description |
| --- | --- |
| **Edit Variant** | Change the variant's name, slug, or conditions. |
| **Duplicate** | Create a copy of the variant with the same content. Useful when two variants share similar content with minor differences. |
| **Delete** | Permanently remove the variant. The default variant cannot be deleted. |
| **Test Variant** | Send a test notification using this variant's content. Enter the recipient's `distinct_id` and select the delivery identity. Uses the live version — publish before testing. |

---

## Promoting to Another Workspace

From the template view, click **Promote** in the global actions to clone the template to another workspace (e.g. from Staging to Production).

- Default target workspace is **Production** (or **Staging** if you're already in Production).
- Target channels and template slug default to the same as the source — you can change these before promoting.

---

## Importing Content

In the variant editor, click **Import Variant** to populate the editor with content from:
- Another variant in the same template
- A different template in your workspace
- A sample template from the SuprSend library

This is useful when creating a new variant that is mostly similar to an existing one.
