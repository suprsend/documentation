---
title: "Template Variants"
description: "Serve different message content to different audiences — by tenant, language, or any condition — from a single template. SuprSend picks the right variant at send time automatically."
---

Variants let you send different content to different recipients without duplicating templates or building conditional logic in your code. One template, one slug, one place to make content changes — SuprSend handles which version each recipient gets.

---

## How variants work

Every template channel has one **default** variant. You add named variants with conditions. At send time, SuprSend evaluates those conditions against the trigger payload and recipient profile, then delivers the best match. If nothing matches, the default is sent.

When to use variants:

- **Multi-tenant** — each customer sees notification content specific to their brand or product context, without a separate template per [tenant](/docs/tenants).
- **Localisation** — one template serves multiple languages. See [Multi-lingual Templates](/docs/multi-lingual-template).
- **A/B testing** — different copy to different audience segments to measure engagement via [Analytics](/docs/analytics).

---

## Variant selection

At send time, SuprSend evaluates all variants for a channel. Selection follows these rules in order:

1. **All conditions on a variant must match** — partial matches are skipped entirely.
2. The **first variant in order** that matches all its conditions is sent. If you want a specific variant to take priority, move it higher in the list.
3. If no variant matches, the **default variant** is sent as the fallback.

**Example — layered conditions:**

| Variant | Conditions | Wins when |
|---|---|---|
| Default | (none) | No other variant matches |
| Spanish | `$recipient.language = es` | Any Spanish-language recipient |
| Acme Spanish | `$recipient.language = es` + `$tenant.id = acme` | Acme tenant + Spanish language |

A trigger for an Acme tenant recipient with `language = es` qualifies both "Spanish" and "Acme Spanish". Whichever appears first in the variant order is sent — so place more specific variants (like "Acme Spanish") above general ones (like "Spanish") to ensure the right match.

Click the **+** button next to "All Variants" in the left panel. A menu appears with two options:

- **New Channel** — add a new channel to the template. This opens the channel selection screen where you select one or more channels and click **Add Channels**.
- **New Variant** — create a new variant with conditions for an existing channel.

**Adding a new channel** — selecting **New Channel** shows the full channel selection grid. Pick the channels you want to add and click **Add Channels**.

<Frame caption="Select channels to add to the template">
  <img src="/images/docs/templates-variants-new-channel.png" />

**Creating a new variant** — selecting **New Variant** opens the Create Variant modal:

<Frame caption="Create Variant modal — Channels, ID, Locale, Tenant, and Conditions">
  <img src="/images/docs/templates-variants-create-modal.png" />

**Fields in the Create Variant modal:**

| Field | Description |
|---|---|
| **Channels** | Select one or more channels this variant applies to (e.g., SMS, Email). *(Required)* |
| **ID** | Unique identifier for the variant. Can contain alphanumeric characters, underscore, hyphen, and dot. Max 128 characters. *(Required)* |
| **Locale** | Language for the variant (e.g., English, Spanish, Hindi). *(Required)* |
| **Tenant** | Tenant ID this variant is scoped to. Leave empty for non-tenant-specific variants. |
| **Conditions** | Rules that determine when this variant is sent. See [Condition operators](#condition-operators) below. |

<Info>
  The modal confirms: _"This variant will be sent when below conditions match. The first variant in the order matching the condition will be sent."_
</Info>

### Condition operators

Conditions are built using **Data Type** (Recipient, Actor, Tenant, or Input Payload), **Property** (the field name), **Operator**, and **Value**. You can combine multiple conditions with **+ OR** logic.

| Operator | Description |
|---|---|
| `==` | Equals |
| `!=` | Not equals |
| `>` | Greater than |
| `>=` | Greater than or equal to |
| `<` | Less than |
| `<=` | Less than or equal to |
| `contains` | Value contains the substring |
| `not contains` | Value does not contain the substring |
| `is empty` | Value is empty or null |
| `is not empty` | Value is not empty |
| `datetime is` | Datetime equals a specific value |
| `datetime is before` | Datetime is before a specific value |
| `datetime is after` | Datetime is after a specific value |
| `intersects (array)` | Array has at least one common element |
| `not intersects (array)` | Array has no common elements |

All conditions on a variant must match for it to qualify. Use **+ OR** to add alternative condition groups.

## Editing a variant

Click **Edit** on any variant to open it in the editor. Editing always works on the **draft version** — the live version is never directly modified. Content saves automatically as you type.

Each variant is edited and published independently. Publishing one variant does not affect others in the same template.

> **Tip:** Use **Import Content** to seed a new variant with content from another variant in this template or a different template. Faster than starting from scratch when variants share most of their content. See [Import content](/docs/templates#import-content) for details.

## Committing changes

Click **Commit** in the top-right corner to make your draft changes live. The Commit Changes modal shows a summary of all changes — variants edited, deleted, or with errors, plus any template settings changes. You can deselect specific changes you don't want to commit.

<Frame caption="Commit Changes modal — review and selectively commit variants">
  <img src="/images/docs/templates-commit-modal.png" />
</Frame>

- **Description** — add a message describing the changes (e.g., "Updated variant for web-push"). This appears in the version history.
- **Version name** — auto-generated (V1, V2, V3…) and not editable.

Once committed, the changes are live immediately and used in all subsequent workflow runs.

**WhatsApp and SMS variants** enter an **Approval Pending** state after committing rather than going live immediately. See [Approval flow](#approval-flow-whatsapp-and-sms) below.

## Approval flow (WhatsApp and SMS)

WhatsApp and [DLT](/docs/dlt-guidelines) SMS templates require [vendor](/docs/vendors) approval before they can be sent. Publishing puts the variant into **Approval Pending** — an **Approve / Reject** button appears when you hover on the variant.

Clicking it opens a modal:

1. **Already approved or needs uploading?**
   - If already approved at the vendor portal: enter the approved template ID and template name from the vendor portal.
   - If not yet approved: the modal shows the template content to upload manually at the vendor portal.
2. **Select status** — Approved or Rejected.
   - If rejected: enter the rejection reason.
3. For **[multi-lingual variants](/docs/multi-lingual-template)**, approval is handled per language — each language is uploaded and approved separately at the vendor end. The approval button appears at the language level.
4. If a **[fallback vendor](/docs/vendor-fallback)** is configured, you must confirm approval (or rejection) for each vendor separately.

The variant goes live as soon as it is approved with the primary vendor. Rejection returns it to Draft for revision.

## Common patterns

**Single template for multiple tenants**

Create one variant per tenant using a `$tenant.id` condition. Use the default variant as the fallback for tenants without a custom variant. Onboarding a new tenant becomes a template edit — no workflow change, no deployment.

**Layered localisation with per-tenant content**

Add a language variant for each locale (`$recipient.language = fr`, `$recipient.language = de`, etc.). For tenants that need both brand customisation and localisation, combine conditions: `$tenant.id = acme` + `$recipient.language = fr`. Place the more specific variant (tenant + language) above the general one (language only) in the variant order so it matches first.

**A/B testing with controlled rollout**

Create a challenger variant with a condition targeting a subset of your audience — for example, a custom attribute like `$recipient.cohort = beta`. Compare [delivery metrics](/docs/analytics). To promote the challenger: adjust its conditions to match the broader audience, or delete the control variant and update the default.

## Variant evaluation at send time

When a [workflow](/docs/workflows) triggers a notification, SuprSend evaluates variants for each enabled channel independently. Here's the exact evaluation flow:

<Steps>
  <Step title="Resolve tenant and locale">
    SuprSend resolves the **tenant** from the `tenant_id` in the workflow trigger, and the **locale** from the recipient's `preferred_language` in their user profile.

    **Tenant** and **locale** are soft properties — they have fallback behaviour:
    - If a variant exists for the specific tenant + locale, it is used.
    - If not, SuprSend falls back to the specific tenant + default locale (English).
    - If no tenant-specific variant exists, it falls back to the default tenant + recipient's locale.
    - Final fallback: default tenant + default locale (the **default** variant).
  </Step>

  <Step title="Evaluate conditions">
    For each variant (in order, top to bottom), SuprSend checks if **all** conditions match against the trigger payload, recipient profile, and tenant data.

    - All conditions on a variant must match — partial matches are skipped.
    - The **first variant in order** that matches all its conditions is selected.
    - Conditions on properties other than tenant and locale are **hard checks** — there is no fallback. If a condition like `$recipient.plan == "pro"` doesn't match, that variant is skipped entirely.
  </Step>

  <Step title="Send or fallback">
    If a matching variant is found, its content is rendered and sent. If no variant matches, the **default** variant is sent.

    If the default variant also has missing required content (e.g., empty body), the notification for that channel is skipped.
  </Step>
</Steps>

**Fallback hierarchy summary:**

| Property | Fallback behaviour |
|---|---|
| **Tenant** (`$tenant.id`) | Falls back to default tenant if no match |
| **Locale** (`$recipient.language`) | Falls back to default locale (English) if no match |
| **All other conditions** | No fallback — variant is skipped if any condition doesn't match |

<Info>
  Ordering matters. If two variants both match (e.g., a general "Spanish" variant and a more specific "Acme + Spanish" variant), the one **higher in the list** wins. Drag variants to reorder them — the default variant always stays at the bottom and cannot be moved.
</Info>

## Best practices

- **Order specific variants first** — place variants with more conditions (e.g., tenant + language) above general ones (e.g., language only). The first match wins.
- **Use the default variant as a fallback** — always keep meaningful content in the default variant. It's the safety net when no other variant matches.
- **Keep conditions simple** — one or two conditions per variant is usually enough. Complex condition chains are harder to debug and maintain.
- **Test before committing** — use the [Test](/docs/testing-the-template) button to send a test notification with specific tenant and recipient values to verify the correct variant is picked.
- **Name variants descriptively** — use names like `acme-spanish` or `pro-users-hindi` rather than `variant-1`, `variant-2`. The name appears in the editor and version history.
- **Don't duplicate content unnecessarily** — if two variants differ by only a few words, use [Import content](/docs/templates#import-content) to copy the base and edit only what's different.
- **Disable channels instead of deleting** — if you temporarily don't want to send on a channel, [disable it](#on-a-channel-three-dot-menu) instead of deleting. Content is preserved for when you re-enable.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="What happens if no variant matches?">
    The **default** variant is sent. Every template always has a default variant that cannot be deleted. It acts as the fallback for all recipients who don't match any specific variant's conditions.
  </Accordion>

  <Accordion title="How does ordering affect which variant is sent?">
    Variants are evaluated top to bottom. The first variant whose conditions all match is sent — subsequent variants are not evaluated. Drag variants to reorder them. The default variant always stays at the bottom.
  </Accordion>

  <Accordion title="What are soft vs hard condition checks?">
    **Soft checks** (tenant and locale) have fallback behaviour — if a specific tenant or language variant doesn't exist, SuprSend falls back through the hierarchy (tenant+locale → tenant+default locale → default tenant+locale → default). **Hard checks** (all other conditions like `$recipient.plan == "pro"`) have no fallback — if the condition doesn't match, the variant is skipped.
  </Accordion>

  <Accordion title="Can I have different variants for different channels?">
    Yes. Variants are per-channel — you can have 3 variants for Email, 1 for SMS, and none (just default) for Push. Each channel is evaluated independently at send time.
  </Accordion>

  <Accordion title="How do I test which variant will be sent for a specific user?">
    Click the **Test** button in the editor and use the "Selected Variant" tab. Enter a recipient, select a tenant, and send a test. The variant whose conditions match the test data will be used. See [Testing Templates](/docs/testing-the-template).
  </Accordion>

  <Accordion title="Can I duplicate a variant across channels?">
    Not directly. Duplicate creates a copy within the same channel. To create similar content on another channel, use [Import content](/docs/templates#import-content) to copy from the source variant into a new variant on the target channel.
  </Accordion>

  <Accordion title="What happens when I disable a channel?">
    Notifications stop being sent on that channel, but the content is preserved. Re-enabling the channel makes it active again with the same content. This is useful for temporary pauses without losing work.
  </Accordion>

  <Accordion title="Can I reorder variants?">
    Yes. Drag variants up or down in the Variants panel to change their evaluation order. The default variant always stays at the bottom and cannot be moved above other variants.
  </Accordion>
</AccordionGroup>
