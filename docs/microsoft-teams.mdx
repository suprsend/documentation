This is a step-by-step guide to integrating and sending notifications to users on Microsoft Teams.

## Pre-Requisites

To send notifications on Microsoft Teams, you'll need to create a Teams bot. This bot will be responsible for sending notifications to users / channels in their Teams workspace. You'll also need a Microsoft 365 developer account and permission to add apps to your teams. You can ask your admin to assign you relevant permission, or you can sign up for a free Microsoft 365 developer program.

* [Sign up for a Microsoft 365 developer program](https://developer.microsoft.com/en-us/microsoft-365/dev-program/)

* [Create a Teams App](docs/microsoft-teams#create-teams-app)

  ### App Type and Tenant ID

    **App Type** must match how your bot is registered in Azure:

    | App Type | When to use | Tenant ID |
    |---|---|---|
    | `Single tenant` | Bots registered after **31 July 2025** — the only type Azure creates today | **Required** |
    | `Multi tenant` | Older bots registered before that date | Not used |

    <Warning>
      Microsoft deprecated multi-tenant bot registration on **31 July 2025**. If you created your bot
      in the Azure portal after that date, it is single tenant — the **Type of App** dropdown no
      longer offers Multi Tenant at all.

      A single-tenant bot configured as multi-tenant will appear to work: the access token is issued
      successfully, but every send is rejected with `401 Authorization has been denied for this request`.
      Set App Type correctly to avoid this.
    </Warning>

    For a single-tenant bot, **Tenant ID** is the Microsoft Entra tenant your bot is registered in.
    Find it in the [Azure portal](https://portal.azure.com/) under **Microsoft Entra ID → Overview → Tenant ID**, or on your app
    registration's **Overview** page as *Directory (tenant) ID*.

    <Note>
      Saving the vendor immediately attempts a real token request. If the **Access Token** field
      stays empty, the stored error explains what to fix — `AADSTS700016` means the app was not found
      in the tenant it was looked up in, which usually means the bot is single tenant but the Tenant
      ID is missing or wrong.

      A populated token confirms your credentials were accepted, but it does **not** by itself
      guarantee that sends will succeed. Microsoft issues the token, then separately checks at send
      time that it came from the tenant the bot is registered against — so a wrong App Type can
      produce a healthy-looking token here and a `401` on every send. Send a test notification to
      confirm the setup end to end.
    </Note>

  ### Sending to more than one organization (multi-tenant MS Teams)

    Most setups never need this. If every recipient is in the same Microsoft Entra directory as your
    bot, leave the defaults and skip ahead.

    It applies when one bot must reach users across several directories — a company with regional
    legal entities, directories inherited through acquisitions, or a product notifying users in its
    customers' own organizations. The deprecation above removed multi-tenant *bots*, but it did not
    remove the ability to serve multiple organizations. Two different settings are involved, and they
    are easy to confuse:

    | Setting | Where | Decides |
    |---|---|---|
    | **App Type** | SuprSend vendor form | Which Entra authority mints the bot's token |
    | **Supported account types** | Azure app registration → Authentication | Which directories can host the app |

    App Type stays `Single tenant` — that is the only option for a bot created today. The app
    registration is what makes the app installable elsewhere.

    <Steps>
      <Step title="Allow the app in other directories">
        In the [Azure portal](https://portal.azure.com/), open **App registrations → your app →
        Authentication**, and set **Supported account types** to *Multiple Entra ID tenants*.

        This is the only change on your side. The bot keeps minting its token from your own
        directory; this setting simply lets other organizations install the app.

        <Frame>
          <img src="/images/docs/msteams-supported-account-types.png" />
        </Frame>
      </Step>

      <Step title="Get the app into each organization">
        Build the app package once, as in **Create Teams app** above, then distribute it. Each
        organization's Teams administrator uploads it to their own catalog — Teams admin center →
        **Teams apps → Manage apps → Upload new app** — or installs it from the Teams Store if you
        have published it there.

        An administrator in that organization has to approve it. Until your app registration has a
        verified publisher (MPN ID), their end users cannot consent to it themselves.
      </Step>

      <Step title="Install it for the recipients">
        Installing the app in a catalog does not put it in front of anyone. In each organization:

        - **For direct messages** — the app must be installed for each user, in *personal* scope.
          Admins can push this to everyone at once through Teams admin center → **Teams apps → Setup
          policies → Installed apps**.
        - **For channels** — add the app to the team, then **@mention the bot once in the channel**.
          Adding the app is not enough on its own; the mention is what puts the bot in the channel's
          conversation roster. It applies team-wide afterwards.
      </Step>

      <Step title="Keep one vendor, and set tenant_id per user">
        One MS Teams vendor serves every organization — same App ID, same password, same
        **Tenant ID** (your bot's own directory).

        What changes is the user profile: each subscriber carries the `tenant_id` of the organization
        that person is actually in, alongside their `user_id` or `conversation_id`.

        ```json
        {
          "tenant_id": "<the recipient's organization>",
          "user_id": "<their Entra object ID>"
        }
        ```
      </Step>
    </Steps>

    <Warning>
      `tenant_id` on the user profile is the **recipient's** organization. `Tenant ID` on the vendor is
      the directory your **bot** is registered in. They hold the same value when a bot serves only its
      own directory, which is why the difference rarely shows — but once a bot serves several, a
      profile without its own `tenant_id` falls back to the vendor's and the send fails with
      `401 Authorization has been denied for this request`.
    </Warning>

  ## Update teams channel in user or object profile

    The information required in the user profile is dependent on the type of message you are sending.

    <AccordionGroup>
      <Accordion title="Sending a direct message" defaultOpen={false}>
        To send a direct message to a user, add `tenant_id` , `service_url` of the tenant, and `conversation_id` or `user_id` corresponding to user personal chat. Only the target — `conversation_id` or `user_id` — is strictly required; `tenant_id` and `service_url` fall back to your vendor settings when omitted.

        You can pass this information in a json format using `user.add_ms_teams` method as below:

        <CodeGroup>

          ```python python
          distinct_id = "__uniq_user_id__"  # Unique identifier of user in your application
          # Instantiate User profile
          user = supr_client.user.get_instance(distinct_id=distinct_id)

          # using conversation_id
          user.add_ms_teams(
            {
          		"tenant_id": "c1981ab2-9aaf-xxxx-xxxx",
          		"service_url": "https://smba.trafficmanager.net/amer",
          		"conversation_id": "19:c1524d7c-a06f-456f-8abe-xxxx"
            })

          # using user_id
          user.add_ms_teams(
            {
          		"tenant_id": "c1981ab2-9aaf-xxxx-xxxx",
          		"service_url": "https://smba.trafficmanager.net/amer",
          		"user_id": "29:1nsLcmJ2RKtYH6Cxxxx-xxxx"
            })

          response = user.save()
          print(response)
          ```

        <Note>
          `service_url` is set per user profile. Microsoft's own guidance is to store the
          `serviceUrl` from the most recent inbound activity, since it is region-pinned and can
          change — and a Multi-Geo tenant can place two users in the same directory in different
          regions, so it genuinely varies per recipient.

          Both `tenant_id` and `service_url` are **optional**. If `service_url` is omitted, SuprSend
          uses Microsoft's global endpoint `https://smba.trafficmanager.net/teams`, which routes to
          the correct region automatically. That is the right choice unless your tenant is in a
          sovereign cloud such as GCC High or DoD, which have their own endpoints.
        </Note>

        You'll get **tenant ID** from the [Azure portal](https://portal.azure.com/), under **Microsoft Entra ID → Overview**.

        You can get **user\_id** by following the steps to [fetch the roster or user profile](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/get-teams-context?tabs=json#fetch-the-roster-or-user-profile). You'll need authentication token to fetch user profile. You can get this token from SuprSend vendor page after saving the form.

        <Tip>
          The roster returns two identifiers per member. Use the **Entra object ID** — it is stable
          for the life of the user, and it is what `user_id` expects.

          | Identifier | In the response | Notes |
          |---|---|---|
          | Entra object ID | `aadObjectId` on `/members`, `objectId` on `/pagedmembers` | Stable. Prefer this |
          | `29:…` | `id` on both | Encrypted per bot app registration — replace the bot and every stored value stops resolving |

          The object ID comes back as `null` unless your app manifest declares a resource-specific
          consent permission such as `TeamMember.Read.Group`. If you cannot add that, `pagedmembers`
          still returns `userPrincipalName` — resolve it to an object ID with
          `GET https://graph.microsoft.com/v1.0/users/{upn}?$select=id`, or look the user up in the
          [Azure portal](https://portal.azure.com/) under **Microsoft Entra ID → Users**.
        </Tip>

        **A Workflows webhook accepts Adaptive Cards only.** Plain text and MessageCard are not
        rendered, so your MS Teams template must produce an Adaptive Card for this delivery path.

        Use **Adaptive Card version 1.4 or 1.5**. Version 1.6 renders through the bot but fails
        silently through a Workflows webhook — the request is accepted and nothing appears in the
        channel.

        <Frame>
          <img src="/images/docs/msteams-adaptive-card-template.png" />
        </Frame>

        There are two ways to handle a plain-text template on this path.

        **Wrap the text in a card.** Keep one template and give it a single `TextBlock`, so the same
        template works over the bot and over the webhook:

        ```json
        {
          "type": "AdaptiveCard",
          "version": "1.5",
          "body": [ { "type": "TextBlock", "text": "Deployment finished", "wrap": true } ]
        }
        ```

        **Or build a workflow that accepts both.** Instead of starting from the webhook template,
        create the flow yourself with a condition on the incoming payload — cards go one way, text the
        other:

        <Frame>
          <img src="/images/docs/msteams-workflow-text-and-card.png" />
        </Frame>

        1. Trigger: **When a Teams webhook request is received**
        2. Add a **Condition**, with this expression on the left and *is greater than* `0` on the right:

            ```
            length(coalesce(triggerBody()?['attachments'], json('[]')))
            ```

        3. **If yes** — add **Post card in a chat or channel**, choose the team and channel, and set
            **Adaptive Card** to:

            ```
            string(first(triggerBody()?['attachments'])?['content'])
            ```

        4. **If no** — add **Post message in a chat or channel** and set the message to:

            ```
            triggerBody()?['text']
            ```

        The condition counts `attachments` on the request. SuprSend sends a card there and plain text
        in `text`, so a card payload takes the first branch and a text payload the second. `coalesce`
        supplies an empty array when `attachments` is absent, which is what stops the expression
        erroring on a text-only payload.

        See [MS Teams template](/docs/ms-teams-template) for authoring the templates themselves.

### Order of precedence
        Microsoft teams profile should only contain `incoming_webhook->url`, or the bot configurations like `tenant_id`, `conversation_id` and `service_url` . If there are multiple keys in `user.add_ms_teams()` call, the order of precedence is as follows:

        `incoming_webhook->url` > `conversation_id` > `user_id`. E.g., if your add\_ms\_teams argument is as follows:

## Tenancy in Microsoft teams

In scenarios where you're sending notifications on behalf of your enterprise clients, each with their own team applications for communicating with end-users, you can define distinct app configurations at the tenant level. In SuprSend, we presently identify tenants as tenants.

To support this, simply include the app configuration for the tenant on the vendor details page. This will override the default tenant vendor at the time of sending notification. This configuration needs to be set up once, and SuprSend will seamlessly direct all notifications associated with that tenant through the vendor configuration specified for the tenant.

> In case you don't have vendor defined for a tenant, notifications will automatically fallback to the default vendor credentials.

Refer Steps to configure tenant level vendor [here](/docs/tenant-vendor)
