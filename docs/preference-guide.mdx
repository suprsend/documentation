Notification preferences give users control over what they hear from your app, on which channel, and how often. Get them right and users stay engaged — they can mute what's noisy without losing what matters. Skip them and users will unsubscribe from everything.

This guide covers nine preference patterns drawn from real-world use cases, from simple channel opt-in/opt-outs to complex multi-tenant setups. Each section explains what the pattern is, when to use it, how to configure it in SuprSend, and the code to implement it in your app.

<Note>
  **New to preferences in SuprSend?** Read the [User Preferences overview](/docs/user-preferences) first — it covers how categories, channels, and the preference API response are structured. For multi-tenant setups, see [Tenant Preferences](/docs/tenant-preference).

  The code examples in this guide use the [`@suprsend/react`](/docs/preference-react-sdk) SDK. If you want a ready-made preference UI without building from scratch, see the [Embedded Preference Centre](/docs/embedded-preference-centre).
</Note>

## 1. Channel opt-in / opt-out

Users control what they receive on each channel. For every channel your app uses (Email, SMS, WhatsApp, Push, etc.), the user picks one of two options:

- **All** — receive all notifications on this channel, except categories they've explicitly turned off
- **Required** — receive only notifications from categories marked as mandatory (Can't Unsubscribe)

Separately, users can also turn individual channels on or off per notification category — for example, keeping Email on for "Product Updates" but turning off WhatsApp for the same category. These are the per-category channel checkboxes shown in the **BY TOPIC** section of the screenshot.

The `channel_preferences` array in the API response drives the global All / Required control. Each item has a `channel` name and an `is_restricted` boolean: `false` means All, `true` means Required. The per-category channel preferences live under `sections[].subcategories[].channels`.

<Frame caption="Channel-level preferences">
  <img src="/images/channel.png" alt="Channel-level preferences" width="450" />
</Frame>

### Configure in SuprSend

1. Go to **Developers → [Notification categories](/docs/managing-notification-categories)** and select a root-category (System, Transactional, or Promotional)
2. Click **`+Section`** to create a section (e.g. "Product", "Billing"). Add a name and click **`Save Changes`**
3. Click **`+Sub-Category`**, fill in the name, select the section, and set a default preference (**On**, **Off**, or **Can't Unsubscribe**)
4. Click **`Publish Changes`**

### Build in your app

Call `getPreferences()` in your parent component on page load and pass the result down as `preferenceData`. The response gives you two independent parts:

- `channel_preferences` — render one row per channel with **All** / **Required** radio buttons. Read `is_restricted` to know which is currently selected: `false` = All, `true` = Required.

Pass `ChannelLevelPreferenceOptions.ALL` or `ChannelLevelPreferenceOptions.REQUIRED` to `updateOverallChannelPreference` when the user changes their selection. Per-category channel checkboxes (which use `sections[].subcategories[].channels`) are covered in Section 2.

```javascript
import {
  ChannelLevelPreferenceOptions,
  useSuprSendClient,
} from "@suprsend/react";

function ChannelPreferences({ preferenceData, setPreferenceData }) {
  const suprSendClient = useSuprSendClient();

  // Global All vs Required control per channel
  // is_restricted: false = All, is_restricted: true = Required
  // API value for "Required" is ChannelLevelPreferenceOptions.REQUIRED
  const handleOverallChannelChange = async (channel, status) => {
    const resp = await suprSendClient.user.preferences.updateOverallChannelPreference(
      channel.channel,
      status // ChannelLevelPreferenceOptions.ALL or ChannelLevelPreferenceOptions.REQUIRED
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  return (
    <>
      {/* Global channel controls — one row per channel */}
      {preferenceData?.channel_preferences?.map((channel, i) => (
        <div key={i}>
          <p>{channel.channel}</p>
          <p>{channel.is_restricted ? "Allow required notifications only" : "Allow all notifications"}</p>
          <input
            type="radio"
            checked={!channel.is_restricted}
            onChange={() => handleOverallChannelChange(channel, ChannelLevelPreferenceOptions.ALL)}
          /> All
          <input
            type="radio"
            checked={channel.is_restricted}
            onChange={() => handleOverallChannelChange(channel, ChannelLevelPreferenceOptions.REQUIRED)}
          /> Required
        </div>
      ))}
    </>
  );
}
```

<Tip>
  **When to use:** Your app sends on multiple channels and users want coarse control over each one. Examples: "Email me everything, but push only for required notifications", "I only want SMS for critical alerts." Common in consumer apps, marketplaces, and collaboration tools.
</Tip>

## 2. Notification category toggles

Users turn each notification type on or off individually — for example, keeping "Invoices & receipts" on while turning off "Sales Newsletter" — and optionally choose which channels receive each type.

This is the standard notification settings page that most apps need. The response gives you sections (top-level groupings like Product, Billing, Sales) containing subcategories (the individual notification types). Each subcategory has a toggle and a list of channel checkboxes.

<Frame caption="Category-level preferences">
  <img src="/images/category.png" alt="Category-level preferences" width="450" />
</Frame>

### Configure in SuprSend

1. Go to **Developers → [Notification categories](/docs/managing-notification-categories)** and select a root-category
2. Click **`+Section`** to create sections (e.g. "Product", "Billing", "Sales"). Add a name and click **`Save Changes`**
3. Click **`+Sub-Category`** for each notification type, select its section, and set a default preference (**On**, **Off**, or **Can't Unsubscribe**)
4. Click **`Publish Changes`**
5. To verify the preference page looks correct, go to **Developers → [Notification categories](/docs/managing-notification-categories)** and click **`Preview`** to see a live preview of the preference UI

### Build in your app

Call `getPreferences()` in your parent component and pass `preferenceData` as a prop. Render sections as headings and subcategories as rows, each with a toggle and channel checkboxes below it.

Three things to handle carefully:

- **`is_editable: false` on a subcategory** means the category is set to **Can't Unsubscribe** in SuprSend. Disable the toggle — users cannot opt out.
- **`is_editable: false` on a channel inside a subcategory** means that specific channel is mandatory for that category and cannot be turned off. Disable the channel checkbox independently of the subcategory toggle. A category can have `is_editable: true` (user can toggle it off) while individual channels within it have `is_editable: false` (those channels cannot be removed).
- **`channels` can be an empty array** for some subcategories. Use optional chaining (`subcategory?.channels?.map(...)`) to handle this safely.

<Note>
  All preference updates (`updateCategoryPreference`, `updateChannelPreferenceInCategory`, `updateOverallChannelPreference`) are **optimistic** — the UI updates immediately and the actual API call happens in the background with a 1-second debounce. Set up these emitter listeners once when loading preferences to handle the confirmed result and catch server-side errors:

  ```javascript
  // Fires after the background API call succeeds — sync your UI state with confirmed data
  suprSendClient.emitter.on("preferences_updated", (preferenceDataResp) => {
    setPreferenceData({ ...preferenceDataResp.body });
  });

  // Fires if the background API call fails — show an error toast or revert the UI
  suprSendClient.emitter.on("preferences_error", (errorResp) => {
    console.log("Error:", errorResp?.error?.message);
  });
  ```
</Note>

```javascript
import { PreferenceOptions, useSuprSendClient } from "@suprsend/react";

function CategoryPreferences({ preferenceData, setPreferenceData }) {
  const suprSendClient = useSuprSendClient();

  // Toggle a category on or off
  // value is true = opt_in, false = opt_out
  const handleCategoryChange = async (subcategory, value) => {
    const resp = await suprSendClient.user.preferences.updateCategoryPreference(
      subcategory.category,
      value ? PreferenceOptions.OPT_IN : PreferenceOptions.OPT_OUT
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  // Toggle a specific channel on or off within a category
  // Skip if is_editable is false — that channel is mandatory for this category
  const handleChannelInCategoryChange = async (channel, subcategory) => {
    if (!channel.is_editable) return;
    const resp = await suprSendClient.user.preferences.updateChannelPreferenceInCategory(
      channel.channel,
      channel.preference === PreferenceOptions.OPT_IN
        ? PreferenceOptions.OPT_OUT
        : PreferenceOptions.OPT_IN,
      subcategory.category
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  return preferenceData?.sections?.map((section, index) => (
    <div key={index}>
      {/* Render section heading only if it has a name */}
      {section?.name && <h3>{section.name}</h3>}
      {section?.subcategories?.map((subcategory, i) => (
        <div key={i}>
          <div>
            <span>{subcategory.name}</span>
            <p>{subcategory.description}</p>
          </div>
          {/* Disable toggle if is_editable is false — this category is Can't Unsubscribe */}
          {/* Replace with your own toggle/switch component */}
          <button
            disabled={!subcategory.is_editable}
            onClick={() => handleCategoryChange(subcategory, subcategory.preference !== PreferenceOptions.OPT_IN)}
            style={{ opacity: !subcategory.is_editable ? 0.5 : 1, background: subcategory.preference === PreferenceOptions.OPT_IN ? '#2563EB' : '#D1D5DB', borderRadius: '9999px', padding: '2px 8px', border: 'none', cursor: !subcategory.is_editable ? 'not-allowed' : 'pointer' }}
          >
            {subcategory.preference === PreferenceOptions.OPT_IN ? 'On' : 'Off'}
          </button>
          {/* Channel checkboxes — channels can be an empty array, handle with ?. */}
          <div>
            {subcategory?.channels?.map((channel, j) => (
              <button
                key={j}
                disabled={!channel.is_editable}
                onClick={() => handleChannelInCategoryChange(channel, subcategory)}
                style={{ opacity: channel.preference === PreferenceOptions.OPT_IN ? 1 : 0.4 }}
              >
                {channel.channel}
              </button>
            ))}
          </div>
        </div>
      ))}
    </div>
  ));
}
```

<Tip>
  **When to use:** The default for most apps — the standard notification settings page. Examples: e-commerce (order updates on, promotions off), SaaS (product updates via email, billing via email + SMS), social apps (comments on, likes off).
</Tip>

## 3. Digest frequency

Instead of one notification per event, users choose how often they want a summary — Daily, Weekly, or Off. A user who picks Daily gets one email at 09:00 summarising everything that happened that day instead of a notification for every single event.

This works by storing the user's chosen schedule as a custom property on their profile using `user.set()`. The workflow's Digest node reads this property at runtime via a [dynamic schedule](/docs/digest#dynamic-schedule-send-digest-based-on-user-preference) and fires at the schedule the user set.

<Frame caption="Digest preferences">
  <img src="/images/t1.png" alt="Digest preferences" width="450" />
</Frame>

### Configure in SuprSend

1. Go to **Developers → [Notification categories](/docs/managing-notification-categories)** and create a sub-category for the notification type you want to digest (e.g. "Activity Summary"). Click **`+Sub-Category`**, fill in the name, and set a default preference
2. Click **`Publish Changes`**
3. In your workflow, add a **[Digest node](/docs/digest)** and configure it to use a **dynamic schedule**. Set the dynamic schedule key to reference the user profile property where you store the schedule (e.g. `."$recipient".digestSchedule`). See [Dynamic schedule](/docs/digest#dynamic-schedule-send-digest-based-on-user-preference)

### Build in your app

Show radio buttons for Daily / Weekly / Off and a time picker for daily and weekly. On save, write the schedule to the user's profile with `user.set()`.

<Warning>
  This is a **profile update**, not a preference API call. Use `suprSendClient.user.set()` to save the digest schedule directly to the user's profile. The workflow's Digest node reads this property via the dynamic schedule key — not via the preference API.
</Warning>

```javascript
import { useSuprSendClient } from "@suprsend/react";
import { useState } from "react";

function DigestPreferences() {
  const suprSendClient = useSuprSendClient();
  const [frequency, setFrequency] = useState("daily");
  const [time, setTime] = useState("09:00");

  // Save digest schedule as a user profile property.
  // In your workflow, set the Digest node's dynamic schedule key to:
  //   ."$recipient".digestSchedule
  // See: https://docs.suprsend.com/docs/digest#dynamic-schedule-send-digest-based-on-user-preference
  const handleSave = async () => {
    await suprSendClient.user.set({
      digestSchedule: {
        frequency: frequency,      // "daily" | "weekly"
        time: time,                // "09:00" — time the digest closes (hh:mm)
        tz_selection: "recipient", // use the recipient's timezone from their profile
      },
    });
  };

  return (
    <div>
      {["daily", "weekly", "off"].map((option) => (
        <label key={option}>
          <input
            type="radio"
            checked={frequency === option}
            onChange={() => setFrequency(option)}
          />
          {option.charAt(0).toUpperCase() + option.slice(1)}
        </label>
      ))}
      {(frequency === "daily" || frequency === "weekly") && (
        <input type="time" value={time} onChange={(e) => setTime(e.target.value)} />
      )}
      <button onClick={handleSave}>Save</button>
    </div>
  );
}
```

<Tip>
  **When to use:** Users get too many individual notifications and want a summary instead. Examples: daily activity digest ("Here's what happened in your workspace today"), weekly analytics reports, aggregated comment or mention notifications, team standup summaries.
</Tip>

**Related docs:** [Digest](/docs/digest) | [Dynamic schedule](/docs/digest#dynamic-schedule-send-digest-based-on-user-preference) | [Users API](/docs/users)

## 4. Hide categories by tenant plan

In a multi-tenant app, different tenants (customers) should only see the notification categories relevant to their plan or configuration. A free-plan tenant sees a limited set of categories; a paid-plan tenant sees everything they've subscribed to. Categories hidden for a tenant don't appear in `getPreferences()` at all, and notifications for those categories are never sent to that tenant's users — even if a user previously opted in.

The mechanism is `visible_to_subscriber` on the tenant's category settings. Set it to `false` to hide a category completely from that tenant's users.

<Frame caption="Free-plan users see only core categories; paid-plan users see the full set">
  <img src="/images/tenant_res.png" alt="Tenant-restricted categories — free vs paid plan" width="560" />
</Frame>

### Configure in SuprSend

Go to **Tenants → select your tenant → Tenant Preference** in the SuprSend dashboard. For each category you want to restrict, set `visible_to_subscriber: false`.

For programmatic management (e.g. automatically restricting categories when a customer downgrades their plan), use the API:

```bash
curl -X PATCH "https://hub.suprsend.com/v1/tenant/{tenant_id}/category/{category_slug}/" \
  -H "Authorization: Bearer {secret_key}" \
  -H "Content-Type: application/json" \
  -d '{"preference": "opt_out", "visible_to_subscriber": false}'
```

Setting `visible_to_subscriber: false` does two things: it removes the category from the user's preference page, and it stops notifications for that category from being sent to that tenant's users — even if they previously opted in. See [Update Tenant Default Preference](/reference/update-tenant-default-preference).

### Build in your app

Pass `tenantId` to `getPreferences()`. SuprSend filters the response server-side — **categories with `visible_to_subscriber: false` are not returned at all**. Your rendering code stays exactly the same as the category-level pattern; restricted tenants simply get fewer categories back.

```javascript
import { PreferenceOptions, useSuprSendClient } from "@suprsend/react";
import { useState, useEffect } from "react";

function TenantRestrictedPreferences({ tenantId }) {
  const suprSendClient = useSuprSendClient();
  const [preferenceData, setPreferenceData] = useState();

  useEffect(() => {
    // Only categories visible for this tenant are returned
    // Free-plan tenants get fewer categories than paid-plan tenants
    suprSendClient.user.preferences
      .getPreferences({ tenantId })
      .then((resp) => {
        if (resp.status !== "error") setPreferenceData({ ...resp.body });
      });
  }, [tenantId]);

  const handleCategoryChange = async (category, value) => {
    const resp = await suprSendClient.user.preferences.updateCategoryPreference(
      category,
      value ? PreferenceOptions.OPT_IN : PreferenceOptions.OPT_OUT
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  // Render sections and subcategories — same pattern as Category-level preferences
  return preferenceData?.sections?.map((section, i) => (
    <div key={i}>
      {section?.name && <h3>{section.name}</h3>}
      {section?.subcategories?.map((sub, j) => (
        <div key={j}>
          <span>{sub.name}</span>
          {/* Replace with your own toggle/switch component */}
          <button
            disabled={!sub.is_editable}
            onClick={() => handleCategoryChange(sub.category, sub.preference !== PreferenceOptions.OPT_IN)}
            style={{ opacity: !sub.is_editable ? 0.5 : 1, background: sub.preference === PreferenceOptions.OPT_IN ? '#2563EB' : '#D1D5DB', borderRadius: '9999px', padding: '2px 8px', border: 'none', cursor: !sub.is_editable ? 'not-allowed' : 'pointer' }}
          >
            {sub.preference === PreferenceOptions.OPT_IN ? 'On' : 'Off'}
          </button>
        </div>
      ))}
    </div>
  ));
}
```

<Tip>
  **When to use:** Multi-tenant SaaS where each tenant's plan determines which notifications are available. Examples: free-plan tenants see only core alert categories, paid tenants see advanced analytics alerts and SLA breach alerts they've subscribed to.
</Tip>

## 5. Filter categories by department or role

Different teams, roles, or departments need different notifications. A sales rep doesn't need deploy alerts; an engineer doesn't need pipeline updates. Instead of showing every category to every user and relying on them to configure it themselves, you filter the preference page automatically based on the user's department, role, or team — showing only the categories relevant to them.

This uses **tags**. You assign tags to notification categories or sections in SuprSend (e.g. `sales`, `finance`, `engineering`). When fetching preferences, you pass the relevant tag and SuprSend returns only the matching categories. The user never sees a department picker — your app reads their department/role/team from their profile or session and passes the corresponding tag silently.

When a tag is assigned at the **section level**, it automatically applies to all subcategories under that section via `effective_tags`.

<Frame caption="A sales user sees only sales-related notification categories">
  <img src="/images/t2_sales.png" alt="Sales department preferences" width="450" />
</Frame>

<Frame caption="A finance user sees only finance-related notification categories">
  <img src="/images/t2_finance.png" alt="Finance department preferences" width="450" />
</Frame>

### Configure in SuprSend

1. Go to **Developers → [Notification categories](/docs/managing-notification-categories)**
2. For each sub-category (or section), add the tag that matches the department it belongs to. For example, tag your "Deal updates" and "Pipeline alerts" sub-categories with `sales`; tag "Deploy alerts" and "Incident alerts" with `engineering`; tag "Budget alerts" and "Expense reports" with `finance`. Tags added at the section level automatically apply to all sub-categories in that section via `effective_tags`
3. Click **`Publish Changes`**

### Build in your app

Read the user's department from their profile or session, then pass it as the `tags` parameter to `getPreferences()`. No filter UI is needed — this happens entirely in code.

```javascript
import { PreferenceOptions, useSuprSendClient } from "@suprsend/react";
import { useState, useEffect } from "react";

function DepartmentPreferences({ user }) {
  const suprSendClient = useSuprSendClient();
  const [preferenceData, setPreferenceData] = useState();

  // Derive tag from user's department — fall back to "engineering" if not set
  const tag = user?.department || "engineering";

  useEffect(() => {
    // Only categories tagged with the user's department are returned
    // A sales user gets Sales Newsletter, Cart & checkout, etc.
    // A finance user gets Budget Alerts, Expense Reports, etc.
    suprSendClient.user.preferences
      .getPreferences({ tags: tag })
      .then((resp) => {
        if (resp.status !== "error") setPreferenceData({ ...resp.body });
      });
  }, [tag]);

  const handleCategoryChange = async (category, value) => {
    const resp = await suprSendClient.user.preferences.updateCategoryPreference(
      category,
      value ? PreferenceOptions.OPT_IN : PreferenceOptions.OPT_OUT
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  return preferenceData?.sections?.map((section, i) => (
    <div key={i}>
      {section?.name && <h3>{section.name}</h3>}
      {section?.subcategories?.map((sub, j) => (
        <div key={j}>
          <span>{sub.name}</span>
          {/* Replace with your own toggle/switch component */}
          <button
            disabled={!sub.is_editable}
            onClick={() => handleCategoryChange(sub.category, sub.preference !== PreferenceOptions.OPT_IN)}
            style={{ opacity: !sub.is_editable ? 0.5 : 1, background: sub.preference === PreferenceOptions.OPT_IN ? '#2563EB' : '#D1D5DB', borderRadius: '9999px', padding: '2px 8px', border: 'none', cursor: !sub.is_editable ? 'not-allowed' : 'pointer' }}
          >
            {sub.preference === PreferenceOptions.OPT_IN ? 'On' : 'Off'}
          </button>
        </div>
      ))}
    </div>
  ));
}
```

The `tags` parameter also supports logical filtering for more complex cases. See [Filter categories with tags](/docs/user-preferences#filter-categories-with-tags) for supported operators (`or`, `and`, `not`, `exists`).

<Tip>
  **When to use:** Users in different roles should automatically see only relevant notifications, with no manual configuration required. Examples: sales reps see deal and pipeline alerts, engineers see deploy and incident alerts, finance sees billing and expense alerts.
</Tip>

## 6. Tenant admin controls

In a B2B product, the person who configures notifications isn't the end user — it's an admin at the customer organisation. This pattern lets tenant admins control which categories are available to their users, what the defaults are, and which channels are enabled — all scoped to their tenant. End users then see only what their admin has left enabled.

The admin view shows a table of categories with a default on/off toggle and a "Keep it visible?" checkbox per category, which maps directly to `visible_to_subscriber` in the API.

<Frame caption="Tenant admin customizing notification preferences for their organization">
  <img src="/images/t3.png" alt="Tenant admin preferences" width="450" />
</Frame>

### Configure in SuprSend

1. First ensure your notification categories are set up under **Developers → [Notification categories](/docs/managing-notification-categories)** and published
2. Go to **Tenants → your tenant → Tenant Preference** in the SuprSend console — this is where tenant admins manage their org's defaults
3. Provide tenant admins access to configure categories via the [Tenant Preference API](/docs/tenant-preference). They can enable/disable categories, set default On/Off, and control channel availability — all scoped to their tenant

### Build in your app

Build two separate views:

**Admin view** — calls the Tenant Preference API to let the admin configure defaults and visibility per category. The columns in the admin UI map directly to API fields: the default on/off toggle maps to `preference`, the "Keep it visible?" checkbox maps to `visible_to_subscriber`.

**End-user view** — calls `getPreferences({ tenantId })` as usual. SuprSend filters the response automatically — users only see what their admin has left enabled. The rendering code is identical to the category-level pattern.

```javascript
import { PreferenceOptions, useSuprSendClient } from "@suprsend/react";

// End-user view — only shows what the tenant admin has enabled
function EndUserPreferences({ tenantId }) {

      category,
      value ? PreferenceOptions.OPT_IN : PreferenceOptions.OPT_OUT
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  return preferenceData?.sections?.map((section, i) => (
    <div key={i}>
      {section?.name && <h3>{section.name}</h3>}
      {section?.subcategories?.map((sub, j) => (
        <div key={j}>
          <span>{sub.name}</span>
          {/* Replace with your own toggle/switch component */}
          <button
            disabled={!sub.is_editable}
            onClick={() => handleCategoryChange(sub.category, sub.preference !== PreferenceOptions.OPT_IN)}
            style={{ opacity: !sub.is_editable ? 0.5 : 1, background: sub.preference === PreferenceOptions.OPT_IN ? '#2563EB' : '#D1D5DB', borderRadius: '9999px', padding: '2px 8px', border: 'none', cursor: !sub.is_editable ? 'not-allowed' : 'pointer' }}
          >
            {sub.preference === PreferenceOptions.OPT_IN ? 'On' : 'Off'}
          </button>
        </div>
      ))}
    </div>
  ));
}
```

<Tip>
  **When to use:** B2B or white-label products where each customer organisation's admin controls the notification experience for their users. Examples: one enterprise customer enables billing + security + product alerts while another only enables billing alerts; a white-label SaaS where each reseller configures the notification defaults for their own users.
</Tip>

## 7. Filter categories by module

Your product has distinct modules — like "Inflow alerts" and "Outflow alerts" in a data pipeline tool, or "Design" and "Engineering" in a project management tool. Users switch between modules and manage notifications for each one separately. The preference page re-fetches with a different tag each time the user switches tabs.

This is the same tag mechanism as Department (Section 5), but driven by a **visible tab selector** in the UI rather than silently from the user's profile.

<Frame caption="Filter by module">
  <img src="/images/t4.png" alt="Filter by module" width="450" />
</Frame>

### Configure in SuprSend

Go to **Developers → [Notification categories](/docs/managing-notification-categories)** and tag your sections or sub-categories per module. Two ways to structure this:

- **Option A — one section per module:** Click **`+Section`** to create a section per module (e.g. "Inflow alerts", "Outflow alerts"). Add a tag to the section (e.g. `inflow`). All sub-categories under that section inherit the tag automatically. Click **`Publish Changes`**.
- **Option B — one section, per-subcategory tags:** Create a single section (e.g. "Projects") with all sub-categories under it. Select each sub-category and add its own tag (e.g. `project-alpha`, `project-beta`). Filtering by tag returns that section with only the matching sub-categories.

### Build in your app

Render tab pills for each module. When the user switches tabs, update `selectedTag` and re-call `getPreferences()` with the new tag. The rest of the rendering is the same as category-level preferences.

```javascript
import { PreferenceOptions, useSuprSendClient } from "@suprsend/react";
import { useState, useEffect } from "react";

function ModulePreferences() {
  const suprSendClient = useSuprSendClient();
  const [selectedTag, setSelectedTag] = useState("inflow");
  const [preferenceData, setPreferenceData] = useState();

  useEffect(() => {
    // Re-fetch when the user switches modules — returns only categories for that tag
    suprSendClient.user.preferences
      .getPreferences({ tags: selectedTag })
      .then((resp) => {
        if (resp.status !== "error") setPreferenceData({ ...resp.body });
      });
  }, [selectedTag]);

  const handleCategoryChange = async (category, value) => {
    const resp = await suprSendClient.user.preferences.updateCategoryPreference(
      category,
      value ? PreferenceOptions.OPT_IN : PreferenceOptions.OPT_OUT
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  return (
    <>
      {/* Module tab selector */}
      {[
        { label: "Inflow alerts", tag: "inflow" },
        { label: "Outflow alerts", tag: "outflow" },
      ].map(({ label, tag }) => (
        <button
          key={tag}
          onClick={() => setSelectedTag(tag)}
          style={{ fontWeight: selectedTag === tag ? "bold" : "normal" }}
        >
          {label}
        </button>
      ))}

      {/* Categories filtered by the selected module tag */}
      {preferenceData?.sections?.map((section, i) => (
        <div key={i}>
          {section?.name && <h3>{section.name}</h3>}
          {section?.subcategories?.map((cat, j) => (
            <div key={j}>
              <span>{cat.name}</span>
              {/* Replace with your own toggle/switch component */}
              <button
                disabled={!cat.is_editable}
                onClick={() => handleCategoryChange(cat.category, cat.preference !== PreferenceOptions.OPT_IN)}
                style={{ opacity: !cat.is_editable ? 0.5 : 1, background: cat.preference === PreferenceOptions.OPT_IN ? '#2563EB' : '#D1D5DB', borderRadius: '9999px', padding: '2px 8px', border: 'none', cursor: !cat.is_editable ? 'not-allowed' : 'pointer' }}
              >
                {cat.preference === PreferenceOptions.OPT_IN ? 'On' : 'Off'}
              </button>
            </div>
          ))}
        </div>
      ))}
    </>
  );
}
```

<Tip>
  **When to use:** Your product has distinct modules and users want to manage notification preferences per module independently. Examples: a data pipeline tool with separate inflow and outflow alert tabs, a project management tool where users switch between team modules to manage alerts separately.
</Tip>

## 8. User-defined alert threshold

Some notifications are only useful when they cross a user-defined threshold. A storage alert at 1% full is noise; at 80% it's urgent. Users set their own trigger point, and the workflow only fires when the incoming metric crosses it.

The threshold value is a custom user profile property — not a preference setting. The preference controls whether the alert is on or off and which channels it goes to. The threshold controls *when* the workflow fires. Both parts are needed.

<Frame caption="Threshold alerts">
  <img src="/images/thresholdimg.png" alt="Threshold alerts" width="450" />
</Frame>

### Configure in SuprSend

1. Go to **Developers → [Notification categories](/docs/managing-notification-categories)**. Click **`+Sub-Category`**, name it (e.g. "Usage alerts") and set a default preference. Click **`Publish Changes`**
2. In your workflow, add a **[Branch node](/docs/branch)** that reads the threshold property from the user's profile and compares it to the incoming metric (e.g. fire when `usage_percent >= user.threshold_percent`). See [Workflows](/docs/workflows)

### Build in your app

Call `getPreferences()` in your parent component and pass `preferenceData` as a prop. The preference page for this pattern has two independent parts rendered together:

1. **Threshold picker** — a number input or slider. Saved via `user.set()` as a profile property. This is not a preference API call.
2. **Category preference** — the standard toggle and channel checkboxes for the "Usage alerts" category. Saved via `updateCategoryPreference` and `updateChannelPreferenceInCategory` as usual.

```javascript
import { PreferenceOptions, useSuprSendClient } from "@suprsend/react";
import { useState } from "react";

function ThresholdPreferences({ preferenceData, setPreferenceData }) {
  const suprSendClient = useSuprSendClient();
  const [threshold, setThreshold] = useState(80);

  // Part 1: Save threshold to user profile — this is a profile update, not a preference call
  // The workflow Branch node reads user.threshold_percent to decide when to fire
  const handleThresholdSave = async () => {
    await suprSendClient.user.set({
      threshold_percent: threshold, // e.g. 80 means "alert me when usage hits 80%"
    });
  };

  // Part 2: Category on/off — standard preference update
  const handleCategoryChange = async (category, value) => {
    const resp = await suprSendClient.user.preferences.updateCategoryPreference(
      category,
      value ? PreferenceOptions.OPT_IN : PreferenceOptions.OPT_OUT
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  return (
    <div>
      {/* Threshold picker */}
      <label>Alert me when usage reaches:</label>
      <input
        type="number"
        min={1}
        max={100}
        value={threshold}
        onChange={(e) => setThreshold(Number(e.target.value))}
      />
      <span>% of Usage</span>
      <button onClick={handleThresholdSave}>Set Alert</button>

      {/* Category preference — render the "Usage alerts" category with toggle + channels */}
      {preferenceData?.sections?.flatMap((s) => s.subcategories || [])
        .filter((sub) => sub.category === "usage-alerts")
        .map((sub, i) => (
          <div key={i}>
            {/* Replace with your own toggle/switch component */}
            <button
              disabled={!sub.is_editable}
              onClick={() => handleCategoryChange(sub.category, sub.preference !== PreferenceOptions.OPT_IN)}
              style={{ opacity: !sub.is_editable ? 0.5 : 1, background: sub.preference === PreferenceOptions.OPT_IN ? '#2563EB' : '#D1D5DB', borderRadius: '9999px', padding: '2px 8px', border: 'none', cursor: !sub.is_editable ? 'not-allowed' : 'pointer' }}
            >
              {sub.preference === PreferenceOptions.OPT_IN ? 'On' : 'Off'}
            </button>
            {sub?.channels?.map((channel, j) => (
              <button
                key={j}
                disabled={!channel.is_editable}
                onClick={() => {
                  if (!channel.is_editable) return;
                  suprSendClient.user.preferences.updateChannelPreferenceInCategory(
                    channel.channel,
                    channel.preference === PreferenceOptions.OPT_IN
                      ? PreferenceOptions.OPT_OUT
                      : PreferenceOptions.OPT_IN,
                    sub.category
                  ).then((resp) => {
                    if (resp.status !== "error") setPreferenceData({ ...resp.body });
                  });
                }}
                style={{ opacity: channel.preference === PreferenceOptions.OPT_IN ? 1 : 0.4 }}
              >
                {channel.channel}
              </button>
            ))}
          </div>
        ))}
    </div>
  );
}
```

<Tip>
  **When to use:** Users need to set their own trigger point for an alert, not just whether to receive it. Examples: cloud storage ("alert me at 80% full"), API rate limits ("notify at 90% of quota"), budget tracking ("warn me when spend hits 75%").
</Tip>

## 9. Per-project preferences

Each project needs a completely independent set of preferences — its own category toggles, its own channel settings, its own defaults. Tags won't work here because tags only filter categories; they don't give each project its own independent channel-level preferences or defaults.

The solution is to model each project as a **tenant** in SuprSend. Preferences are then scoped per tenant. When the user switches projects, you switch the `tenantId` passed to `getPreferences()`, and all reads and writes happen against that project's tenant.

<Frame caption="Project-level preferences — each project = tenant">
  <img src="/images/t5.png" alt="Project-level preferences" width="450" />
</Frame>

### Configure in SuprSend

1. Create **one tenant per project** in SuprSend (via **Tenants** in the dashboard or the Tenants API)
2. For each tenant, go to **Tenants → your tenant → Tenant Preference** and configure which categories are enabled, what the defaults are, and which channels are available
3. Ensure your notification categories are published under **Developers → [Notification categories](/docs/managing-notification-categories)**

### Build in your app

Show a project selector. When the user picks a project, pass its tenant ID to `getPreferences()`. Render the full preference UI — channel-level (All / Required per channel) and category-level (toggles + channel checkboxes). All update calls are automatically scoped to the selected tenant.

```javascript
import {
  PreferenceOptions,
  ChannelLevelPreferenceOptions,
  useSuprSendClient,
} from "@suprsend/react";
import { useState, useEffect } from "react";

// Example projects — in production these come from your own data
const PROJECTS = [
  { label: "Project Alpha", tenantId: "project-alpha" },
  { label: "Project Beta",  tenantId: "project-beta" },
];

function ProjectPreferences() {
  const suprSendClient = useSuprSendClient();
  const [selectedTenantId, setSelectedTenantId] = useState(PROJECTS[0].tenantId);
  const [preferenceData, setPreferenceData] = useState();

  useEffect(() => {
    // Switching projects re-fetches preferences scoped to that project's tenant
    suprSendClient.user.preferences
      .getPreferences({ tenantId: selectedTenantId })
      .then((resp) => {
        if (resp.status !== "error") setPreferenceData({ ...resp.body });
      });
  }, [selectedTenantId]);

  // Category toggle
  // Per SDK docs, all updates are scoped to the tenantId from the last getPreferences() call.
  // You do not pass tenantId to update methods — the SDK tracks it internally.
  const handleCategoryChange = async (category, value) => {
    const resp = await suprSendClient.user.preferences.updateCategoryPreference(
      category,
      value ? PreferenceOptions.OPT_IN : PreferenceOptions.OPT_OUT
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  // Channel checkbox within a category
  const handleChannelInCategoryChange = async (channel, subcategory) => {
    if (!channel.is_editable) return;
    const resp = await suprSendClient.user.preferences.updateChannelPreferenceInCategory(
      channel.channel,
      channel.preference === PreferenceOptions.OPT_IN
        ? PreferenceOptions.OPT_OUT
        : PreferenceOptions.OPT_IN,
      subcategory.category
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  // Global All / Required per channel
  const handleOverallChannelChange = async (channel, status) => {
    const resp = await suprSendClient.user.preferences.updateOverallChannelPreference(
      channel.channel,
      status
    );
    if (resp.status !== "error") setPreferenceData({ ...resp.body });
  };

  return (
    <>
      {/* Project selector */}
      {PROJECTS.map(({ label, tenantId }) => (
        <button key={tenantId} onClick={() => setSelectedTenantId(tenantId)}>
          {label}
        </button>
      ))}

      {/* Channel-level preferences (All / Required) */}
      {preferenceData?.channel_preferences?.map((channel, i) => (
        <div key={i}>
          <p>{channel.channel}</p>
          <input
            type="radio"
            checked={!channel.is_restricted}
            onChange={() => handleOverallChannelChange(channel, ChannelLevelPreferenceOptions.ALL)}
          /> All
          <input
            type="radio"
            checked={channel.is_restricted}
            onChange={() => handleOverallChannelChange(channel, ChannelLevelPreferenceOptions.REQUIRED)}
          /> Required
        </div>
      ))}

      {/* Category preferences */}
      {preferenceData?.sections?.map((section, i) => (
        <div key={i}>
          {section?.name && <h3>{section.name}</h3>}
          {section?.subcategories?.map((sub, j) => (
            <div key={j}>
              <span>{sub.name}</span>
              {/* Replace with your own toggle/switch component */}
              <button
                disabled={!sub.is_editable}
                onClick={() => handleCategoryChange(sub.category, sub.preference !== PreferenceOptions.OPT_IN)}
                style={{ opacity: !sub.is_editable ? 0.5 : 1, background: sub.preference === PreferenceOptions.OPT_IN ? '#2563EB' : '#D1D5DB', borderRadius: '9999px', padding: '2px 8px', border: 'none', cursor: !sub.is_editable ? 'not-allowed' : 'pointer' }}
              >
                {sub.preference === PreferenceOptions.OPT_IN ? 'On' : 'Off'}
              </button>
              {sub?.channels?.map((channel, k) => (
                <button
                  key={k}
                  disabled={!channel.is_editable}
                  onClick={() => handleChannelInCategoryChange(channel, sub)}
                >
                  {channel.channel}
                </button>
              ))}
            </div>
          ))}
        </div>
      ))}
    </>
  );
}
```

<Tip>
  **When to use:** Each project or sub-account needs completely independent preferences — its own defaults, its own channel settings, everything separate. Examples: an ad platform where each ad account has independent budget alert settings; a cloud hosting provider where production, staging, and dev each have separate alert preferences.
</Tip>
