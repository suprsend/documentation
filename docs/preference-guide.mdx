Notification preferences give users control over what they hear from your app, on which channel, and how often. Get them right and users stay engaged. Skip them and they'll unsubscribe from everything.

This guide covers eight common preference patterns, from a simple on/off toggle to multi-tenant team-filtered setups. Each section covers what it is, how to set it up in SuprSend, the code for your app, and when to use it.

> **New to preferences in SuprSend?** Read the [User Preferences overview](/docs/user-preferences) first — it covers how categories, channels, and the preference API response are structured. For multi-tenant setups, see [Tenant Preferences](/docs/tenant-preference).

## 1. Channel-level preferences

Users choose **All or Only important** per channel (Email, Push, SMS) and separately pick **which channel gets each type of notification**.

<Frame caption="Channel-level preferences">
  <img src="/images/Enhance%20Screen%20Design.png" alt="Channel-level preferences" width="560" />
</Frame>

**Configure in SuprSend**

1. Go to **Developers → [Notification categories](/docs/managing-notification-categories)**
2. Create sections and sub-categories; turn on the channels you need per category
3. Define the global options to offer (e.g. **All**, **Only important**)
4. Click **Publish Changes**

**Build in your app**

Call `getPreferences()` on page load. The response gives you two things: `channel_preferences` for the global per-channel controls, and `sections[].subcategories[].channels` for the per-topic channel picker. Only show channels you have labels for — filter out anything not in `channelLabels`.

```javascript
const { data, updateOverallChannelPreference, updateChannelPreferenceInCategory } = usePreferences();

// Block 1 — Global: All vs Only important per channel
data?.channel_preferences?.map((ch) => (
  <button onClick={() => updateOverallChannelPreference(ch.channel, 'all')}>All</button>
  <button onClick={() => updateOverallChannelPreference(ch.channel, 'required')}>Only important</button>
));

// Block 2 — Per-category: which channel for each notification type
data?.sections?.flatMap((s) => s.subcategories || []).map((sub) =>
  sub.channels?.map((ch) => (
    <button onClick={() => updateChannelPreferenceInCategory(ch.channel, ch.preference === 'opt_in' ? 'opt_out' : 'opt_in', sub.category)}>
      {ch.channel}
    </button>
  ))
);
```

**When to use:** Apps with multiple active channels where users want coarse control over volume. "Email me everything, push only the important stuff."

**Related docs:** [User Preferences](/docs/user-preferences) | [Manage Categories](/docs/managing-notification-categories) | [JS SDK preferences](/docs/js-preferences)

## 2. Category-level preferences

Users **turn each notification type on or off** (e.g. Product updates, Billing) and optionally choose which channel receives each type.

<Frame caption="Category-level preferences">
  <img src="/images/Section.png" alt="Category-level preferences" width="560" />
</Frame>

**Configure in SuprSend**

1. Go to **Developers → [Notification categories](/docs/managing-notification-categories)**
2. Create sections (e.g. Product, Billing, Sales) and sub-categories under each
3. Add channels to each sub-category
4. Click **Publish**

**Build in your app**

Call `getPreferences()`. Render sections as headings and sub-categories as rows with a toggle and channel pills.

One thing to handle: each sub-category has an `is_editable` field. If it is `false`, disable the toggle. That category is mandatory and users cannot opt out of it.

```javascript
const { data, updateCategoryPreference, updateChannelPreferenceInCategory } = usePreferences();

data?.sections?.map((section) => (
  <div key={section.name}>
    <h3>{section.name}</h3>
    {section.subcategories?.map((sub) => (
      <div key={sub.category}>
        <span>{sub.name}</span>
        <button onClick={() => updateCategoryPreference(sub.category, sub.preference === 'opt_in' ? 'opt_out' : 'opt_in')}>
          On/Off
        </button>
        {sub.channels?.map((ch) => (
          <button key={ch.channel} onClick={() => updateChannelPreferenceInCategory(ch.channel, ch.preference === 'opt_in' ? 'opt_out' : 'opt_in', sub.category)}>
            {ch.channel}
          </button>
        ))}
      </div>
    ))}
  </div>
));
```

**When to use:** Most apps. This is the standard notification settings page. "Product updates: On, Billing: Off." "Send this type by Email and Push only."

**Related docs:** [User Preferences](/docs/user-preferences) | [Manage Categories](/docs/managing-notification-categories) | [Update category preference](/reference/update-user-category-preference)

## 3. Digest

Instead of individual notifications, users choose a **summary frequency** (daily, weekly, or off) and a delivery time. Your workflow sends one digest instead of many separate pings.

This works through two user profile fields: `digest_frequency` and `digest_time`. The Digest node in your workflow reads these at runtime to determine when to send.

<Frame caption="Digest preferences">
  <img src="/images/digest.png" alt="Digest preferences" width="560" />
</Frame>

**Configure in SuprSend**

1. In your workflow, add a **Digest node**
2. Set the schedule to **Dynamic** and map it to `digest_frequency` and `digest_time` on the user profile. See [Dynamic schedule](/docs/digest#dynamic-schedule-send-digest-based-on-user-preference)

**Build in your app**

Add radio buttons for frequency (Daily / Weekly / No digest) and a time picker. On save, write to the user profile using `client.user.set`. This is not a preferences API call; it is a profile update.

```javascript
const client = useSuprSendClient();
const [frequency, setFrequency] = useState('daily');
const [time, setTime] = useState('09:00');

const save = async () => {
  await client.user.set({
    digest_frequency: frequency,  // 'daily' | 'weekly' | 'off'
    digest_time: time,            // e.g. '09:00'
  });
};
```

**When to use:** Activity feeds, team updates, analytics reports. Any case where one batched summary is better than a stream of individual pings.

**Related docs:** [Digest](/docs/digest) | [Dynamic schedule](/docs/digest#dynamic-schedule-send-digest-based-on-user-preference) | [Users API](/docs/users)

## 4. Tenant restriction

In multi-tenant apps, each customer org sees **only the notification categories you allow for them**. You control this per tenant from the dashboard. Users in that org see only what you have left enabled.

<Frame caption="Tenant-restricted categories">
  <img src="/images/Enhance%20Screen%20Design-2.png" alt="Tenant-restricted categories" width="560" />
</Frame>

**Configure in SuprSend**

1. Go to **Tenants → [your tenant] → [Tenant Preference](/docs/tenant-preference)**
2. Disable any categories or channels this tenant's users should not see
3. Repeat per tenant. Only categories you leave enabled will appear for that tenant's users

**Build in your app**

Pass `tenantId` when loading preferences. SuprSend filters the response to only return what is enabled for that tenant. Rendering and update calls work exactly the same as [Category-level preferences](#2-category-level-preferences).

```javascript
const TENANT_ID = 'default';
const { data, updateCategoryPreference } = usePreferences({ tenantId: TENANT_ID });

data?.sections?.flatMap((s) => s.subcategories || []).map((cat) => (
  <div key={cat.category}>
    <span>{cat.name}</span>
    <button onClick={() => updateCategoryPreference(cat.category, cat.preference === 'opt_in' ? 'opt_out' : 'opt_in')}>
      On/Off
    </button>
  </div>
));
```

**When to use:** White-label SaaS where Brand A sees Billing + Product and Brand B sees Billing + Sales. Any multi-tenant product where different orgs have different feature sets or compliance requirements.

**Related docs:** [Tenant Preference](/docs/tenant-preference) | [User Preferences](/docs/user-preferences) | [Preference Evaluation](/docs/preference-evaluation)

## 5. Department

Users pick their **team or department** (e.g. Engineering, Sales) and see only notification categories tagged for that team. Instead of one long list of everything, they see what is actually relevant to them.

<Frame caption="Filter by department">
  <img src="/images/Enhance%20Screen%20Design-3.png" alt="Filter by department" width="560" />
</Frame>

**Configure in SuprSend**

1. In **Developers → [Notification categories](/docs/managing-notification-categories)**, add tags to sections or sub-categories (e.g. `engineering`, `sales`)
2. Click **Publish**

**Build in your app**

Add a team selector (pills, tabs, or dropdown). When a user picks a team, reload preferences with that tag. Rendering and updates work the same as [Category-level preferences](#2-category-level-preferences).

```javascript
const [tag, setTag] = useState('engineering');
const { data, updateCategoryPreference } = usePreferences({ tags: tag });

// Team selector pills, then category list
data?.sections?.flatMap((s) => s.subcategories || []).map((cat) => (
  <div key={cat.category}>
    <span>{cat.name}</span>
    <button onClick={() => updateCategoryPreference(cat.category, cat.preference === 'opt_in' ? 'opt_out' : 'opt_in')}>
      On/Off
    </button>
  </div>
));
```

**When to use:** Internal tools, HR platforms, developer portals. "I'm in Engineering" shows only dev and product categories. "I'm in Sales" shows only sales and billing. One page, filtered by role.

**Related docs:** [User Preferences](/docs/user-preferences) | [Manage Categories](/docs/managing-notification-categories) | [Lists](/docs/lists)

## 6. Department + Tenant

The same as [Department](#5-department), but scoped to the current tenant. Users see only categories that are both allowed for their org and tagged for their team. SuprSend returns the intersection of both filters automatically.

Tenant admins can set org-level defaults per category from the dashboard or via `PATCH /v1/tenant/{tenant_id}/preference/category/{category_slug}/`.

<Frame caption="Filter by department, scoped to tenant">
  <img src="/images/Enhance%20Screen%20Design-4.png" alt="Filter by department, scoped to tenant" width="560" />
</Frame>

**Configure in SuprSend**

1. Add tags to categories as in [Department](#5-department)
2. In **Tenants → [tenant] → [Tenant Preference](/docs/tenant-preference)**, disable categories this tenant's users should not see
3. Publish both

**Build in your app**

Pass both `tenantId` and `tags`. That is the only difference from Department.

```javascript
const TENANT_ID = 'default';
const [tag, setTag] = useState('sales');
const { data, updateCategoryPreference } = usePreferences({ tenantId: TENANT_ID, tags: tag });
```

**When to use:** Multi-tenant B2B apps where both the org and the user's role shape which notifications are relevant. Workforce tools, employee comms platforms, ops software with team structures.

**Related docs:** [Tenant Preference](/docs/tenant-preference) | [User Preferences](/docs/user-preferences) | [Lists](/docs/lists)

## 7. Categories by module

Users pick a **project** (e.g. Project Alpha, Project Beta) and see only notification categories tagged for that project. This uses the same tag pattern as Department, with a project selector instead of a team selector.

<Frame caption="Filter by project or module">
  <img src="/images/Enhance%20Screen%20Design-5.png" alt="Filter by project or module" width="560" />
</Frame>

**Configure in SuprSend**

In **Developers → [Notification categories](/docs/managing-notification-categories)**, tag your sections or sub-categories per project. Two ways to structure this:

- **Option A:** One section per project (e.g. "Project Alpha" tagged `project-alpha`) with sub-categories under it. Filtering by tag returns the whole section.
- **Option B:** One shared section (e.g. "Projects") with each sub-category tagged individually. Filtering by tag returns that section with only the matching sub-categories.

Click **Publish** after either approach.

**Build in your app**

Add a project selector. When a user picks a project, reload preferences with that project's tag. Render sections and sub-categories with toggles and update via `updateCategoryPreference`.

```javascript
const [selectedTag, setSelectedTag] = useState('project-alpha');
const { data, updateCategoryPreference } = usePreferences({ tags: selectedTag });

// Project selector: Project Alpha | Project Beta
data?.sections?.map((section) => (
  <div key={section.name}>
    <h3>{section.name}</h3>
    {(section.subcategories || []).map((cat) => (
      <div key={cat.category}>
        <span>{cat.name}</span>
        <button onClick={() => updateCategoryPreference(cat.category, cat.preference === 'opt_in' ? 'opt_out' : 'opt_in')}>
          On/Off
        </button>
      </div>
    ))}
  </div>
));
```

**When to use:** Project management tools, client portals, engineering platforms where users belong to specific projects and each project has its own set of notification categories.

**Related docs:** [User Preferences](/docs/user-preferences) | [Manage Categories](/docs/managing-notification-categories) | [Lists](/docs/lists)

## 8. Threshold

Users pick **at what level they want to be alerted** (e.g. 80% or 90% of a usage limit). This is stored as a user profile property. Your workflow reads it and fires when the metric crosses that value. No preference APIs are involved; it is purely profile-driven.

<Frame caption="Threshold alerts">
  <img src="/images/Enhance%20Screen%20Design-6.png" alt="Threshold alerts" width="560" />
</Frame>

**Configure in SuprSend**

In your workflow, add a **condition node** that reads `threshold_percent` from the user's profile and compares it to the incoming metric (e.g. fire when `usage >= user.threshold_percent`). See [Workflows](/docs/workflows).

**Build in your app**

Show two option cards (e.g. 80% "Earlier warning" / 90% "Closer to limit") and a Save button. On save, write the value to the user profile using `client.user.set`.

```javascript
const client = useSuprSendClient();
const [threshold, setThreshold] = useState(80);

const save = async () => {
  await client.user.set({
    threshold_percent: threshold,  // 80 or 90
  });
};

// UI: card with title "Usage alert threshold"
// Two option cards: 80% "Earlier warning" | 90% "Closer to limit"
// Save button
```

**When to use:** Usage-based SaaS (storage, API credits, seats), budget monitoring, infrastructure dashboards. Any scenario where users have different risk tolerances and want to choose their own alert trigger point.

**Related docs:** [Workflows](/docs/workflows) | [Users API](/docs/users)
