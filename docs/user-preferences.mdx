Preferences allow users to opt out of notification categories, choose their preferred communication channels, and set the frequency of notifications. Providing granular preferences reduces the likelihood of users disabling all notifications from your platform.

In SuprSend, you can use [ready-made UI](/docs/user-preferences#controlling-what-categories-to-show-on-ui) and [APIs](/reference/overview) to manage multi-tenant preference use cases. This includes letting admins set preferences for internal teams and handle notifications for enterprise customers, where companies, customers, and end users have distinct preferences.

## How preferences work?

Each user has a preference set within SuprSend, and users receive notifications in the category and channel they haven't opted out of. If a user hasn’t configured preferences for a category, the system uses [default preferences](/docs/user-preferences#set-default-preferences).

Preference set contains three level of preferences: `channel_preferences` (for channel-level opt-outs), `categories`, and `opt_out_channels` within each category. In the below example, user has opted out of `email`, `invoice-ready` category and slack channel in `payment-reminder` category.

<CodeGroup>

```json User Preference set
{
  "channel_preferences": [
    {
      "channel": "email",
      "is_restricted": true
    }
  ],
  "categories": [
    {
      "category": "invoice-ready",
      "preference": "opt_out"
    },
    {
      "category": "payment-reminder",
      "preference": "opt_in",
      "opt_out_channels": [
        "slack"
      ]
    }
  ]
}
```

</CodeGroup>

## Set up preference categories in SuprSend

### Create notification category

To set up notification preferences, start by creating notification categories. Instead of creating a separate category for each trigger, group similar notifications to keep categories more user-friendly. You can also add sections to organize your categories more effectively.

> Don't add too many categories as it can drive users to use channel level opt-outs.

You can update notification categories from the [Developers → Preference categories](https://app.suprsend.com/en/staging/developers/preference-categories) page. Add categories under any of the three predefined root categories:

- **System**: For critical system notifications like OTPs, verification, and authentication. Users can't opt out of this category.
- **Transactional**: Notifications related to user transactions on your platform, such as payment confirmations, delivery statuses, and comments. The default preference for this category opts users in, but you can change it at the individual category level.
- **Promotional**: Marketing notifications like newsletters, announcements, deals, and discounts. The default preference for this category opts users out, but you can change it at the individual category level.

### Set default preferences

If the user hasn't set preferences in a category, the system sends notifications based on default preferences. Default preferences are set in the notification category. The tenant can override the default preferences for their users, either through the [tenant preference API](/reference/update-tenant-default-preference) or from the tenant details page.

You can set following default preferences at category level:

1. **On**: opt-in on all channels
2. **Off**: opt-out on all channels
3. **Can't Unsubscribe**: Use this to prevent users from completely opting out of critical notification categories, such as anomaly alerts or important transactions (e.g., completed trades, payments). Channel `opt-out` does not block notifications from mandatory channels in this category.

## Preference States

Understanding preference states is crucial for implementing effective notification management. SuprSend supports several preference states that control how notifications are delivered to users:

### Available Preference States

| State | Description | When to Use | User Control |
|-------|-------------|-------------|--------------|
| `opt_in` | User actively chooses to receive notifications in this category | Default for transactional notifications, user-initiated subscriptions | User can change to `opt_out` |
| `opt_out` | User has disabled notifications for this category | Default for promotional notifications, user unsubscribes | User can change to `opt_in` |
| `cant_unsubscribe` | System-enforced delivery, user cannot disable | Critical system notifications (OTPs, security alerts, password resets) | User cannot modify |

<CodeGroup>

```json Example: Mixed Preference States
{
  "categories": [
    {
      "category": "security-alerts",
      "preference": "cant_unsubscribe",
      "description": "Critical security notifications"
    },
    {
      "category": "order-updates", 
      "preference": "opt_in",
      "description": "Transaction confirmations and delivery updates"
    },
    {
      "category": "marketing-emails",
      "preference": "opt_out", 
      "description": "Promotional campaigns and newsletters"
    }
  ]
}
```

</CodeGroup>

### State Behavior in Practice

- **`opt_in`**: Notifications are delivered across all enabled channels unless specifically restricted
- **`opt_out`**: All notifications in this category are blocked regardless of channel
- **`cant_unsubscribe`**: Notifications are always delivered, ignoring user channel preferences for this category

## System vs Custom Categories

SuprSend provides a structured approach to organizing notification categories through system-defined and custom categories:

### System Categories (Predefined by SuprSend)

These are the three root categories that cannot be modified but can contain custom subcategories:

| Category | Purpose | Default State | User Control | Priority |
|----------|---------|---------------|--------------|----------|
| **System** | Critical system notifications (OTPs, verification, authentication) | `cant_unsubscribe` | None - always delivered | Highest |
| **Transactional** | User-initiated or transaction-related notifications | `opt_in` | Can opt-out of non-critical subcategories | High |
| **Promotional** | Marketing and promotional content | `opt_out` | Full control | Lowest |

### Custom Categories (Developer-Defined)

Custom categories are subcategories you create under the system categories:

<CodeGroup>

```json System Category Structure
{
  "system": {
    "subcategories": [
      "password-reset",
      "account-verification", 
      "security-alerts"
    ]
  },
  "transactional": {
    "subcategories": [
      "order-confirmations",
      "payment-receipts",
      "delivery-updates",
      "comment-notifications"
    ]
  },
  "promotional": {
    "subcategories": [
      "newsletters",
      "product-announcements", 
      "special-offers",
      "feature-updates"
    ]
  }
}
```

</CodeGroup>

### Key Differences

| Aspect | System Categories | Custom Categories |
|--------|-------------------|-------------------|
| **Creation** | Predefined by SuprSend | Created by developers |
| **Modification** | Names and behavior fixed | Fully customizable |
| **Hierarchy** | Root level only | Nested under system categories |
| **Default Behavior** | Inherits system defaults | Can override defaults |
| **UI Display** | Always visible | Can be hidden with visibility controls |

<Note>
**Why Some Examples Show Extra Toggles**: Documentation examples that display additional preference toggles often use system categories with multiple custom subcategories. Each subcategory appears as a separate toggle in the preference UI, giving users granular control over their notification experience.
</Note>

## Hiding Notifications from UI

You can suppress notifications from appearing in UI components (like toast notifications or in-app feeds) while still maintaining them in logs for analytics and debugging purposes.

<Note>
**React SDK Note**: In the latest `@suprsend/react` SDK, toast notification functionality is no longer included in the `Inbox` component by default. Use the headless approach with `useFeedClient` hook and event listeners for custom toast control, or implement conditional rendering for feed visibility.

**Web Components Note**: The `hideToast` and `hideFeed` properties are configuration options that can be passed in the initial config object to `initSuprSend()`, or updated dynamically after initialization using `updateInboxConfig()` and `updateFeedConfig()` methods.
</Note>

### Suppressing Toast Notifications

<CodeGroup>

```javascript React - Headless Toast Control
import { SuprSendProvider, SuprSendFeedProvider, useFeedClient } from '@suprsend/react';
import { useEffect } from 'react';

function App() {
  return (
    <SuprSendProvider>
      <SuprSendFeedProvider>
        <NotificationHandler />
      </SuprSendFeedProvider>
    </SuprSendProvider>
  );
}

function NotificationHandler() {
  const feedClient = useFeedClient();
  
  useEffect(() => {
    if (!feedClient) return;
    
    feedClient.emitter.on('feed.new_notification', (notification) => {
      // Custom logic to decide whether to show toast
      const shouldShowToast = notification.category !== 'low-priority';
      
      if (shouldShowToast) {
        // Show your custom toast
        showCustomToast(notification);
      }
      
      // Notification is always logged regardless of toast display
      console.log('Notification logged:', notification.id);
    });
  }, [feedClient]);
  
  return null; // This component only handles notifications
}
```

```javascript Web Components - Hide Toast
// Initialize with inbox config to hide toast
const suprsendConfig = {
  distinctId: "YOUR_DISTINCT_ID",
  publicApiKey: "YOUR_PUBLIC_API_KEY",
  inbox: {
    hideToast: true  // No toast notifications shown
  }
};

// Initialize components
initSuprSend(suprsendConfig);

// All notifications still tracked in logs
```

```javascript React - Complete Toast Suppression
import { SuprSendProvider, SuprSendFeedProvider, useFeedClient } from '@suprsend/react';

function App() {
  return (
    <SuprSendProvider>
      <SuprSendFeedProvider>
        <NotificationFeed />
        <ToastController suppressAll={true} />
      </SuprSendFeedProvider>
    </SuprSendProvider>
  );
}

function ToastController({ suppressAll }) {
  const feedClient = useFeedClient();
  
  useEffect(() => {
    if (!feedClient || !suppressAll) return;
    
    // Completely suppress toast notifications
    feedClient.emitter.on('feed.new_notification', (notification) => {
      // Do nothing - toast is suppressed
      // Notification still logged in SuprSend
      console.log('Toast suppressed for:', notification.id);
    });
  }, [feedClient, suppressAll]);
  
  return null;
}
```

</CodeGroup>

### Hiding In-App Feed

<CodeGroup>

```javascript Web Components - Hide Feed, Show Only Toast
// Initialize with feed config to hide feed but show toast
const suprsendConfig = {
  distinctId: "YOUR_DISTINCT_ID",
  publicApiKey: "YOUR_PUBLIC_API_KEY",
  feed: {
    hideFeed: true,     // Hide the notification feed UI
    hideToast: false    // Still show toast notifications
  }
};

// Initialize components
initSuprSend(suprsendConfig);

// Useful for showing immediate notifications without persistent feed
```

```javascript React - Conditional Feed Rendering
import { SuprSendProvider, SuprSendFeedProvider, NotificationFeed, useFeedClient } from '@suprsend/react';
import { useState } from 'react';

function App() {
  const [showFeed, setShowFeed] = useState(false);
  
  return (
    <SuprSendProvider>
      <SuprSendFeedProvider>
        {/* Conditionally render feed based on state */}
        {showFeed && <NotificationFeed />}
        
        {/* Toast notifications still work */}
        <ToastController />
        
        {/* Toggle button for feed visibility */}
        <button onClick={() => setShowFeed(!showFeed)}>
          {showFeed ? 'Hide Feed' : 'Show Feed'}
        </button>
      </SuprSendFeedProvider>
    </SuprSendProvider>
  );
}

function ToastController() {
  const feedClient = useFeedClient();
  
  useEffect(() => {
    if (!feedClient) return;
    
    feedClient.emitter.on('feed.new_notification', (notification) => {
      // Always show toast notifications
      showCustomToast(notification);
    });
  }, [feedClient]);
  
  return null;
}
```

</CodeGroup>

### How It Works

When you suppress UI notifications:

1. **Logging Continues**: All notifications are still recorded in SuprSend logs
2. **Analytics Preserved**: Delivery metrics and user interaction data remain intact  
3. **API Access**: Notifications remain accessible via API calls
4. **Debugging Available**: Full notification history available in workflow execution logs

**Use Case**: Suppress promotional toast notifications during user focus sessions while maintaining audit trails for compliance.

## Real-World Example: E-commerce Notification Strategy

Consider an e-commerce platform implementing a comprehensive notification preference system:

### Scenario Setup

```json Category Configuration
{
  "system": {
    "password-reset": { "preference": "cant_unsubscribe" },
    "account-verification": { "preference": "cant_unsubscribe" },
    "security-alerts": { "preference": "cant_unsubscribe" }
  },
  "transactional": {
    "order-confirmations": { "preference": "opt_in" },
    "payment-receipts": { "preference": "opt_in" }, 
    "delivery-updates": { "preference": "opt_in" },
    "review-requests": { "preference": "opt_in" }
  },
  "promotional": {
    "daily-deals": { "preference": "opt_out" },
    "newsletters": { "preference": "opt_out" },
    "product-recommendations": { "preference": "opt_out" }
  }
}
```

### User Behavior Examples

**Scenario 1: User Disables Marketing Emails**
```json User Preference Update
{
  "categories": [
    {
      "category": "daily-deals",
      "preference": "opt_out"
    },
    {
      "category": "newsletters", 
      "preference": "opt_out"
    }
  ]
}
```

**Result**: 
- ❌ Daily deals and newsletters are blocked
- ✅ Order confirmations and delivery updates continue normally
- ✅ Password reset emails always delivered (system category)

**Scenario 2: User Disables All Email**
```json Channel-Level Opt-out
{
  "channel_preferences": [
    {
      "channel": "email",
      "is_restricted": true
    }
  ]
}
```

**Result**:
- ❌ All promotional and transactional emails blocked
- ✅ Critical system notifications (OTPs, password resets) still delivered via email
- ✅ Notifications continue via other channels (SMS, push, in-app)

### Business Impact

This approach ensures:
- **User Trust**: Critical communications always reach users
- **Compliance**: Transactional notifications maintain legal delivery requirements  
- **Engagement**: Users retain control without losing essential updates
- **Revenue Protection**: Payment confirmations and order updates preserve customer experience

<Tip>
**Best Practice**: Always categorize password resets, account security alerts, and payment confirmations under system or mandatory transactional categories to ensure delivery regardless of user preferences.
</Tip>

## Capture user preferences

You can capture user preference choice using an out-of-the-box hosted subscription page or by embedding a preference center within your product.

### Hosted Preference Page

Once you publish preference categories, SuprSend automatically generates a dedicated webpage for collecting out-of-the-box user preferences. Users can set channel-specific preferences from the hosted page. e.g., if you add it to your email, the page displays only the relevant preference categories for email, and the user’s selections save for email. Include it in your templates using `{{$hosted_preference_url}}`.

### Controlling what categories to show on UI

It is always a good practice to show only the categories that are relevant to the user. There are 2 ways to achieve this:
1. **Turning off category visibility for all users of a tenant**: In a multi-tenant setup, if tenants or admins decide what categories their users should see, you can control this via the `visible_to_subscriber: false` flag in default [tenant preferences](/reference/update-tenant-default-preference).

2. **Setting custom preference UI for each user**: Use tags to show categories based on user roles, departments, or teams. These tags can then be used to filter categories in preference center.

<Steps>
<Step title="Setting Preference tags">
Tags can be added to categories and sections directly from the SuprSend Console → Preference Page. When a tag is assigned at the section level, it automatically applies to all categories under that section—so filtering by a section tag also filters its child categories.
![Tags Within Preference Categories](/images/preference-tag-changelog.png)

</Step>

<Step title="Filter Categories with Tags">
You can filter categories using the tags query parameter in the API. This can be a simple tag match (e.g. `tags=tag1`) or a more advanced filter using logical operators.

Supported operators:

| Operator | Operand Datatype | Description | Example |
----- | ------ | ------- | ------- |
|`exists` | boolean | Returns categories where any tag is set | `tags={"exists":true}` |
|`not` | string | Excludes categories that have the specified tag | `tags={"not":"admin"}` |
|`or` | array | return categories that have any of the mentioned tags | `tags={"or":["sales","marketing"]}` |
|`and` | array | return categories that have all the mentioned tags| `tags={"and":["sales","manager"]}` |

You can combine these operators for nested filtering like `tags={"or":[{"and":["sales","manager"]},{"and":["marketing","associate"]}]}`.

</Step>
</Steps>

## Preference evaluation at runtime

When a workflow triggers, SuprSend evaluates preferences for each recipient before each delivery node.

<Steps>
  <Step title="Evaluating Recipient preferences">

If recipient preferences aren't set, the system picks the default preference setting. Once the user sets a preference in a category, changes to the default preference of existing categories won't affect recipient preferences.

  </Step>
  <Step title="Factoring in tenant preferences">

If you are triggering notification for a tenant, [tenant default preference](/docs/tenant-preference) setting takes precedence over default preference set at category level.

  </Step>
  <Step title="Resolving preference conflicts">

The order of precedence is always `user > tenant > org` (set in notification category settings). However, if you turn off notifications in a category from the [tenant page](https://app.suprsend.com/en/demo/tenants), users will not receive notifications in that category.

  </Step>

  <Step title="Debugging preference evaluation in workflow runs">

User preferences can change over time, and when checking a workflow run, you need to know what user preferences were at that time. You can view this using the step-by-step debugger in [workflow executions](https://app.suprsend.com/en/demo/logs/executions/?last_n_minutes=1440).

![](/images/docs/e0555b827b95d61b16ba0f58fa1faa05b5109709828157df9d774fb123954516-image.png)

You can also track when user updated their preference by filtering on `Subscriber preference update` in [request logs](https://app.suprsend.com/en/demo/logs/api/?last_n_minutes=1440).

  </Step>
</Steps>

## Frequently Asked Questions

<AccordionGroup>
  <Accordion title="How to setup digest schedule in my preferences?">
    You can create sub-categories for different digest schedules or set the digest schedule in the user profile and pass a dynamic schedule in the workflow digest node. An option to set the digest schedule directly on your preference page will be available soon.
  </Accordion>
  <Accordion title="I have a use case where a company has multiple departments/roles, and the admin will set preferences for users in these departments.">
    You can manage this with tenant preferences. In the SuprSend system, each tenant represents an organization, and the administrator sets which categories to send to their internal team using the [tenant preference API](/reference/update-tenant-default-preference).
  </Accordion>
  <Accordion title="What happens to existing user preference view if I change default preference setting? ">
    Changing the default preference for a category doesn't affect users who have already made changes to that category. For categories where users haven't made any changes, the preferences update according to the new default settings.
  </Accordion>
  <Accordion title="I have multiple enterprise customers with various product offerings. Customers should only receive notifications for the products they have enabled, and the same should be visible on their preference page. How can I manage this in SuprSend?">
    You can turn off categories for tenants from the tenant page on the SuprSend console. Turning off the preference for a category automatically removes it from the tenant preference APIs and UI view. To further apply this to the tenant's users, set `visible to subscriber` to `false` in the default tenant preferences to hide the category from the tenant's end users.
  </Accordion>
</AccordionGroup>
