Smart Channel Routing is SuprSend's approach to multi-channel notification delivery that eliminates notification fatigue. Instead of blasting all channels simultaneously, notifications are delivered **sequentially across outside-app channels** — with a configurable delay between each attempt — and stop the moment the user engages.

This reduces unnecessary noise on paid channels (like SMS and WhatsApp), lowers delivery costs, and improves overall notification engagement rates including delivery, open, and interaction rates.

> **Key behavior:** The **Inbox channel is always attempted first**, immediately and outside the routing queue, before any outside-app channel is triggered. Users who are active in your app are reached instantly — without consuming paid channels unnecessarily. If the user engages via Inbox, all outside-app deliveries are skipped.

Notification content for each channel is configured using [templates](/docs/templates). SuprSend lets you design content for all channels — email, SMS, WhatsApp, push, Inbox, and more — within a single template group.

## How Smart Channel Routing Works

<Steps>
  <Step title="Inbox is always attempted first">
    If **Inbox** is active on both the template and the user profile, SuprSend delivers the notification to Inbox **immediately** — before any outside-app channel is evaluated. This step is independent of the routing queue and does not consume any time-to-live budget.

    Inbox is prioritized because it is a zero-cost in-app channel. If the user's [success metric](/docs/smart-delivery#success-metric) is achieved via Inbox (e.g., they open or interact with the notification), all outside-app channel deliveries are skipped, saving cost and reducing notification noise.
  </Step>
  <Step title="Identify applicable outside-app channels">
    After the Inbox attempt, SuprSend evaluates which outside-app channels (email, SMS, WhatsApp, push, Slack, MS Teams, etc.) are eligible. Eligible channels are the intersection of:

    - **Active channels on the template** — Published and live channels. For WhatsApp and SMS with Indian vendors, templates must be approved by the provider before they go live.
    - **Active channels in the user profile** — Channels available in the user profile that are not marked inactive. A channel is deactivated if it is `removed` or `unset` via [SDK or API](/docs/users#via-sdk), or is marked inactive by SuprSend.
    - **Channels where the user is opted in** — If you use SuprSend's preference centre, only channels with `opt-in` status for the given channel and notification category are included. Verify user opt-in status with the [get user preference API](/reference/get-user-category-preferences).
  </Step>
  <Step title="Order outside-app channels using routing rules">
    The sequence of outside-app channel delivery is determined by the configured [routing rule](/docs/smart-delivery#routing-rules). By default, channels are ordered to [optimize on cost](/docs/smart-delivery#optimize-on) — attempted from lowest to highest cost, based on vendor configuration.

    > Optimization on engagement metrics (open rate, click-through rate) is coming soon, enabling smarter routing based on which channel a user is most likely to respond to.
  </Step>
  <Step title="Deliver sequentially using time-to-live intervals">
    Notifications are sent to each outside-app channel in order, separated by a time interval calculated as:
```
    delay = time_to_live ÷ (number_of_outside-app_channels − 1)
```

    **Example:** 3 active outside-app channels + 1 hour time-to-live → notifications sent 30 minutes apart across each channel.

    Delivery halts as soon as the configured [success metric](/docs/smart-delivery#success-metric) is met. Channels remaining in the queue are skipped.
  </Step>
</Steps>

## Setting Routing Rules

Routing rules control how notifications are sequenced and delivered across outside-app channels.

### Optimize On

Defines the channel ordering strategy. When set to **cost**, SuprSend arranges outside-app channels in ascending order of cost — ensuring free or low-cost channels (like web push) are always tried before paid ones (like SMS or WhatsApp).

> Coming soon: manual channel ordering and optimization on engagement signals like open rate, click rate, and response time.

### Time to Live

Time to live (TTL) defines the **total delivery window** for outside-app channel routing. The inter-channel delay is:
```
inter-channel delay = TTL ÷ (number_of_outside-app_channels − 1)
```

**Example:** 3 outside-app channels with a 1-hour TTL → each channel is attempted 20 minutes apart.

> **Note:** TTL applies only to outside-app channels. Inbox is always delivered immediately and does not consume any portion of the TTL window.

### Must Send To

Channels listed under **Must Send To** are delivered **immediately and unconditionally**, bypassing the sequential routing order. Use this for channels that must always receive the notification regardless of whether success has already been achieved on another channel.

### Success Metric

The success metric is the trigger that halts further channel delivery. Once a user satisfies the success metric, all remaining queued channels are skipped. Two types are supported:

1. **Notification Status** — A status event on any delivered channel: `Delivered`, `Seen`, or `Interacted / Clicked`. For example, if your goal is for the user to open the notification, set the success metric to `Notification Status — Seen`.

2. **Custom Event** — Any platform event that indicates the desired user action. For example, on a payment reminder workflow, set the success metric to `Invoice Paid` to stop routing once payment is confirmed.

## Override Channels

Override Channels lets you **dynamically pass the channel list at runtime** using event properties — useful when a user's preferred delivery channel varies per event. For example, when booking an appointment, a user might select their preferred notification channel (SMS, email, WhatsApp) for that specific booking.

For persistent, user-level preferences — such as a user always preferring email, or setting a default channel per notification category — use [user preferences](/docs/user-preferences) instead.

**To configure channel override:**

1. Include a `channels` array in the event properties payload.
2. Map the corresponding event property key to the **Override Channels** field on the SuprSend workflow form.

<Frame caption="Override channels configuration in SuprSend workflow">
  <img src="/images/docs/eb7ac2c-image.png" />
</Frame>

**Accepted channel values:**
```json
["email", "sms", "whatsapp", "androidpush", "iospush", "webpush", "slack", "inbox", "ms_teams"]
```

Channel values can be mapped using a [JQ expression](https://jqlang.github.io/jq/manual/) to handle non-standard formats:

| Event property structure | JQ expression |
|---|---|
| `{ "channels": [...] }` (top-level) | `.channels` |
| `{ "user": { "channels": [...] } }` (nested) | `.user.channels` |
```json
{
  "user": {
    "name": "Steve",
    "channels": ["email", "inbox"]
  }
}
```

<Warning>
  If the specified channel key is missing or resolves to an invalid value, workflow execution stops immediately and the error is logged.
</Warning>

## Frequently Asked Questions

<AccordionGroup>
  <Accordion title="Why is Inbox always attempted first in Smart Channel Routing?">
    Inbox is a zero-cost, in-app channel. Attempting it first means users who are actively using your app receive the notification immediately — before any paid channels like SMS or WhatsApp are triggered. If the user engages via Inbox, the entire outside-app routing queue is skipped, reducing cost and notification noise without sacrificing delivery effectiveness.
  </Accordion>
  <Accordion title="Does Inbox delivery count against the time-to-live window?">
    No. Inbox is delivered immediately and independently of the outside-app routing queue. The time-to-live budget applies exclusively to outside-app channels (email, SMS, WhatsApp, push, etc.).
  </Accordion>
  <Accordion title="How does channel routing work when a user has multiple identities on the same channel (e.g., multiple email addresses)?">
    Routing operates at the channel identity level. If a user has multiple email addresses, the notification is sent to each address sequentially with the configured inter-channel delay between each attempt.
  </Accordion>
  <Accordion title="How does Smart Channel Routing interact with vendor routing?">
    Vendor routing is independent of Smart Channel Routing. Vendor-level failover does not contribute to or affect the inter-channel delay in Smart Channel Routing.
  </Accordion>
  <Accordion title="Can I use Smart Channel Routing to optimize for engagement rather than cost?">
    Cost-based optimization is available today. Engagement-based optimization — where SuprSend automatically routes to the channel a user is most likely to respond on — is on the roadmap and will be introduced in a future release.
  </Accordion>
</AccordionGroup>
