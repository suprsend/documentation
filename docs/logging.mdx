## Overview

SuprSend provides end-to-end logging across requests, executions, broadcasts, and messages. Navigate to the [Logs tab](https://app.suprsend.com/en/production/logs/) to access your logs. **No sampling—all events are recorded.**

Every notification produces logs at different stages. Start with the one that matches your problem.

**Start here:**

- **Delivery issue?** → [Message Logs](#message-logs)
- **Workflow didn't trigger?** → [Workflow Execution Logs](#workflow-execution-logs)
- **Broadcast issue?** → [Broadcast Execution Logs](#broadcast-execution-logs)
- **Need full trace?** → Use [Idempotency Key](#tracing-notifications) search

## Understanding Log Types

The four log types follow the notification lifecycle: **Request** → **Workflow Execution** → **Broadcast Execution** (if applicable) → **Message**. Each log type captures events at a specific stage.

<Columns>
  <Column>
    **Request Logs**
    
    API and SDK requests before workflow processing. Check when API calls fail or you need to verify payloads.
  </Column>
  <Column>
    **Workflow Execution Logs**
    
    Individual workflow processing per user. Check when workflows don't trigger, notifications aren't sent (but API succeeded), or you need processing steps and template/channel errors.
  </Column>
  <Column>
    **Broadcast Execution Logs**
    
    Broadcast campaigns across user lists. Check when broadcasts don't reach all users, you need aggregate statistics, or want to understand user skipping.
  </Column>
  <Column>
    **Message Logs**
    
    Individual message delivery and engagement. Check when notifications aren't delivered, you need delivery status, or want to track user engagement.
  </Column>
</Columns>

**Tracing notifications:**

Use the **idempotency key** to trace a notification across all log types. Click the **"i" icon** on any log entry to view it, then use the idempotency key filter to search across all log types.

<Note>
  Not every request produces all log types. Depending on conditions and preferences, a request may not produce executions or messages.
</Note>

<Warning>
  **Important:** "Completed" execution does not mean "Delivered". A workflow can complete successfully but still have message delivery failures. Check Message Logs for actual delivery status.
</Warning>

## Using Logs

### Filters & Controls

Filters, date range, refresh, and auto-refresh are available on **all log tabs**. Some filters are tab-specific (e.g., Status filter appears in execution logs but not request logs).

**Fastest ways to find something:**

- **Have an idempotency key?** → Paste it in the filter (works across all log types)
- **Have a recipient?** → Filter by user/object ID or email address
- **Have an execution ID?** → Use it to find specific workflow or broadcast execution
- **Know the workflow name?** → Search by name filter

<Frame caption="Filters panel for narrowing logs">
  <img src="/images/filters.png" alt="Filters panel" width="700" />
</Frame>

#### Available Filters

Filters help you narrow down logs quickly. Use them individually or combine multiple filters.

| Filter | Description | Use Case |
|--------|-------------|----------|
| **Status** | Filter by execution status (Completed, Partial Failure, Failed) | Quickly find failed executions |
| **Error Severity** | Filter by error level (Errors or Warnings) | Focus on critical errors vs. warnings |
| **API Type** | Filter by API endpoint type (e.g., `/trigger/`, `/event/`) | Isolate logs from specific API endpoints |
| **Name** | Search workflow, broadcast, or event name in real-time | Find all logs for a specific workflow or broadcast |
| **Idempotency Key** | Search across all log types using the unique key | Trace a single notification request across all log types |
| **Recipient** | Search by user/object ID or email address | View all logs for a specific user or recipient |
| **Object** | Filter by object ID or type | See all notification activity related to a specific object and its subscribers |
| **Tenant ID** | Filter by tenant identifier | Isolate logs for a specific tenant or brand |

#### Date Range & Retention

**Date Selection:**

Logs default to "Last 1 day" when first opened. Choose from relative ranges (Last 1 day, 7 days, 30 days, and additional presets) or select absolute date ranges with timezone-aware selection.

**Log Retention:**

Retention periods depend on your plan. Extended retention options are available—contact support for details.

<Note>
  Retention periods may vary by plan tier. After retention expires, logs and their identifiers are no longer accessible.
</Note>

#### Auto-Refresh

Auto-refresh controls how logs update in the interface.

| Mode | Behavior | When to Use |
|------|----------|-------------|
| **ON (Automatic)** | Logs refresh automatically at regular intervals | Monitoring active workflows or debugging real-time issues |
| **OFF (Manual)** | Logs refresh only when you click the refresh button | Investigating a specific issue to prevent new logs from changing your view |

<Tip>
  Switch to manual refresh when investigating a specific issue to prevent new logs from changing your view. Switch to auto-refresh when monitoring ongoing processes.
</Tip>

## Log Types

### Request Logs

Request logs capture all API and SDK requests before workflow processing begins. This is the entry point for all notifications.

**When to check:** API calls fail or return unexpected responses, need to verify request payloads, or want to see exact API responses and input data.

<Frame caption="Interactive graph showing request volume with hover details">
  ![](/images/graph-hover.png)
</Frame>

The request logs page displays an interactive graph showing request volume over time. Hover over any point to see date/time range, total requests, and success/failed/partial failure percentages. Click or drag to zoom into specific time periods.

<Frame caption="Request log entry details">
  ![](/images/requestlogs-detailed.png)
</Frame>

Each request log entry includes three main sections:

| Section | Details |
|---------|---------|
| **Response** | Success response with status, or failure response with error code, description, type, severity, and context |
| **Input** | HTTP method, endpoint (e.g., `/event/`, `/trigger/`), and complete JSON payload |
| **Summary** | Recipient (clickable link to user page), idempotency key (with copy button), received at timestamp, workflow name (if applicable), and tenant ID |

**Common errors captured:**

| Error Type | Examples |
|------------|----------|
| **API-level errors** | Invalid requests, missing required fields, workflow not found, authentication failures |
| **Schema validation errors** | Event properties that don't match the workflow schema |
| **Early-stage failures** | Errors detected before workflow processing begins |

**Navigate from here:** Use idempotency key to find related workflow execution logs, click recipient to view all logs for that user, or click workflow name to view all execution logs for that workflow.

<Note>
  If your API request returns 200 but you don't see a workflow execution, common causes include trigger conditions not matching, workflow disabled, or downstream filtering (preferences, rate limits, missing channel info). Check the request log to verify the payload was correct.
</Note>

<Warning>
  Request logs show complete JSON payloads, which may include PII. Avoid sending secrets in payload fields. Access control determines who can view logs.
</Warning>

### Workflow Execution Logs

Workflow execution logs show how individual workflows are processed for each user, including execution steps and channel delivery status. These logs are per-user and provide step-by-step workflow details.

**When to check:** Workflows don't trigger after a successful API call, notifications aren't sent (but API succeeded), need to see workflow processing steps and node execution, template rendering or channel computation failed, or want to understand why certain channels were selected or skipped.

<Frame>
  ![](/images/workflow-detailed.png)
</Frame>

**Status indicators:**

| Status | Meaning |
|--------|---------|
| 🟢 **Completed** | All channels processed successfully |
| 🟠 **Partial Failure** | At least one channel failed, but others succeeded |
| 🔴 **Failed** | Workflow execution failed completely before any notifications were triggered |

**What you'll see:**

The **overview section** shows workflow slug (clickable link to workflow configuration), tenant ID, execution ID (with copy button), idempotency key (with copy button), recipient, status, started at timestamp, and notification category.

A **workflow diagram** shows your workflow structure with trigger, nodes, and exit points, highlighting the path taken during execution, including which conditional branch executed and time spent in delays.

The **execution history** is a chronological log showing workflow start, node processing, channel computation, template rendering, and notification triggering. Each entry shows timestamp and relevant properties. Every node includes detailed logs with template used, execution status, and processing steps.

The log shows how user preferences were evaluated and which channels were selected based on opt-outs and channel availability. For each notification channel, view vendor information, triggered status (✅ or ❌), delivery timing (e.g., "116ms"), seen status, and click/interaction data. A user channel summary shows which channels were active and used for each recipient.

**Common errors captured:**

| Error Type | Examples |
|------------|----------|
| **Template rendering failures** | Missing variables, syntax errors |
| **Channel computation issues** | No active channels, preference opt-outs |
| **Node execution failures** | Condition mismatches, data validation errors |
| **Variable evaluation errors** | Missing data, type mismatches |

**Navigate from here:** Use "View Execution" link in message logs to navigate to the corresponding workflow execution, click workflow slug to view workflow configuration, use idempotency key to find related request logs and message logs, or click recipient to view all logs for that user.

### Broadcast Execution Logs

Broadcast execution logs track broadcast campaigns sent to user lists. Unlike workflow execution logs which are per-user, broadcast logs provide a summary of execution across a list of users, showing aggregate statistics and processing steps.

**When to check:** Broadcasts don't reach all users in the list, need aggregate statistics (triggered, skipped, failed counts), want to understand why users were skipped, need channel-level breakdowns across all users, or want to track broadcast processing performance.

<Frame>
  ![](/images/broadcast-detailed.png)
</Frame>

**Status indicators:**

| Status | Meaning |
|--------|---------|
| 🟢 **Triggered** | Users who received notifications on at least one channel |
| 🟠 **Skipped** | Excluded due to missing channels or opt-out |
| 🔴 **Failed** | Trigger failed due to errors (e.g., template rendering failures) |

<Note>
  Broadcast "Triggered" means "user received notification on at least one channel". This is different from Message "Triggered" which means "handed off to vendor".
</Note>

**What you'll see:**

The **broadcast information** includes broadcast slug (auto-generated from template slug, list ID, and notification category), status, started at timestamp, list ID, tenant ID, idempotency key (with copy button), broadcast execution ID (with copy button), and notification category.

The **execution history** is a chronological log showing broadcast start, template loading, user profile fetching (with progress percentage), channel computation, template rendering, and notification triggering. Each entry shows timestamp and relevant properties.

**Aggregate statistics** summarize the broadcast performance:

| Metric | Description |
|--------|-------------|
| **Total users processed** | Percentage and count of all users in the list |
| **Triggered by SuprSend** | Percentage and count of users who received notifications |
| **Channel-level stats** | Detailed breakdown by channel showing triggered counts |
| **View all message logs** | Link to see individual delivery status for all users |

**Common errors captured:**
- Template rendering failures result in failed status for affected users
- Channel computation errors at scale

**Why execution is skipped:**

| Reason | Description |
|--------|-------------|
| **Unsubscribed** | User has unsubscribed from that notification category |
| **Missing channel** | User does not have that channel (e.g., no email address, no phone number) |
| **Preference opt-out** | User preference opt-outs prevent delivery |

**Navigate from here:** Click "View all message logs" to navigate directly to individual message delivery status for all users in the broadcast, use idempotency key to find related request logs, or click list ID to view list details.

<Warning>
  Broadcast logs show processing up to trigger. For delivery details, see message logs.
</Warning>

---

### Message Logs

Message logs show individual notification messages and delivery tracking across all channels. These logs capture all send nodes and delivery attempts from trigger through delivery to user engagement.

**When to check:** Notifications aren't delivered to users, need channel-level delivery status and timing, want to track user engagement (seen, clicked), need vendor responses and delivery confirmations, or want to debug delivery failures or delays.

<Frame>
  ![](/images/messages-detailed.png)
</Frame>

**What you'll see:**

Each message log entry includes **message information**: triggered at timestamp, workflow/broadcast name, node (e.g., Multi-Channel, Email, SMS, Mobile Push, Inbox), template, recipient ID, and tenant ID.

For each channel, the **channel status flow** shows the delivery timeline:

| Stage | Details |
|-------|---------|
| **Vendor** | Notification service provider (e.g., SuprSend, SendGrid) |
| **Triggered** | ✅ (success) or ❌ (failed) - whether the notification was successfully triggered to the vendor |
| **Delivered** | ✅ (success) or ❌ (failed) with delivery time (e.g., "116ms") - whether the notification was delivered to the end user |
| **Seen** | Whether the notification was seen/read by the user |
| **Clicked** | Whether the notification was clicked/interacted with |

Hover over status indicators to see the specific state (when triggered, delivered, seen, clicked) and if failed, the reason for failure. Messages can be sent immediately, scheduled, or delayed. All delivery attempts to webhooks are logged with request and response details.

<Note>
  Configure `https://hub.suprsend.com/webhook/*` in your vendor dashboard to track delivery, seen, and click events. Timing depends on vendor callback speed.
</Note>

**Common errors captured:**

<Columns>
  <Column>
    **Trigger Failed** — SuprSend could not hand off to vendor:
    
    - Template rendering failures before vendor API call
    - Missing channel information (no email, no phone)
    - Bad configuration (invalid credentials, network failure)
    - Internal SuprSend errors before vendor contact
    - Vendor rejected request before accepting (rate limits, account issues)
  </Column>
  <Column>
    **Failure by vendor** — Vendor accepted request but failed to send/deliver:
    
    - Invalid recipient format (bad email/phone format)
    - Template rejected by vendor (doesn't meet vendor requirements)
    - Provider outage or service unavailable
    - Invalid template structure for that vendor
    - Credential errors discovered after acceptance
  </Column>
</Columns>

<Note>
  **Delivery delays:** Some events (delivery/seen/click) depend on vendor callbacks and may appear with delay.
</Note>

**Navigate from here:** Use "View Execution" link to navigate to the corresponding workflow execution log, use idempotency key to find related request logs and workflow execution logs, or click recipient ID to view all logs for that user.

## Reference

<AccordionGroup>
  <Accordion title="Notification Status Stages">
    SuprSend tracks notification status through multiple stages from request acceptance to user interaction:

    | Stage | Status | Description |
    |-------|--------|-------------|
    | 1 | **Requested** | Notification request is accepted by SuprSend |
    | 2 | **Processed** | SuprSend started processing the request |
    | 3 | **Triggered** | Notification request is passed from SuprSend to channel vendor |
    | 3 | **Trigger Failed** | SuprSend encountered an error forwarding the request to the vendor |
    | 3 | **Failure by vendor** | Vendor accepted the request but failed to deliver to the end user |
    | 4 | **Delivered** | Notification is successfully delivered to the end user |
    | 5 | **Seen** | Notification was seen/read by the user |
    | 6 | **Dismissed** | User dismissed the notification (Android Push only) |
    | 7 | **Interacted** | User clicked on the notification |

    <Note>
      For detailed explanations of **Trigger Failed** scenarios and troubleshooting steps, see the [Error Guides](/docs/error-guides).
    </Note>
  </Accordion>

  <Accordion title="Status Tracking by Channel">
    **Requested, Processed, Triggered** are tracked for all channels. Here are the statuses tracked from delivery onwards:

    | Channel | Failure by vendor / Trigger Failed | Delivered | Seen | Dismissed | Interacted (Clicked) |
    |---------|-----------------------------------|-----------|------|-----------|---------------------|
    | Email | ✅ | ✅ | ✅ | - | ✅ |
    | SMS | ✅ | ✅ | - | - | - |
    | WhatsApp | ✅ | ✅ | ✅ | - | - |
    | Android Push | ✅ | ✅ | ✅ | ✅ | ✅ |
    | iOS Push | ✅ | ✅ | ✅ | - | ✅ |
    | Web Push | ✅ | ✅ | ✅ | - | ✅ |
    | Inbox | ✅ | ✅ | - | - | ✅ |
    | Slack | ✅ | ✅ | - | - | - |
    | MS Teams | ✅ | ✅ | - | - | - |

    <Note>
      **Set Callback URL**: Configure `https://hub.suprsend.com/webhook/*` in your vendor dashboard to track delivery, seen, and click events. See [vendor integration](/docs/vendors) docs for details.
    </Note>
  </Accordion>

  <Accordion title="Technical Details">
    **Log ordering and consistency:**

    Logs are ordered by timestamp, but some events (delivery/seen/click) depend on vendor callbacks and may appear with delay. Message logs may appear before execution logs complete due to async processing.

    **Timezone semantics:**

    - UI displays timestamps in your browser's timezone
    - Date range selection supports timezone-aware selection
    - Export format timezone depends on the export method

    **Access and limits:**

    - Log search may have rate limits depending on your plan
    - Filters query within the selected date range
    - Pagination is available for large result sets
    - Access control determines who can view logs in your workspace
  </Accordion>
</AccordionGroup>
