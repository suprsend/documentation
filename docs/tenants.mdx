**Tenants** isolate notification configuration so that each customer, brand, project, product module, or use case has its own settings—for example multiple projects or a tenancy with its own global-level preferences. Each tenant has its own branding, preferences, vendors, and hosted unsubscribe page. One workflow and one template serve all tenants; the `tenant_id` in each send request selects which configuration is applied at runtime.

## Use cases

<CardGroup cols="3">
  <Card title="Multi-tenant SaaS or B2B" icon="building" iconType="solid">
    Send notifications on behalf of many customer organizations or to their end users.
  </Card>
  <Card title="White-labelling" icon="palette" iconType="solid">

## Per-tenant capabilities

Each tenant can have its own:

| Capability | What it means |
|------------|----------------|
| **[Branding & templates](/docs/tenant-templates)** | One shared template; logo, colors, and social links are applied per tenant so each notification reflects that tenant’s identity. |
| **[Unsubscribe page](/docs/user-preferences#hosted-preference-page)** | A hosted preference (unsubscribe) page for that tenant so users manage preferences in the right tenant context—for example, from a link in the email footer. |
| **[Preferences](/docs/tenant-preference)** | **Admin:** which notification categories and channels are visible or configurable for the tenant.<br/>**Defaults:** default opt-in/opt-out and channel settings for that tenant’s users. |
| **[Vendors](/docs/tenant-vendor)** | Email domain, SMS sender ID, and other channel providers configured per tenant so notifications are sent via that tenant’s accounts. |


## Quick example

When a notification is sent with `tenant_id: "acme"` and a template that uses `$tenant.tenant_name`, the recipient sees “Acme” in the notification. The `$tenant.*` variables in templates are replaced with tenant-specific values based on the `tenant_id` passed when sending.
