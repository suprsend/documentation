title: "Branch"
description: "Use branch to route notifications across different paths by applying condition on input data."

Branch is an `if / else if / else` step that routes notifications through different workflow paths based on conditions. You can add up to 10 branches (9 condition branches + 1 default branch). The first branch that satisfies its condition will be executed.

Conditions are evaluated **at runtime**, using the latest available data at the moment the Branch node executes.

**Common use cases:** A/B testing, personalized journeys, conditional follow-ups, multi-step reminders, routing by trigger payload, batch/digest data, or tenant settings.

## Execution Model

The Branch node supports two branch types:

1. **Condition Branch**: Executes when its condition evaluates to true (up to 9 condition branches).
2. **Default Branch**: Executes when no condition branch evaluates to true.

**Execution rules:**
- Conditions are evaluated in order from first to last.
- The first condition that evaluates to true executes its branch.
- If no condition evaluates to true, the default branch executes.
- If the default branch has no nodes, it automatically connects to the exit node.

<Note>
  If you need to execute additional nodes, add them to a condition branch rather than the default branch.
</Note>

## Condition Syntax

Conditions evaluate data from trigger payloads, user properties, tenant properties, or message status. A condition consists of four components: **Data type**, **Key**, **Operator**, and **Value**.

### Data Types

Available data sources:

| Data Type | What It Represents | How to Reference |
|-----------|-------------------|------------------|
| **Input Payload** | Data from trigger payload or nodes before the branch | Use key directly (e.g., `order_amount`) |
| **Actor** | Properties of the user who performed the action | `$actor.<property_key>` (e.g., `$actor.role`) |
| **Recipient** | Properties of the user receiving the notification | `$recipient.<property_key>` (e.g., `$recipient.plan`) |
| **Tenant** | Properties of the tenant/brand | `$brand.<property_key>` (e.g., `$brand.timezone`) |
| **Message Status** | Delivery status of previously sent notifications | `message_status` (reference node by slug, e.g., `message_status from node "welcome-email" == "seen"`) |

<Note>
  **Message Status**: Requires vendor tracking enabled and node slug reference. See [Message Status reference](#message-status-reference) below for available statuses, channel support, and behavior details.
</Note>

### Operators

Available comparison operators:

| Operator | Use Case | Example | Supported Data Types |
|----------|----------|---------|---------------------|
| `==` | Equal to (case sensitive) | `user_role == "admin"` | All |
| `!=` | Not equal to (case sensitive) | `user_role != "guest"` | All |
| `>`, `>=` | Greater than / greater than or equal | `order_amount >= 100` | Numbers, timestamps |
| `<`, `<=` | Less than / less than or equal | `order_amount <= 50` | Numbers, timestamps |
| `contains` | Substring or array item match | `tags contains "urgent"` | Strings, arrays |
| `not contains` | No substring or array item match | `tags not contains "spam"` | Strings, arrays |
| `is empty` | Missing, empty string, or null | `phone_number is empty` | All |
| `is not empty` | Present and not empty/null | `phone_number is not empty` | All |
| `datetime is` | Datetime equal to | `event_date datetime is "2024-01-01T00:00:00Z"` | Timestamps |
| `datetime is before` | Datetime less than | `event_date datetime is before "now+1d"` | Timestamps |
| `datetime is after` | Datetime greater than | `event_date datetime is after "now"` | Timestamps |
| `intersects` | Any array value matches | `user_roles intersects ["admin", "manager"]` | Arrays |
| `not intersects` | No array values match | `user_roles not intersects ["guest"]` | Arrays |

<Note>
  **Type constraints**: If a key's data type doesn't match the operator (e.g., using `>` on a string), the condition will always evaluate to false.
</Note>

### Values

**Fixed values:**
- String: `"admin"`
- Number: `100`, `99.99`
- Boolean: `true`, `false`
- Datetime: `"2024-01-01T00:00:00Z"`, `"now+1d"`

**Dynamic values:**
- Input payload: Use key directly (e.g., `payment_due_date`)
- User/tenant properties: Use `$` prefix (e.g., `$recipient.plan`, `$brand.timezone`)

## Combining Conditions

Combine conditions using `AND` and `OR` logical operators:

- **AND**: All conditions must evaluate to true
- **OR**: At least one condition must evaluate to true

**Example:** `(user_role == "admin" OR user_role == "manager") AND priority == "high"`

<Note>
  Nested grouping is not supported. Rewrite complex logic using equivalent expanded conditions. For example, `(a OR b) AND c` becomes `(a AND c) OR (b AND c)`.
</Note>

## Message Status Reference

**Prerequisites:**
- Vendor tracking enabled
- Node slug reference (e.g., `message_status from node "welcome-email"`)

**Statuses:**

| Status | `==` | `!=` | Description |
|--------|------|------|-------------|
| `delivered` | ✅ | ✅ | Notification reached user (includes delivered, seen, clicked) |
| `seen` | ✅ | ✅ | User viewed/opened notification |
| `clicked` | ✅ | ✅ | User clicked notification |
| `delivery_failed` | ✅ | ❌ | Vendor error prevented delivery |

**Channel Support:**

| Channels | Delivered | Seen | Clicked |
|----------|-----------|------|---------|
| Email, Android Push, iOS Push, Web Push, Inbox | ✅ | ✅ | ✅ |
| WhatsApp | ✅ | ✅ | ❌ |
| SMS, Slack, MS Teams | ✅ | ❌ | ❌ |

**Multi-Channel Rules:**

| Condition | Result |
|-----------|--------|
| `== "delivered"` | At least one channel succeeds → `delivered` |
| `== "delivery_failed"` | All channels must fail → `delivery_failed` |
| `!= "delivered"` | No channel succeeds → condition passes |
| `== "seen"` or `== "clicked"` | Any channel reports event → condition passes |
| `!= "seen"` or `!= "clicked"` | No channel reports event → condition passes |

<Note>
  Evaluation occurs after the referenced node executes and vendor feedback is received. Only fixed enum values allowed.
</Note>

## Examples

**Example 1: Route by user plan**

```
Branch:
  Condition: $recipient.plan == "premium"
    → Execute: Send premium notification
  Default:
    → Execute: Send standard notification
```

**Example 2: Fallback routing on delivery failure**

```
Node: Send push notification (slug: "order-update")
Branch:
  Condition: message_status from "order-update" == "delivery_failed"
    → Execute: Send same message via SMS
  Default:
    → Execute: Continue workflow
```

**Example 3: Follow-up based on engagement (combining conditions)**

```
Node: Send welcome email (slug: "welcome-email")
Wait: 24 hours
Branch:
  Condition: message_status from "welcome-email" == "delivered" 
            AND message_status from "welcome-email" != "seen"
    → Execute: Send reminder email
  Condition: message_status from "welcome-email" == "clicked"
    → Execute: Send advanced tutorial
  Default:
    → Execute: No action needed
```

**Example 4: Priority-based routing with user role**

```
Branch:
  Condition: priority == "high" AND $recipient.role == "admin"
    → Execute: Send immediately via all channels
  Condition: priority == "medium"
    → Execute: Send batched notification
  Default:
    → Execute: Send daily digest
```

## Frequently Asked Questions

<AccordionGroup>
  <Accordion title="How many branches can I add?" defaultOpen={false}>
    Up to 10 branches total: 9 condition branches + 1 default branch.
  </Accordion>

  <Accordion title="What happens if multiple branches are satisfied?" defaultOpen={false}>
    The first branch in order is executed (as mentioned in the intro). Place more specific conditions before general ones.
  </Accordion>

  <Accordion title="When are Message Status conditions evaluated?" defaultOpen={false}>
    Only after the referenced node has executed and vendor feedback has been received. The condition checks actual delivery state, not input data.
  </Accordion>

  <Accordion title="Why don't my Message Status conditions work?" defaultOpen={false}>
    Message Status requires vendor tracking. Ensure you have:
    * A vendor configured in your workspace
    * Tracking enabled for the channel (email requires explicit tracking)
    * The referenced node has already executed
  </Accordion>

  <Accordion title="What's the difference between 'delivery_failed' and 'not delivered'?" defaultOpen={false}>
    * **`delivery_failed`** (`== "delivery_failed"`): Requires **all channels** to fail. If any channel succeeds, it's not considered failed.
    * **`!= "delivered"`**: Requires **no channel** to succeed. If any channel reports Delivered/Seen/Clicked, the condition fails.
    
    **Common mistake**: `delivery_failed` ≠ "some channels failed". It requires all channels to fail.
  </Accordion>

  <Accordion title="How does 'Delivered' work in multi-channel mode?" defaultOpen={false}>
    If the message is delivered on **at least one channel**, the overall status is **Delivered**. For example, if you send via Email + WhatsApp + Push and only Email succeeds, the status is still "Delivered".
  </Accordion>

  <Accordion title="Can I use dynamic values with Message Status?" defaultOpen={false}>
    No. Only fixed enum values are allowed: `"delivered"`, `"seen"`, `"clicked"`, or `"delivery_failed"`.
  </Accordion>

  <Accordion title="How do I reference a node for Message Status?" defaultOpen={false}>
    Each node has a unique slug. Use the node's slug to check message status from that specific node (e.g., `message_status` from node with slug `"welcome-email"`).
  </Accordion>
</AccordionGroup>
