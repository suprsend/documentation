This page covers all types of errors that can occur while validating and processing API/SDK requests, including common causes and how to fix them. If you encounter an error not listed here, please contact support with the error message and request details.

### What Request Logs are
[Request Logs](/docs/logging) capture every API/SDK request SuprSend receives, including the full request payload and API response. They help you debug request validation issues, missing required fields, authentication failures, invalid resource identifiers, and any error that prevents workflow execution from starting.

### channel details missing for transient user


**What does this mean:**
A transient (anonymous) user was specified with `"is_transient": true` in the workflow trigger but no channel identities were provided.

**How to fix it:**
When you pass `is_transient: true` in the workflow trigger, SuprSend doesn't create or look for that user in the database. Since it's used for anonymous sending, you need to pass channel details inline in the recipient object like this — `{"is_transient": true, "$email": ["joe@example.com"]}`. See [Sending to Anonymous Users](/docs/node-trigger-workflow-from-api#sending-notification-to-anonymous-user) for more details.

### one of [distinct_id, object_type/id] must be present / user's distinct_id must be present if it's not transient


**What does this mean:**
In your API-based trigger, the recipient object is missing its identifier — neither `distinct_id` nor the `object_type`/`id` pair was included.

**How to fix it:**
Every recipient object must have either a `distinct_id` (for users), `is_transient: true` with channel details (for anonymous users), or both `object_type` and `id` (for objects). Check if you're missing it or the key name is wrong. See [Trigger Workflow](/docs/trigger-workflow).

### no valid recipients found / user [distinct_id: `<distinct_id>`] not found / User not found with distinct_id: `<distinct_id>`


**What does this mean:**
The `distinct_id` passed in the [event trigger](/docs/event-vs-api-trigger) or `recipient` passed in the API trigger does not exist in the workspace.

**How to fix it:**
- Search with the `distinct_id` on the user page in the dashboard to confirm if the user exists. If not, create the user via API/SDK or dashboard. See [Create User](/docs/users#creating-user-profile-on-suprsend).
- You can also create the user inline in case of an API-based trigger by passing channel info inline in the recipient object like this — `{"distinct_id": "user-123", "$email": ["user@example.com"]}`.
- For event-based triggers, users need to be pre-created; but if that user is part of your payload instead of the direct `distinct_id` field, you can use override settings in the trigger node to override the recipient with the value from your payload. See [Trigger Workflow](/docs/trigger-workflow).
- If the user exists but the error still occurs, check if the workflow has any recipient filtering conditions in the trigger node that may be excluding this user.

### `"recipients":"must contain at least 1 item"`


**What does this mean:**
The `recipients` array passed in the **Add/Update Object Subscription API** is empty. At least one recipient must be present in the array.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Ensure the `recipients` array has at least one valid entry before making the request. You can pass up to 100 recipients in a single API call:
```json
{
  "recipients": ["user123", "user456"]
}
```
- If you're building the `recipients` list dynamically in your code, add a guard to ensure the array is non-empty before calling the API.
- See [Object Subscriptions](/docs/object-subscriptions) for more details.

### `"distinct_ids":"must contain at maximum 100 items"`


**What does this mean:**
The `distinct_ids` array in your request exceeds the maximum limit of 100 items per API call. This error can occur in two APIs:
- **Bulk User Update API** — when updating user profiles in bulk
- **Bulk User Preference Update API** — when updating preferences for multiple users at once

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Split your `distinct_ids` array into batches of 100 or fewer and make multiple API calls:
```json
{
  "distinct_ids": ["user1", "user2", "...up to 100 users"]
}
```
- If you're building the list dynamically, add a chunking step in your code before calling the API. For example, if you have 300 users, make 3 separate calls with 100 users each.
- See [Bulk Update User Preference](/reference/bulk-update-user-preference) and [Users](/docs/users) for more details.

<span id="error-category-not-applicable"></span>

### Category `'<category>'` not applicable to tenant `'default'`


**What does this mean:**
The workflow is assigned a notification category (e.g., `system`, `transactional`, or `promotional`) that has not been configured for the `default` tenant. In SuprSend, vendors for Email and SMS channels are configured at the root-category level, and each tenant — including the `default` tenant — must have a vendor set up for the category being used. If no vendor is configured for that category on the tenant, the request is rejected before workflow execution begins.

**How to fix it:**
- Go to the [Vendor Settings](/docs/vendors) page in the dashboard and ensure a vendor is configured for the relevant category (e.g., `system`) under the **default** tenant.
- If you did not intend to use the `default` tenant, verify that you are passing the correct `tenant_id` in your workflow trigger. If no `tenant_id` is passed, SuprSend automatically falls back to the `default` tenant. See [Trigger Workflow](/docs/trigger-workflow).
- If you are using a custom tenant, make sure the `tenant_id` in your trigger matches a tenant that exists in your workspace and has a vendor configured for the workflow's category. See [Tenant Vendor](/docs/tenant-vendor).
- To review which categories are configured and how root-categories map to vendors, see [Notification Categories](/docs/notification-category).

### tenant/brand doesn't exist with id: `<tenant_id>` / No tenant found for tenant_id `<tenant_id>`


**What does this mean:**
The `tenant_id` referenced in the request does not exist in the workspace. This error can occur on workflow triggers (when a non-existent tenant is passed in the trigger payload) as well as on direct Tenant API calls (e.g., tenant update) where the tenant has not been created yet. SuprSend validates the tenant at the API request stage and rejects the request if no matching tenant is found.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Verify that the `tenant_id` value in your request matches an existing tenant in your workspace. You can view all tenants from the **Tenants** page in the dashboard.
- Tenant IDs are case-sensitive. Ensure there are no typos, extra characters, or casing mismatches between what you're passing and what's configured in the dashboard.
- If the tenant does not exist yet, create it first via the dashboard or using the backend SDK before triggering the workflow or making update calls. See [Tenants](/docs/tenants).
- If you are calling the **Tenant Update API** directly, verify that the `tenant_id` in the request URL matches an existing tenant in your workspace before making update calls.
- If you do not need tenant-specific customization, remove the `tenant_id` field from your trigger entirely — SuprSend will automatically fall back to the `default` tenant. See [Trigger Workflow](/docs/trigger-workflow).

### workflow version not found


**What does this mean:**
The workflow linked to the triggered event exists in the workspace but has no published version. This happens when a workflow has been created but never committed, or when a previously committed version was unpublished. SuprSend cannot execute a workflow with no active version, so the request is rejected at the API request stage before execution begins.

This error is most commonly seen with **event-based triggers**, where an event is mapped to a workflow in the dashboard but the workflow is still in draft state.

**How to fix it:**
- Go to the [workflow details page](https://app.suprsend.com/en/production/workflows) in the dashboard and check if the workflow is in `draft` state.
- If it is, click **Commit** to publish the workflow and make it live. See [Design Workflow](/docs/design-workflow).
- If the workflow was recently edited, ensure the latest changes have been committed — uncommitted edits remain in draft and are not used for execution.
- If you are not sure which workflow is linked to the event, go to the [Events](https://app.suprsend.com/en/production/events) page in the dashboard, find the event by name, and check which workflow it is mapped to.

### template `'<slug>'` not found


**What does this mean:**
The template referenced in the workflow trigger does not exist in the workspace. SuprSend validates the template slug at the API request stage and rejects the request if no matching template is found.

This can happen when:
- The template slug passed in the trigger is incorrect, misspelled, or uses a different casing.
- The template was deleted or renamed after the trigger was set up.
- The template exists but belongs to a different workspace than the one being used.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Go to the [Templates](https://app.suprsend.com/en/production/templates) page in the dashboard and verify that a template with the referenced slug exists. Template slugs are derived from the template name and are case-sensitive.
- If the template was deleted or renamed, either restore it, create a new template with the correct slug, or update your trigger to reference the correct slug.
- If you are using the **workflow-based trigger** (recommended), ensure the workflow is linked to a published template in its delivery node. The template must have a live version before it can be used. See [Design Template](/docs/templates) and [Design Workflow](/docs/design-workflow).

**What does this mean:**

<span id="error-subscribers-list-empty"></span>

### subscribers list is empty for list_id: `'<list_id>'`


**What does this mean:**
The list referenced in the broadcast trigger exists in the workspace but has no subscribers. SuprSend rejects the broadcast at the API request stage if the list is empty, since there are no recipients to send the notification to.

This is commonly seen with **scheduled broadcasts** where a list is populated dynamically — if no users were added to the list before the broadcast was triggered, the request will fail.

**How to fix it:**
- Go to **Subscribers → Lists** in the dashboard and verify that the list has active subscribers before triggering the broadcast.
- If the list is populated dynamically (e.g., synced from a database or third-party platform), ensure the sync has completed and users have been added to the list before the broadcast runs. See [List sync via database](/docs/list-sync-via-database).
- If you are running a **scheduled broadcast**, check whether the schedule timing aligns with when the list is expected to be populated. If the list is empty at the time of trigger, adjust the schedule or add a delay to ensure users are present before the broadcast fires.
- If an empty list is a valid and expected state in your setup (e.g., some days there may be no idle users), you can safely ignore this error — no notifications will be missed since there are no recipients to notify.

<span id="error-schema-validation-failed"></span>

### Workflow trigger payload failed schema validation


**What does this mean:**
The `data` payload passed in the workflow trigger failed JSON Schema validation. The workflow has a schema linked to it that enforces required fields, allowed properties, and expected types — and the payload you sent violates one or more of those rules.

SuprSend validates the payload against the linked schema at the API request stage and rejects the trigger immediately if validation fails — before workflow execution begins.

Common validation errors include:
- **Missing required field** — e.g., `(root): missing required property 'invoice_id'` or `charger: missing required property 'name'`
- **Wrong data type** — e.g., `int: Instance type "string" is invalid. Expected "number"`
- **Disallowed property** — e.g., `(root): property 'key' is not allowed by the schema`

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request, response, and validation error details by clicking on the failed log in the **Request Logs** tab.
- Review the `data` payload you are sending and ensure all required fields defined in the linked schema are present and of the correct type. The error message indicates the exact path and field — for example, `charger: missing required property 'name'` means the `name` field is absent inside the `charger` object, and `(root): missing required property 'invoice_id'` means `invoice_id` is missing at the top level.
- If a field has the **wrong type** (e.g., passing `"42"` as a string instead of `42` as a number), correct the value type before sending.
- If a **property is not allowed**, it means the schema has `additionalProperties: false` set and you are sending a field that is not defined in the schema. Either remove the unexpected field from your payload, or update the schema to allow it.
- Multiple validation errors can appear in a single error message separated by spaces — fix all of them before re-triggering.
- To view the schema linked to the workflow, go to **Developers → Schemas** in the dashboard, or open the workflow's **Trigger Step → Schema** section.
- If the schema requires a field that is not always available in your payload, update the schema to make that field optional, or ensure your integration always includes it. See [Validate Trigger Payload](/docs/validate-workflow-payload).
- If you are using an **event-based trigger**, the schema is linked to the event — check the schema on the **Events** page in the dashboard.

<span id="error-object-subscription-missing-identifier"></span>

### in case recipient is a map, one of [distinct_id, object_type/id] must be present


**What does this mean:**
A recipient object passed in the **Add/Remove Object Subscription API** is missing its identifier. When a recipient is passed as an object (map), SuprSend requires either a `distinct_id` (to subscribe a user) or both `object_type` and `id` (to subscribe a child object). If neither is present, the request is rejected at the API request stage.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Ensure every recipient object in your `recipients` array includes a valid identifier. Use `distinct_id` for users, or `object_type` + `id` for child objects:
```json
// Subscribe a user
{
  "distinct_id": "user-123",
  "$email": ["user@example.com"]
}

// Subscribe a child object
{
  "object_type": "teams",
  "id": "devs"
}
```
- Check for `null`, `undefined`, or empty string values being passed as the identifier — these will also trigger this error.
- If you are passing recipients as a plain array of strings (distinct IDs only), this error will not occur. This error is specific to recipients passed as objects (maps). See [Object Subscriptions](/docs/object-subscriptions).

### object `<object_type>/<object_id>` not found


**What does this mean:**
The object referenced in the **Add/Update Object Subscription API** does not exist in the workspace. The `object_type` and `object_id` passed in the request URL could not be found.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Verify that the `object_type` and `object_id` in your request URL are correct and the object has been created before adding subscriptions to it:
```bash
POST /v1/object/:object_type/:object_id/subscription/
```
- If the object doesn't exist yet, create it first using the [Create/Update Object API](/reference/create-update-objects) before calling the subscription API.
- Note that `object_type` and `object_id` only support the following characters: `a-z, 0-9, -, _`. Ensure there are no uppercase letters, spaces, or special characters in your values.
- See [Object Subscriptions](/docs/object-subscriptions) for more details.

<span id="error-invalid-channel-value"></span>

### invalid value for channel `'<channel>'`: `<value>`. error: invalid email address


**What does this mean:**
The channel identifier passed in the recipient object — in this case, an email address — failed format validation. SuprSend validates channel values at the API request stage before workflow execution begins. The request is rejected if the value is not a valid, well-formed address for that channel.

Common causes:
- The email address contains invalid characters, incorrect formatting, or is malformed (e.g., missing `@`, invalid domain, trailing dot before `@` like `user.@example.com`, or leading/trailing spaces).
- The value passed is not an email address at all — for example, a placeholder, an unresolved variable, or data from the wrong field.
- The channel identifier was populated from user input that was not sanitized before being passed to the API.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Verify the value being passed for the `$email` field in your recipient object is a valid email address:
```json
{
  "distinct_id": "user-123",
  "$email": ["user@example.com"]
}
```
- If the value is being populated dynamically from user input or an external system, ensure it is validated and sanitized before being passed to the SuprSend API.
- Watch for subtle formatting issues that pass basic checks but are still invalid:
  - ❌ `SwarnaM.@kantar.com` → ✅ `SwarnaM@kantar.com`
  - ❌ `user.@example.com` → ✅ `user@example.com`
- If the user's email is stored on their profile in SuprSend, you do not need to pass it inline — SuprSend will resolve it from the user's profile automatically. See [Create User](/docs/users#creating-user-profile-on-suprsend).

<span id="error-invalid-sms-channel-value"></span>

### invalid value for channel `'sms'`: `<value>`. error: error while parsing number to E164 format


**What does this mean:**
The phone number passed for the `$sms` channel could not be parsed into **E.164 format**. E.164 is the international standard for phone numbers and requires a `+` prefix followed by the country code and the subscriber number (e.g., `+15555555555` for a US number). Numbers passed without a country code, with incorrect formatting, or with non-numeric characters will fail this validation.

SuprSend validates channel values at the API request stage and rejects the request before workflow execution begins.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Ensure the phone number is in valid **E.164 format**: a `+` sign followed by the country code and the full subscriber number, with no spaces, dashes, or brackets:
  - ❌ `8168250067` → ✅ `+18168250067`
  - ❌ `0091-9876543210` → ✅ `+919876543210`
  - ❌ `(816) 825-0067` → ✅ `+18168250067`
- If the phone number is being populated dynamically from user input or an external system, ensure the country code is always included and the number is sanitized to E.164 format before being passed to the SuprSend API.
- If the user's phone number is already stored correctly on their profile in SuprSend, you do not need to pass it inline — SuprSend will resolve it from the user's profile automatically. See [Create User](/docs/users#creating-user-profile-on-suprsend).

<span id="error-87"></span>

### error while parsing number to E164 format


**What does this mean:**
The phone number passed in the `$phone`, `$sms`, or `$whatsapp` field in the **User Update API** could not be parsed because it is not in the valid E.164 format.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Ensure all phone numbers are passed in **E.164 format**: a `+` sign followed by the country code and the number, with no spaces, dashes, or special characters:
```json
{
  "$sms": ["+14155552671"],
  "$sms": ["4155552671"],
  "$sms": ["+1-415-555-2671"],
  "$sms": ["(415) 555-2671"]
}
```
  - ✅ `+14155552671` — correct
  - ❌ `4155552671` — missing country code
  - ❌ `+1-415-555-2671` — dashes not allowed
  - ❌ `(415) 555-2671` — spaces and brackets not allowed
- Make sure a `+` sign is always included with the country code prefix before the number. For example, `+1` for the US, `+44` for the UK, `+91` for India.
- See [Users](/docs/users) for more details on updating user channel information.

<span id="error-invalid-locale-language"></span>

### invalid locale/language: `'<value>'`


**What does this mean:**
The `$preferred_language` value passed in the user update request is not a valid language code. SuprSend expects language to be set in **ISO 639-1 2-letter format** (e.g., `en`, `pt`, `es`, `fr`). Passing a locale tag like `pt-br`, a full language name like `Portuguese`, or any other non-standard format will cause this error.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Update the `$preferred_language` value to use the correct **ISO 639-1 2-letter** language code. For example:
  - ❌ `pt-br` → ✅ `pt`
  - ❌ `zh-CN` → ✅ `zh`
  - ❌ `Portuguese` → ✅ `pt`
  - ❌ `ua` → ✅ `uk` (Ukrainian — `ua` is the country code, not the language code)
- For the full list of supported language codes, refer to the [SuprSend language codes reference](https://github.com/suprsend/suprsend-py-sdk/blob/v0.12.0/src/suprsend/language_codes.py).
- This field can be set on the user profile via backend SDK, or passed inline in the recipient object during a workflow trigger. See [Trigger Workflow](/docs/trigger-workflow).

<span id="error-invalid-timezone"></span>

### invalid timezone: `'<value>'`


**What does this mean:**
The `$timezone` value passed in the user update request is invalid. SuprSend expects timezones in **IANA (TZ identifier) format** (e.g., `America/New_York`, `Asia/Kolkata`, `UTC`). Passing `null`, an empty string, an unresolved variable, or any value that does not match a valid IANA timezone identifier will cause this error.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Ensure the `$timezone` value is a valid IANA timezone string. You can find the full list of valid identifiers in the [IANA timezone database](https://en.wikipedia.org/wiki/List_of_tz_database_time_zones#List). For example:
  - ❌ `null` / `<nil>` / `""` → ✅ `"America/New_York"`
  - ❌ `"IST"` → ✅ `"Asia/Kolkata"`
  - ❌ `"GMT+5:30"` → ✅ `"Asia/Kolkata"`
- If the timezone is being populated dynamically from a third-party integration (e.g., Segment, Asana, or another connector), ensure the source field is mapped correctly and always resolves to a valid non-null value before being passed to SuprSend.
- If the timezone is not known or not available for a user, omit the `$timezone` field entirely rather than passing `null` or an empty value.

<span id="error-invalid-webpush-subscription"></span>

### invalid webpush subscription: `{"keys":{"auth":"","p256dh":""}}`


**What does this mean:**
The [web push](/docs/js-webpush) subscription object passed in the user update request is invalid because the `auth` and `p256dh` keys are empty strings. These are VAPID encryption keys that are generated by the browser when a user grants push notification permission and a valid push subscription is created. Empty values mean the subscription was not successfully generated before being sent to SuprSend.

Common causes include:
- The web push subscription object was captured before the browser finished generating it.
- The user's browser denied or blocked notification permission, resulting in an empty or incomplete subscription.
- The `requestNotificationPermission` method returned an incomplete subscription object that was passed to SuprSend without validation.
- The VAPID key was not configured correctly, preventing the browser from generating a valid subscription.

**How to fix it:**
- Before sending the web push subscription to SuprSend, validate that both `auth` and `p256dh` values are non-empty strings. Only send the subscription object if both keys are present and populated.
- Ensure the SuprSend Javascript SDK is correctly initialized with the VAPID key from your SuprSend dashboard (**Vendors → Web Push → VAPID Keys**) before requesting push permission.
- Call `requestNotificationPermission` only on a user action (e.g., a button click) — not on page load — to ensure the browser prompt is shown and the subscription is generated correctly.
- Ensure your website is served over **HTTPS**, as web push subscriptions cannot be generated on non-secure origins.
- See [WebPush](/docs/js-webpush) for the full setup guide.

<span id="error-duplicate-object-key"></span>

### db_integrity_violation ERROR: duplicate key value violates unique constraint `"objects_ws_type_id_uniq_idx"`


**What does this mean:**
Two concurrent requests attempted to create the same object (identified by the same `object_type` and `id` pair) at the same time, causing a duplicate key conflict in the database. Objects in SuprSend are uniquely identified by the combination of `object_type` and `id` within a workspace. This error occurs only on the first creation of an object — if the object already exists, subsequent upsert calls update it without conflict.

This is most commonly caused by parallel or duplicate API calls being fired simultaneously for the same object before it has been created for the first time.

**How to fix it:**
- Check the API request where you're getting this error — you can see the exact request and response by clicking on the failed log in the **Request Logs** tab.
- Avoid sending concurrent requests for the same `object_type` and `id` pair during initial object creation. Ensure your integration serializes object creation calls or adds deduplication logic before calling the API.
- If you are retrying failed requests, use the [`idempotency_key`](/docs/logging) field to prevent duplicate processing of the same request.
- Once the object has been successfully created, subsequent upsert calls for the same `object_type` and `id` will update the object without triggering this error.
- See [Manage Objects](/docs/objects) for details on how object creation and updates work.
