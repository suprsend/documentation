SuprSend lets you send Slack notifications to channels and direct messages to users — in your own workspace, your customers' workspaces, or a fixed internal channel via webhook.

This integration does not support Slack modals, slash commands, shortcuts, or interactive dialogs.

## Choosing your implementation

### [Sending a message to your own workspace](/integrations/chat/slack/sending-an-internal-message)

Use this when you want to send notifications to channels or users in **your own** company's Slack workspace. You install a Slack app once, copy its bot token, and use it to send messages. No OAuth flow required.

Common use cases:
- Deployment alerts and release notifications to `#deployments`
- On-call and incident notifications to `#incidents` or an engineer's DM
- Anomaly detection and monitoring alerts from your infrastructure
- Internal ops notifications (new signups, payment failures, threshold breaches)

### [Sending a message to another workspace](/integrations/chat/slack/sending-a-message-to-channels)

Use this when you're building a SaaS product and want to send notifications into **your customers'** Slack workspaces. Each customer authorizes your app via an [OAuth V2 flow](https://api.slack.com/authentication/oauth-v2), giving you a bot token scoped to their workspace.

Common use cases:
- Task assignments and project updates delivered into a customer's workspace
- Weekly digests or activity summaries
- Real-time product event notifications (new comment, status change, approval request)
- Customer-facing alerting where each customer picks their own channel

### [Sending via incoming webhook](/integrations/chat/slack/sending-a-direct-message)

Use this when you need a quick, fixed-channel setup with no OAuth flow. An [incoming webhook](https://api.slack.com/messaging/webhooks) ties one URL to one channel — SuprSend posts to that URL and Slack delivers the message. Simplest option, but limited to one channel per webhook and cannot send DMs.

Common use cases:
- CI/CD status and deployment summaries to `#deployments`
- Error and anomaly alerts to a dedicated `#alerts` channel
- Product announcements or changelogs to `#announcements`
- Internal operational notifications where the destination channel never changes

## Prerequisites

Regardless of which guide you follow, you'll need:

- A [SuprSend account](https://app.suprsend.com)
- A Slack account with permission to create or manage [Slack apps](https://api.slack.com/apps)
- A Slack workspace — you can [create a free one](https://slack.com/get-started#/createnew) if needed

You do not need to create a new Slack app if you already have one. All three guides explain how to use an existing app.

## Storing Slack identity: pre-stored vs. inline

SuprSend gives you two ways to associate a Slack identity with a recipient.

**Pre-stored (recommended for most cases):** Call [`user.add_slack()`](https://docs.suprsend.com/docs/nodejs-sdk) to save the user's Slack identity to their profile in SuprSend. Any workflow triggered for that `distinct_id` will automatically route to the right place — no need to pass identity on every trigger.

**Inline (useful for one-off or dynamic sends):** Pass the Slack identity directly in the `$slack` field of the `recipients` array when [triggering a workflow](https://docs.suprsend.com/docs/workflow-trigger). Nothing is stored in SuprSend — the identity is resolved at trigger time.

```json
{
  "workflow": "_workflow_slug_",
  "recipients": [
    {
      "distinct_id": "user_001",
      "$slack": [
        {
          "email": "user@example.com",
          "access_token": "xoxb-XXXXXXXX"
        }
      ]
    }
  ],
  "data": { ... }
}
```

Use inline when you don't want to manage user profiles in SuprSend, or when the Slack identity isn't known until the moment of the trigger. Use pre-stored when the same user will receive multiple notifications over time — it avoids passing identity on every call.

## Order of precedence

When SuprSend resolves a Slack delivery target — whether from a stored profile or an inline payload — it uses the following priority order if more than one field is present:

| Priority | Field | Delivers to |
|----------|-------|-------------|
| 1 (highest) | `incoming_webhook.url` | The channel the webhook was configured for |
| 2 | `channel_id` + `access_token` | The specified Slack channel |
| 3 | `user_id` + `access_token` | A DM to the Slack user with that ID |
| 4 (lowest) | `email` + `access_token` | A DM after resolving the user by email |

Only include the fields relevant to your use case.
