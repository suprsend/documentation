---
title: "What is SuprSend?"
description: "SuprSend is API-first notification infrastructure for product, transactional and marketing messages across email, SMS, WhatsApp, push, inbox, Slack and Teams."
---

Your developers integrate SuprSend once. After that, every team works on the same users, templates and logs, from the dashboard, the API, the CLI or an AI agent, whichever suits the task:

- **Developers** [trigger workflows](/docs/trigger-workflow) from one API call or event, keep workflows and templates in Git, and promote them from staging to production.
- **Product teams** design workflows, templates and the preference center, and change copy or logic without a code deploy.
- **Growth and marketing teams** send [broadcasts](/docs/broadcast) to [SQL segments](/docs/segment-lists) (beta) and track results across channels in [analytics](/docs/analytics).
- **AI agents** can do any of this for any team. They build, test and debug notifications through the [MCP server](/reference/mcp-overview), set up in one step with the [SuprSend plugin](/reference/agent-plugin). Your role decides which tools they get. Your own production agents send notifications through the [Agent SDK](/reference/agent-sdk) (early access).

One API covers email, SMS, WhatsApp, mobile and web push, an In-App Inbox, Slack and Microsoft Teams. One [template](/docs/templates) holds the content for every channel, translated into each user's language. A [workflow](/docs/workflows) decides when and where each message goes: it can delay, batch or digest messages, branch on conditions in your data, send in each user's timezone, and send on all of a user's channels at once or one after another with [Smart Channel Routing](/docs/smart-delivery), which stops as soon as the user engages. Each channel sends through your own [providers](/docs/vendors), with [fallback](/docs/vendor-fallback) if one fails. Users choose which channels they want in their [preferences](/docs/user-preferences).

Product alerts, transactional messages and marketing campaigns share one user profile, one preference store and one log, so you don't need to build and manage separate tools for each.

1. **Trigger.** Your backend calls the [workflow API](/docs/trigger-workflow) or sends an [event](/docs/events). A workflow can also start when a user joins or leaves a [list](/docs/lists), and a [broadcast](/docs/broadcast) sends one message to a whole list.
2. **Preference check.** SuprSend skips users who opted out of the category or channel, before the workflow runs and again at each send step. See [preference evaluation](/docs/preference-evaluation).
3. **Workflow.** A [workflow](/docs/workflows) can [delay](/docs/delay), [batch](/docs/batch), [digest](/docs/digest) or [branch](/docs/branch). It can also [wait until](/docs/wait-until) something happens, send only in a [time window](/docs/time-window) in the user's timezone, [throttle](/docs/throttle) how often a user gets it, [fetch](/docs/fetch) data from your API or [invoke another workflow](/docs/invoke-workflow).
4. **Send step.** Each send step picks the channels, the [template](/docs/templates), the [translation](/docs/translations) and any [variant](/docs/template-variants) for the customer or condition. Content changes don't need a code deploy.
5. **Delivery.** SuprSend sends through your own [providers](/docs/vendors) (SuprSend calls them vendors), such as SendGrid, Amazon SES, Twilio, Firebase Cloud Messaging and APNs, and reroutes to a [fallback provider](/docs/vendor-fallback) if one fails.
6. **Logs.** Follow every request, workflow run and message in [logs](/docs/logging), including messages that were skipped and why. Track results in [analytics](/docs/analytics), or send status events to your systems with [webhooks](/docs/outbound-webhook).

Triggering a workflow is one request:

<CodeGroup>
```bash cURL
curl --request POST \
  --url https://hub.suprsend.com/trigger/ \
  --header "Authorization: Bearer __YOUR_API_KEY__" \
  --header 'Content-Type: application/json' \
  --data '{
    "workflow": "order-shipped-notification",
    "recipients": [{ "distinct_id": "user_1a2b3c" }],
    "data": { "order_id": "ORD-1234" }
  }'
```

```javascript Node.js
const { Suprsend, WorkflowTriggerRequest } = require("@suprsend/node-sdk");
const supr_client = new Suprsend("_workspace_key_", "_workspace_secret_");

const w1 = new WorkflowTriggerRequest({
  workflow: "order-shipped-notification",
  recipients: [{ distinct_id: "user_1a2b3c" }],
  data: { order_id: "ORD-1234" },
});

supr_client.workflows.trigger(w1).then((res) => console.log(res));
```

```python Python
from suprsend import Suprsend, WorkflowTriggerRequest

supr_client = Suprsend("_workspace_key_", "_workspace_secret_")

w1 = WorkflowTriggerRequest(body={
    "workflow": "order-shipped-notification",
    "recipients": [{"distinct_id": "user_1a2b3c"}],
    "data": {"order_id": "ORD-1234"},
})

res = supr_client.workflows.trigger(w1)
```
</CodeGroup>

## Core concepts

| Concept | What it is |
|---|---|
| **[Workflow](/docs/workflows)** | The logic of a notification: its trigger, steps such as delay, batch and branch, and delivery |
| **[Template](/docs/templates)** | The content for every channel, with variants, translations and versions |
| **[User](/docs/users)** | A recipient, with their channels, properties and preferences |
| **[List](/docs/lists)** | A set of users that you send broadcasts to or that starts a workflow |
| **[Tenant](/docs/tenants)** | One of your business customers, with its own branding, providers and preference defaults |
| **[Notification category](/docs/notification-category)** | A group of workflows that users set preferences on, such as Billing or Product updates |
| **[Workspace](/docs/workspaces)** | An isolated environment, such as staging or production, with its own keys, providers and data |

Every category sits under one of three roots. Each root has its own queue, so a large marketing send doesn't delay a password reset:

| Root category | What it covers |
|---|---|
| **System** | Essential messages users can't opt out of, such as one-time passwords, password resets and incident reports |
| **Transactional** | Responses to something a user did, such as payment confirmations, bookings, account updates and activity on their posts |
| **Promotional** | Messages that promote your product or bring users back, such as newsletters, announcements, product updates and deals |

Read [core concepts](/docs/core-concepts) for how these fit together.

## What you can build

- **Sign-in codes and security alerts** that users can't opt out of, sent by SMS or WhatsApp with a fallback provider.
- **Activity alerts that don't flood users.** [Batch](/docs/batch) many comments or updates into one message, or send a daily or weekly [digest](/docs/digest).
- **An in-app notification feed** with the [Inbox](/docs/inbox-overview), plus a [preference center](/docs/user-preferences) where users choose what they get.
- **Alerts for each of your business customers,** with their branding, their providers and their admin's defaults, using [tenants](/docs/tenants).
- **Campaigns and announcements** to a [list](/docs/lists) or [SQL segment](/docs/segment-lists) (beta), across email, push, WhatsApp and inbox.
- **Messages from your own AI agents,** which trigger your workflows through the [Agent SDK](/reference/agent-sdk) (early access).

## Built API-first

The objects you work with in the dashboard are API objects too:

- **Every core object has an API.** Users, objects, tenants, lists, workflows, templates, preferences and translations all have APIs. See the [API reference](/reference/overview) and the [Management API](/docs/management-api-overview).
- **Notifications as code.** Pull and push workflows and templates with the [CLI](/reference/cli-intro), keep them in Git, and [sync them](/reference/cli-sync) from staging to production. [Validate trigger payloads](/docs/validate-workflow-payload) with JSON Schema and [generate types](/docs/type-generation) from them.
- **Agent-ready by design.** The [MCP server](/reference/mcp-overview) exposes the same objects as tools, and agents act with your account's permissions.

All four ways of working use the same workflows, templates and users, so a change made in one shows up in the others:

| Where | What you do there |
|---|---|
| **Dashboard** | Build workflows and templates visually, send broadcasts, read logs and analytics |
| **API and SDKs** | Trigger workflows and sync users with the [REST API](/docs/developer/rest-api) or SDKs for [Python, Node.js, Java and Go](/docs/developer/sdk-overview). Add the [Inbox](/docs/inbox-overview), push and the preference center with [client SDKs](/docs/developer/sdk-overview) for JavaScript, React, React Native, Expo, Flutter, iOS and Android. |
| **CLI** | Pull and push workflows, templates, schemas and translations with the [CLI](/reference/cli-intro), keep them in Git, and run changes in CI |
| **AI** | Build, change or debug notifications from an AI client through the [MCP server](/reference/mcp-overview), or ask the [SuprSend Agent](/reference/agent) in the dashboard or the [Slack Agent](/reference/slack-agent) |

## For product and growth teams

Developers connect SuprSend once: they send users and events, and add a provider for each channel. After that, product, marketing and support teams can do this themselves, in the dashboard or through an AI agent:

- **Change content** in each channel's editor, and preview and test it before it goes live. See [templates](/docs/templates).
- **Send campaigns** to a [list](/docs/lists) as a [broadcast](/docs/broadcast), now or on a schedule.
- **Build audiences** with a SQL [segment](/docs/segment-lists) (beta) that the AI agent can write for you, or from a database sync, a CSV or Mixpanel.
- **Let users choose** what they receive with a hosted or embedded [preference center](/docs/user-preferences).
- **See results** by channel, workflow and category in [analytics](/docs/analytics).
- **Ask questions in plain English** about delivery and engagement through the [SuprSend Agent](/reference/agent) or the [Slack Agent](/reference/slack-agent).

## For products that serve other businesses

If your customers are companies, each one can get its own notification setup without separate code:

- **[Tenants](/docs/tenants)** hold each customer's branding, preferences and providers. They're available on the Enterprise plan and as an add-on for the Business plan.
- **[Sub-tenants](/docs/sub-tenants)** nest up to 5 levels, and a child inherits its parent's preferences, vendors, branding and properties.
- **[Tenant preferences](/docs/tenant-preference)** let a customer's admin set defaults for their own users.
- **[Tenant providers](/docs/tenant-vendor)** send through your customer's own email or SMS accounts.
- **[Objects](/docs/objects)** represent teams, projects or channels that people subscribe to, so you notify the group instead of listing every member.
- **[Slack](/docs/slack)** and **[Microsoft Teams](/docs/microsoft-teams)** messages can go into your customers' own workspaces.

To choose between workspaces, tenants and objects, see [multi-tenant modelling](/docs/guides/multi-tenant-modelling).

## For AI agents: MCP server, plugins and Agent SDK

Because SuprSend is API-first, an agent works with the same objects your code does, in three ways:

- **Agents that operate SuprSend.** The hosted [MCP server](/reference/mcp-overview) (beta) gives AI clients such as Claude, ChatGPT, Codex, Cursor, Gemini and VS Code access to your workspace. Agents can debug why a user didn't get a message, query analytics, and edit workflows and templates as drafts before publishing. They sign in with your SuprSend account and get the tools your role allows. The server also serves SuprSend's skills, covering workflow and template schemas, SQL rules and the docs, so agents work from the real spec instead of guessing. The [SuprSend plugin](/reference/agent-plugin) connects Claude, VS Code, GitHub Copilot CLI, Codex, Kiro and Cursor (Teams and Enterprise plans) in one install. Coding agents that run the SuprSend CLI can add the [`suprsend-cli` skill](/reference/agent-skill-cli).
- **Agents that send notifications.** The [Agent SDK](/reference/agent-sdk) (early access) gives production agents ready-made SuprSend tools, so they can trigger a workflow when they need to tell a person something.
- **Docs agents can read.** Every page is available as Markdown by adding `.md` to its URL. [llms.txt](https://docs.suprsend.com/llms.txt) indexes the docs, and [llms-full.txt](https://docs.suprsend.com/llms-full.txt) holds the whole site in one file.

AI features are optional. An admin can turn off the SuprSend Agent in **Account Settings → [AI & Agents](https://app.suprsend.com/en/account-settings/ai-agents)**, and the Slack Agent works only after an admin connects Slack.

Start with [Build with AI](/reference/build-with-ai).

## Security, reliability and deployment

| Question | Answer |
|---|---|
| Can we test without messaging real users? | Every account has Sandbox, Staging and Production [workspaces](/docs/workspaces), which share no data. [Test Mode](/docs/developer/test-mode) in staging sends only to your testers. |
| How do changes go live? | Workflow and template edits stay drafts until you commit them. Move them between workspaces with the dashboard, the [CLI](/reference/cli-sync) or the Management API. Check the [go-live checklist](/docs/go-live-checklist) before launch. |
| What if our code retries a request? | Pass an [idempotency key](/reference/idempotent-requests). SuprSend skips repeats of the same key for 24 hours. |
| What if a provider goes down? | [Provider fallback](/docs/vendor-fallback) reroutes messages to your next provider. |
| Is our data secure? | SuprSend is SOC 2 Type II and ISO 27001 compliant and supports GDPR, HIPAA and CPRA requirements. Each workspace has a data region, including the EU. See [security](/docs/security). |
| Who can see and change what? | Admins and members have [different permissions](/docs/managing-members). Members can't see user PII in production. [SAML SSO](/docs/authentication-methods) and [audit logs](/docs/audit-logs) are on the Enterprise plan. |
| Can we monitor it with our own tools? | Stream notification metrics to [OpenTelemetry](/docs/opentelemetry), [Datadog](/docs/datadog) or [New Relic](/docs/new-relic) on the Enterprise plan, or export data to [Amazon S3](/docs/amazon_s3_v2). |
| Where can SuprSend run? | SuprSend cloud, your own cloud (BYOC), or fully [self-hosted](/docs/self-hosted/introduction), with the same features as SuprSend cloud. Self-hosting needs an Enterprise license. |
| What does it cost? | See [plans and pricing](https://www.suprsend.com/pricing). This page notes when a feature needs the Enterprise plan. |
| We already send notifications. Can we move over gradually? | Yes. Start with a few key notifications and add the rest over time. See [migrating your existing notifications](/docs/migrating-your-existing-notifications). |

New to SuprSend? Start with the [Quick start](/docs/quick-start-guide).
