The Email channel in SuprSend gives you three ways to build templates — a drag-and-drop **Design Editor**, a raw **HTML Editor**, and a **Plain Text** editor. All three work together: HTML and plain text are always sent as a single multi-part email, and the Design and HTML editors share the same live preview.

This guide covers email settings, each editor mode, variables, preview, testing, and publishing.

<Note>
  You need an [email vendor](/docs/vendors) connected before notifications can be sent.
</Note>

---

## How the Email editor works

Before you write a single word, it helps to understand how the three editors relate to each other:

- **Design Editor** — drag-and-drop blocks (text, image, button, table, etc.) into a responsive layout. No code needed.
- **HTML Editor** — write or paste raw HTML directly. Full control, but email client compatibility is your responsibility.
- **Plain Text** — the text-only fallback sent alongside HTML in every email. You can auto-generate it from your HTML or write it yourself.

**You never choose between HTML and plain text** — both are always sent together as a multi-part MIME message. Plain text is the fallback for recipients who block HTML, and it improves deliverability.

**One important thing to know upfront:** The Design Editor and HTML Editor save independently. **Whichever tab is active when you click Commit is what gets published.** Always verify you're on the right tab before committing.

Editor-specific behaviour — blocks, HTML constraints, and plain-text fallback — is in **[Editors](#editors)** below.

## Email settings

Click the **pencil icon** above the editor to open Email Settings. Configure these before previewing or committing.

<Frame caption="Email Settings panel">
  <img src="/images/docs/templates-editor-email-settings.png" />
</Frame>

| Field | Required | Variables | What it is |
|---|---|---|---|
| **Subject** | Yes | Yes | Subject line shown in the inbox before open |
| **From Name** | Optional | Yes | Display name next to the sender address. Uses vendor defaults if blank. |
| **From Email** | Optional | Yes | Sender address — domain must be verified with your vendor |
| **Reply To** | Optional | Yes | Address that receives replies — use when replies should go to support or another mailbox |
| **CC** | Optional | Yes | Visible copy recipients — keep short for deliverability |
| **BCC** | Optional | Yes | Hidden copy recipients — avoid large BCC lists on bulk sends |
| **Add Multiple Tos** | Optional | Yes | Multiple primary recipients in one send |
| **Preheader** | Optional | No | Preview text shown next to or below the subject line |
| **Gmail Action Buttons** | Optional | Yes | JSON-LD for Gmail inbox actions (tracking, RSVP, etc.) |

**Subject line tips:** lead with the most relevant detail — order number, name, or required action. Aim for under ~60 characters so mobile clients don't truncate. Examples: `Your order {{order_id}} has shipped` · `{{first_name}}, your free trial ends tomorrow`

**Preheader:** treat it as a second subject line. Add context or urgency — don't repeat the subject. Aim for ~40–140 characters. If left blank, email clients may pull the first line of body text.

### Gmail Action Buttons

The **Email Markup JSON** field lets you add structured JSON-LD so Gmail can show actions directly in the inbox — track a delivery, RSVP to an event, rate a product — without opening the email.

Common use cases: order tracking, event RSVP, flight boarding passes, review requests, invoices.

```json
{
  "@context": "http://schema.org",
  "@type": "Order",
  "merchant": { "@type": "Organization", "name": "{{$brand.brand_name}}" },
  "orderNumber": "{{order_id}}",
  "potentialAction": {
    "@type": "TrackAction",
    "target": "{{{tracking_url}}}"
  }
}
```

<Warning>
  **Testing Gmail markup:** send from and to the same Gmail account (e.g. `you@gmail.com`) with any body content. Gmail allows markup testing when sender equals recipient without registration. For production, you must [register with Google](https://developers.google.com/gmail/markup/registering-with-google).
</Warning>

## Editors

In the product, the email body uses three tabs — **Design**, **HTML**, and **Plain text**. The sections below mirror that layout.

<Tabs>
  <Tab title="Design">

The drag-and-drop editor builds responsive emails by default — layouts adapt to mobile automatically without media queries.

<Frame caption="Design Editor with drag-and-drop blocks">
  <img src="/images/docs/templates-editor-email-body-general.png" />
</Frame>

The bottom toolbar has **Undo / Redo**, a **Preview** button (eye icon) for a full rendered preview, and a **Desktop / Mobile** toggle. The right sidebar has five panels: **Content** (drag blocks), **Blocks** (saved reusable rows), **Body** (global defaults), **Images** (free stock photos), and **Uploads** (your own images, hosted by SuprSend across all templates).

### Step 1 — Set Body defaults first

Before adding content, open the **Body** panel in the right sidebar. These are the global defaults that apply to every block unless you override them per block.

<Frame caption="Body panel — General settings">
  <img src="/images/docs/templates-editor-email-body-general.png" />
</Frame>

- **Content Width** — default is 600px, the standard for email. Change only if you have a specific reason.
- **Font Family** — web-safe fonts render reliably everywhere: Arial, Helvetica, Georgia, Times New Roman, Verdana, Tahoma. Google Fonts and custom fonts may fall back to system defaults in Outlook and Gmail.
- **Text Colour / Background Colour** — set brand defaults here so you don't repeat them on every block.
- **Link Colour / Underline** — global link styling.

<Frame caption="Body panel — Link settings">
  <img src="/images/docs/templates-editor-email-body-links.png" />
</Frame>

### Step 2 — Build your layout with rows and columns

Emails are structured as **rows** containing **columns**. Drag the **Columns** block to add a row with your preferred layout (1-col, 2-col, 3-col, or asymmetric).

<Frame caption="Column layout presets">
  <img src="/images/docs/templates-editor-email-columns-layout.png" />
</Frame>

Each row has: background colour, background image, display condition, and device-specific overrides (Desktop/Mobile tabs). Use the row header icons to delete, duplicate, or save as a reusable block. Each column has its own background, padding, and border — drag edges to resize.

### Step 3 — Add content blocks

Drag blocks from the **Content** panel into your rows:

**Heading** — section titles. Renders as h1–h4 depending on font size. Supports bold, italic, colour, and alignment.

**Paragraph** — body text. Supports bold, italic, underline, links, lists, and Merge Tags. Supports Handlebars variables inline.

**Button** — CTA button. Set the URL (supports variables; use triple braces in Handlebars when the URL must stay unescaped). Configure background colour, text colour, and border radius. **Width** is auto by default — turn auto off for a fixed pixel width for consistent sizing across clients. For tenant-branded buttons, use the **Tenant** block instead.

**Image** — add by upload, public URL, or from the Images panel (free stock photos). The Image URL field supports variables (e.g., `{{product_image_url}}`). Always set **Alt Text** — it can be static or dynamic (`{{product_name}}`). Alt text shows when images are blocked and helps accessibility.

**Divider** — horizontal separator. Configure colour, thickness, width percentage, and padding.

**HTML** — raw HTML block for custom code. Supports Handlebars variables inside the HTML. Useful for custom tables, embedded widgets, or code from external tools.

**Table** — data table for order line items, pricing breakdowns, or comparison grids. Cell contents support variables.

**Menu** — horizontal navigation links for headers or footers. Configure labels, URLs, separator character, font, and alignment.

**Tenant** — pre-built branded header, footer, or button that auto-renders each tenant's logo, colours, and links. See [Tenant branding](#tenant-branding) below.

### Merge Tags — repeating rows for arrays

Merge Tags let you associate a row with an array variable so the row repeats for each item at send time. This is how you build order line items, product lists, or notification digests.

1. Declare an array in the Variables panel (Input Payload section).
2. Click a row — an array association icon appears in the bottom-left.
3. Select your array. The row turns green.
4. Inside that row, use Merge Tags or Handlebars paths to reference array item properties (for example product name and price fields).

Merge Tags work on **rows and columns** — the entire row repeats per array item. Don't associate both a row and a column inside it with the same array.

<Note>
  Merge Tags only appear in the toolbar when variables are defined in the Variables panel.
</Note>

### Display conditions — show or hide blocks dynamically

Show or hide any row or block based on runtime data — for example, show a "Pro" badge only for premium users, or a tenant-specific banner.

1. Select the row or block.
2. Expand **Display Condition** in the settings panel.
3. Set **Property**, **Operator**, and **Value**. Combine with **+ AND** or **+ OR**.

<Frame caption="Display Conditions">
  <img src="/images/docs/templates-editor-email-display-conditions-modal.png" />
</Frame>

Supported operators include equality, inequality, and comparisons — the same set shown in the **Display Condition** UI (for example `==`, `!=`, and numeric comparisons).

### Saved blocks

Save any row as a reusable block — click the **save** icon in the row header, name it, and it appears in the **Blocks** panel across all templates. Saved blocks work at the **row level only** (not individual columns or blocks). They're a copy-on-insert — editing the saved block later doesn't update templates that already use it.

### Tenant branding

The **Tenant** block auto-renders a branded header, footer, or button using the tenant's profile (logo, colours, address). Select a tenant in the Variables panel to preview with their branding.

For custom control beyond the Tenant block, use `$brand` variables directly — for example logo, primary and secondary colours, brand name, address, and the hosted preference URL for unsubscribes. Use the paths documented under [Handlebars](/docs/handlebars-helpers) and the **Variables** panel (for example `$brand.logo`, `$brand.primary_color`, `$brand.$hosted_preference_url`).

<Warning>
  Email clients strip many HTML and CSS features. Key constraints to know:

  - **Gmail** — strips `style` in head (partially), `position`, `float`, `form` elements
  - **Outlook** — uses Word's rendering engine. No `div` layouts, `max-width`, `float`, or `border-radius`. Use `table` for everything.
  - **Yahoo** — strips `style`, rewrites class names
  - **Apple Mail** — most permissive (supports `style`, media queries, web fonts)
  - **All clients** — no JavaScript, no `form`, no external fonts (except Apple Mail)

  Check support at [Can I Email](https://www.caniemail.com/) and [Campaign Monitor CSS Guide](https://www.campaignmonitor.com/css/).
</Warning>

You can paste compiled output from MJML, React Email, Maizzle, or any other email toolchain. See [Tips for building HTML emails](#tips-for-building-html-emails) for specific workflows.

**Auto mode** — leave blank and SuprSend auto-generates plain text from your HTML on every commit.

**Custom mode** — click **Fetch from HTML** to pull the current HTML as a starting point, then edit. Once you manually edit the plain text, auto-generation stops for this template.

Write plain text so the message makes sense without any layout — lead with the action and include full URLs (don't rely on click tracking or button styling).

Plain text is best for: sales outreach, OTP and verification codes, internal alerts — anywhere design doesn't matter and deliverability does.

## Personalise with variables

Variables in email use [Handlebars](/docs/handlebars-helpers) syntax — `{{variable_name}}` for regular values, `{{{variable}}}` for URLs that contain `&`, `?`, or `=` to avoid HTML-escaping.

**In the Design Editor** — use the **Merge Tags** button in the text toolbar to insert variables from a dropdown. Or type `{{` in any text field for auto-suggestions. Variables work in text blocks, button URLs, image URLs, alt text, and HTML blocks.

**In the HTML Editor** — write Handlebars directly in the HTML source. Variables render in the live preview.

Set up your variable data in the **Variables panel** (`{}` tab in the left sidebar) before using them. See [The Variables panel](/docs/templates#the-variables-panel) for details on Input Payload, Recipient, Tenant, and Actor.

<Warning>
  If a variable cannot be rendered at send time (missing or mismatched data), SuprSend skips that notification for the affected user. Other channels in the same template group are still sent.
</Warning>

## Preview and test

Use the **eye icon** in the bottom toolbar for a full preview. Toggle **Desktop / Mobile** to check responsive behaviour in the Design Editor.

Click **Test** (top-right) to send a real email to a real address. This uses the **live version** — commit your changes before testing. See [Testing a Template](/docs/templates#test) for the full guide.

## Publish

Click **Commit** to publish. The commit snapshots the active editor's content, plain text, and all Email Settings.

<Warning>
  **Commit publishes the active editor only.** Design Editor and HTML Editor save independently. **Whichever tab is active when you click Commit is what gets published.** Switch to the tab you intend to publish before committing. If Plain Text is blank, it's auto-generated from HTML at commit time.
</Warning>

## Tips for building HTML emails

If you're pasting HTML into the HTML Editor rather than using the drag-and-drop editor, here are the common starting points:

**From a screenshot or PDF** — use an LLM with image input: ask for responsive HTML email with inline CSS and table layout. Attach the image or describe the layout, request variables as placeholders, then replace with Handlebars in the HTML tab.

**From Figma** — use [Emailify](https://emailify.io) to export Figma frames to responsive HTML email, or spec frames in Figma and build in [MJML](https://mjml.io/try-it-live). The [Builder.io Figma plugin](https://www.builder.io/blog/figma-to-html) also outputs HTML — add inline styles manually for email client compatibility.

**From an email toolchain** — compile from [MJML](https://mjml.io), [Maizzle](https://maizzle.com), [Foundation for Emails](https://get.foundation/emails.html), or [Litmus](https://litmus.com/email-builder) and paste the output into the HTML tab. Then wire `{{ }}` Handlebars variables.

**From a received email** — in Gmail, go to **Show original** → download the `.eml` → open in an editor and copy the HTML. Strip tracking pixels, keep structure, add variables, and paste into the HTML tab.

**Migrating from another ESP** — export HTML from Mailchimp, SendGrid, HubSpot, or similar. Map merge tags to Handlebars: `*|FNAME|*` → `{{first_name}}`. Map field names to your trigger payload paths.

**With React Email** — run `npm create email@latest`, build in JSX, export with `npx react-email export`, paste the output HTML into the HTML tab, and replace literals with Handlebars variables.

**Design Editor then HTML tweaks** — build in the Design Editor first, then copy the generated HTML, make your pixel-level adjustments in a code editor, and paste into the HTML tab. Remember: verify the active tab before committing.

## Best practices

- **Subject + preheader work together** — aim for ~50–60 characters in the subject and ~85–100 in the preheader. The preheader should add context or urgency, not repeat the subject.
- **One primary CTA** — one main button in brand colour; put secondary actions as text links. Label with specific verbs (`Track order`, `View invoice`) not `Click here` or `Learn more`.
- **Keep HTML under ~102 KB** — Gmail clips larger emails. Use inline CSS, table-based layout, and host images externally with alt text.
- **Use `{{$brand.*}}` for tenant branding** — keep logo and colours in tenant config; reserve the event payload for order, booking, and user-specific data.
- **Don't mix promotional content into transactional emails** — it changes consent requirements and how spam filters and users treat the message.
- **Always include a visible URL under verification buttons** — some clients strip buttons and security tools rewrite links. A plain-text URL is the fallback.
- **Use plain text seriously** — auto-generation is convenient but custom plain text that mirrors your email's intent improves deliverability and reads well in all clients.

## FAQ

  <Accordion title="Which fonts work reliably across email clients?">
    Web-safe fonts that render everywhere: Arial, Helvetica, Georgia, Times New Roman, Verdana, Tahoma, Courier New. Google Fonts and custom fonts may fall back to system defaults in Outlook and many webmail clients. Apple Mail is the most permissive. Contact support if you need a specific custom font uploaded.
  </Accordion>

  <Accordion title="Design Editor or HTML — which gets committed?">
    Whichever tab is **active when you click Commit**. They save independently. Always verify you're on the right tab before committing.
  </Accordion>

  <Accordion title="What's the difference between the three editors?">
    **Design Editor** — visual drag-and-drop with blocks, rows, Merge Tags for arrays, and display conditions. **HTML Editor** — full control with pasted or hand-written HTML and Handlebars. **Plain Text** — the text fallback of the MIME message, always sent with HTML, either auto-generated or customised.
  </Accordion>

  <Accordion title="What happens if Plain Text is blank?">
    SuprSend auto-generates it from the HTML on every commit. Click **Fetch from HTML** in the Plain Text tab to preview what it looks like. Once you edit plain text manually, auto-generation stops for this template.
  </Accordion>

  <Accordion title="How do Merge Tags work with arrays?">
    Associate a row with an array variable — the row repeats for each item. Inside the row, variables reference array item properties (e.g. `{{product_name}}`). Don't associate both a row and a column inside it with the same array — it won't work correctly.
  </Accordion>

  <Accordion title="Can I use variables in image URLs and alt text?">
    Yes. The Image URL field supports variables like `{{product_image_url}}`. Alt text also supports variables — use `{{product_name}}` for dynamic alt or a static string for fixed descriptions.
  </Accordion>

  <Accordion title="Why does my email look different in Gmail vs Outlook?">
    Each client has different CSS support. Gmail strips `<style>` blocks; Outlook uses Word's rendering engine (no border-radius, max-width, or div layouts). Use inline styles, table-based layouts, and web-safe fonts. Check [Can I Email](https://www.caniemail.com/) for specifics.
  </Accordion>

  <Accordion title="How do I test on mobile before publishing?">
    In the Design Editor, use the **Desktop / Mobile** toggle and the **Preview** (eye icon) control. For HTML you paste yourself, test on a real device or use a service that renders email HTML across clients — the editor does not simulate every client.
  </Accordion>

  <Accordion title="How do I add an unsubscribe link?">
    Use the **Tenant** block or the `{{$brand.$hosted_preference_url}}` variable — this is the hosted preference and unsubscribe URL for the tenant. You can also link to your own preference centre if you host one.
  </Accordion>

  <Accordion title="Can I use Handlebars inside the HTML block in the Design Editor?">
    Yes. The HTML content block in the Design Editor supports Handlebars variables — write them directly in the HTML source inside the block.
  </Accordion>

  <Accordion title="How do Saved Blocks work?">
    Save any row as a reusable block from the row header. Available in the **Blocks** panel across all templates. They're a copy-on-insert — editing the saved block doesn't update templates that already use it. Saved blocks work at the row level only, not individual columns or content blocks.
  </Accordion>

  <Accordion title="What happens if a variable is missing or has the wrong value at send time?">
    SuprSend skips that notification for the affected user. Other channels in the same template group are still sent.
  </Accordion>

  <Accordion title="Can I use this channel alongside other channels in the same workflow?">
    Yes. Email is one channel in a template group — add SMS, push, and others. Each channel renders independently.
  </Accordion>

  <Accordion title="How do I pass variable values when triggering the workflow?">
    Put data in the workflow trigger payload or event properties so paths match your Handlebars (e.g. `{{order_id}}`). Configure sample data in the **Variables panel**. See [The Variables panel](/docs/templates#the-variables-panel) and your SDK docs.
  </Accordion>
</AccordionGroup>
