This page documents the **Email** channel in the SuprSend template editor: **Email settings** (subject, from, preheader, Gmail markup), the **Design**, **HTML**, and **Plain Text** editors, **Handlebars** variables, preview, test, and commit. Use it when you are building or editing an email template in the dashboard.

**Who this is for:** engineers and operators who configure templates and connect them to workflows — not end recipients.

## Build your layout

The email editor has three modes — **Design Editor** (drag-and-drop), **HTML Editor** (raw code), and **Plain Text** (text part of the MIME message). **Plain Text** is always sent alongside HTML — you don't choose between them; you can auto-generate the text part or write your own.

Use the **tabs below** to switch between documentation for each editor. In the product, switch **Design** / **HTML** / **Plain Text** the same way before you **Commit**.

## Email settings (fields)

Click the **pencil icon** above the editor to open Email Settings before previewing or committing. You need an [email vendor](/docs/vendors) connected before notifications can be sent.

</Frame>

| Field | Required | Variables | What it is | Example / notes |
| --- | --- | --- | --- | --- |
| **Subject** | Yes | Yes | Subject line in the inbox before open | `Your order {{order_id}} has shipped` · `{{first_name}}, your free trial ends tomorrow` |
| **From Name** | Optional | Yes | Display name next to the sender address | Product or team name; [vendor defaults](/docs/vendors) if blank |
| **From Email** | Optional | Yes | Sender address (domain must be verified with your vendor) | `notifications@yourdomain.com` |
| **Reply To** | Optional | Yes | Address that receives **Reply** | Use when replies should go to support or another mailbox |
| **CC** | Optional | Yes | Visible copy recipients | Keep short for deliverability |
| **BCC** | Optional | Yes | Hidden copy recipients | Archival or discreet copies; avoid large BCC lists on bulk sends |
| **Add Multiple Tos** | Optional | Yes | Multiple primary recipients in one send when enabled | Each address must be valid for your vendor |
| **Preheader** | Optional | No | Preview text next to or below the subject | ~40–140 characters; if blank, clients may pull the first body line |
| **Gmail Action Buttons** | Optional | Yes | JSON-LD for Gmail inbox actions (tracking, RSVP, etc.) | See [Gmail Action Buttons](#gmail-action-buttons) |

**Subject line tips:** lead with the most relevant detail (order number, name, or required action). Aim for **under ~60 characters** so mobile clients don’t truncate heavily.

**Preheader:** treat it as a **second subject line** — add context or urgency, not a repeat of the subject.

### Gmail Action Buttons

Structured JSON in **Email Markup JSON** lets Gmail show actions (confirm, track, RSVP, etc.) in the inbox.

**Common use cases:**

- **Order tracking** — delivery status with tracking link
- **Event RSVP** — Yes / No / Maybe in the inbox
- **Flight boarding pass** — flight details, departure, arrival
- **Review request** — star rating in the inbox
- **Invoice / receipt** — line items and total

```json
{
  "@context": "http://schema.org",
  "@type": "Order",
  "merchant": { "@type": "Organization", "name": "{{$brand.brand_name}}" },
  "orderNumber": "{{order_id}}",
  "potentialAction": {
    "@type": "TrackAction",
    "target": "{{{tracking_url}}}"
  }
}
```

<Warning>
  **Testing markup:** set the From and To addresses to the **same Gmail account** (e.g., send from and to `you@gmail.com`) with any body content. Gmail allows markup testing when sender = recipient without registration. For production use, you must [register with Google](https://developers.google.com/gmail/markup/registering-with-google).
</Warning>

## Content blocks

Drag blocks from the **Content** panel into a row. Click any block to see its settings.

### Heading

For section titles. Renders as h1, h2, h3, or h4 depending on the font size you set. Use the rich toolbar for bold, italic, colour, and alignment.

### Paragraph

Body text. Rich toolbar for bold, italic, underline, links, lists, and merge tags. Supports Handlebars variables inline.

### Button

CTA button. Set the URL (supports variables like `{{{action_url}}}`), background colour, text colour, border radius (for rounded corners). **Width** is auto by default — turn auto off and set a fixed pixel width for consistent sizing across clients. If you want tenant-branded buttons, use the **Tenant** block instead.

### Image

Three ways to add: upload directly, paste a public URL, or browse the **Images** panel (free stock photos). The Image URL field supports variables (e.g., `{{product_image_url}}`). Always set **Alt Text** — it can be static ("Product image") or dynamic (`{{product_name}}`). Alt text shows when images are blocked and helps accessibility.

### Divider

Horizontal line separator. Configure colour, thickness, width percentage, and padding.

### HTML (content block)

Raw HTML block for custom code. Supports Handlebars variables inside the HTML. Useful for custom tables, embedded widgets, or code from external tools.

### Table

Data table for order line items, pricing breakdowns, comparison grids. Cell contents support variables.

### Menu

Horizontal navigation links (header or footer). Configure labels, URLs, separator character, font, and alignment.

### Tenant

Pre-built branded header, footer, or button that auto-renders each tenant's logo, colours, and links. See [Tenant branding](#tenant-branding).

## Rows and columns

Emails are structured as **rows** containing **columns**. Drag the **Columns** block to add a row with your preferred layout (1-col, 2-col, 3-col, asymmetric).

<Frame caption="Column layout presets">
  <img src="/images/docs/templates-editor-email-columns-layout.png" />
</Frame>

Each row has: background colour, background image, display condition, and device-specific overrides (Desktop/Mobile tabs). Use the row header icons to delete, duplicate, or save as a reusable block.

Each column has: its own background, padding, and border. Drag column edges to resize. Add or remove columns with the **+** and **delete** icons.

## Merge Tags (dynamic lists)

Merge Tags let you associate a row with an array variable — the row repeats for each item at send time. This is how you build order line items, product lists, or batched notification digests.

1. Declare an array in the Variables panel (Input Payload).
2. Click a row — an array association icon appears in the bottom-left.
3. Select your array. The row turns green.
4. Inside that row, use Merge Tags or <code>{'{{'}</code> to insert array item variables (e.g., <code>{'{{product_name}}'}</code>, <code>{'{{price}}'}</code>).

Merge Tags work on **rows and columns** — the entire row repeats for each array item. Don't associate both a row and a column inside it with the same array, or it won't work correctly.

<Note>
  Merge Tags only appear in the toolbar when variables are defined in the Variables panel.
</Note>

## Display conditions

Show or hide any row or block based on runtime data — For example, show a "Pro" badge only for premium users, or a tenant-specific banner.

1. Select the row or block.
2. Expand **Display Condition** in the settings panel.
3. Set **Property**, **Operator**, and **Value**. Combine with **+ AND** or **+ OR**.

<Frame caption="Display Conditions">
  <img src="/images/docs/templates-editor-email-display-conditions-modal.png" />

## Saved blocks

Save any row as a reusable block — click the **save** icon in the row header, name it, and it appears in the **Blocks** panel for all templates. Saved blocks work at the **row level only** (not individual columns or blocks).

Saved blocks are a copy-on-insert — editing the saved block later doesn't update templates that already use it.

## Personalise with variables

Variables in email use [Handlebars](/docs/handlebars-helpers) syntax — `{{variable_name}}` for regular values, `{{{variable}}}` for URLs with special characters.

**In the Design Editor** — use the **Merge Tags** button in the text toolbar to insert variables from a dropdown. Or type `{{` in any text field for auto-suggestions. Variables work in text blocks, button URLs, image URLs, alt text, and HTML blocks.

**In the HTML Editor** — write Handlebars directly in the HTML source. Variables render in the live preview.

Set up your variable data in the **Variables panel** (`{}` tab in the left sidebar) before using them. See [The Variables panel](/docs/templates#the-variables-panel) for details on Input Payload, Recipient, Tenant, and Actor.

<Warning>
  If a variable cannot be rendered at send time (missing or mismatched data), SuprSend skips that notification for the affected user. Other channels in the same template group are still sent.
</Warning>

## Other ways to build this template

These options are not tied to a single editor tab — use them whenever you need faster or more maintainable HTML than hand-coding from scratch.

### Start from a screenshot (screenshot → HTML)

You have a PDF, a screenshot of a competitor's email, a Zeplin export, or a Figma mockup. Open it in any LLM that accepts image input (Claude, GPT-4o) and ask it to recreate the layout as responsive HTML email using inline CSS. This is the fastest path from a visual reference to working code. Works best for layout — always review the output for broken spacing on mobile.

### Figma → responsive email HTML

Design your email layout in Figma with exact spacing, colours, and typography. Then use one of these tools to convert:

- **[Emailify](https://emailify.io)** — Figma plugin that exports directly to responsive HTML email. The most polished Figma-to-email tool available.
- **[Builder.io Figma plugin](https://www.builder.io/blog/figma-to-html)** — converts Figma frames to HTML/CSS, then you manually apply inline styles for email compatibility.
- **Manual MJML route** — export Figma frame dimensions and spacing as a spec, then write the email in [MJML](https://mjml.io/) which compiles to email-safe responsive HTML. Use the [MJML online editor](https://mjml.io/try-it-live) to iterate live.

### Use a framework instead of writing raw HTML

Raw HTML email is notoriously fragile. These frameworks generate compatible code automatically:

- **[MJML](https://mjml.io)** — XML-like syntax compiles to responsive, inbox-tested HTML. The community standard. Install via `npm install mjml` or use the online editor. Then paste the compiled output into SuprSend's HTML editor.
- **[Maizzle](https://maizzle.com)** — Tailwind CSS for email. Write utility classes, Maizzle inlines everything and strips unused styles. Best for teams already using Tailwind.
- **[Foundation for Emails (Inky)](https://get.foundation/emails.html)** — HTML templating language by Zurb that compiles to table-based responsive email HTML.
- **[Litmus email builder](https://litmus.com/email-builder)** — drag-and-drop editor that exports clean, tested HTML. Useful if you don't want to touch code.

### View source from a real email you like

This is the most underused technique. In Gmail: open the email → three-dot menu top right → "Show original" → "Download original". Open the `.eml` file in VS Code or any text editor. The raw HTML is inside. Copy it, strip tracking pixels (anything with `src` pointing to a tracking domain), replace content with your own variables, and paste into SuprSend's HTML editor. This gives you battle-tested responsive HTML for free.

### Convert an existing email template from another ESP

If you're migrating from Mailchimp, SendGrid, HubSpot, or any other platform, you almost certainly have working HTML templates already. Export them as HTML (every ESP has an export option), paste them into SuprSend's HTML editor, and replace the ESP's merge tag syntax with Handlebars: <code>{'*|FNAME|*'}</code> → <code>{'{{first_name}}'}</code>, <code>{'{{ subscriber.first_name }}'}</code> → <code>{'{{first_name}}'}</code>. The HTML rendering is identical — only the variable syntax changes.

### Use React Email to build and export

[React Email](https://react.email/) lets you write email templates as React components, preview them live in a browser with hot reload, and export them as HTML. Ideal for teams with frontend engineers who already know React. Install with `npm create email@latest`, build your template as JSX, run `npx react-email export`, and paste the HTML output into SuprSend. The component library includes pre-built blocks (buttons, dividers, headings) styled for inbox compatibility.

### Steal the plain-text technique for deliverability

Many teams focus entirely on HTML and ignore the plain-text editor. ISPs and spam filters check that both versions exist and are consistent. A plain-text version also renders perfectly in every environment without any HTML compatibility worries. After finishing your HTML template, switch to the Plain Text tab and write a stripped-down version — no markup, just the essential message and a bare URL. This alone can improve inbox placement rates.

### Use SuprSend's drag-and-drop blocks + export for minor HTML edits

Design your email in the Drag & Drop editor first. When you're happy with the layout, copy the generated HTML and open it in VS Code or any code editor for fine-grained adjustments — custom fonts via `@import`, specific padding values the editor doesn't expose, or inserting a third-party tracking pixel. Then paste the edited HTML into the HTML editor tab. This hybrid approach gives you the speed of the visual editor plus the control of code.

## Best practices

- **Write the subject last** — Once you've written the body you know the one thing worth surfacing in the inbox.
- **Use preheader text as a second subject line, not a repeat of it** — Complement the subject with extra context or urgency.
- **One CTA per email** — Secondary links compete with the main action — pick a single primary goal.
- **Inline CSS only in HTML templates** — Most email clients strip `<style>` blocks — put critical styles inline.

  <Accordion title="Which fonts work reliably across email clients?">
    Web-safe fonts that render everywhere: Arial, Helvetica, Georgia, Times New Roman, Verdana, Tahoma, Courier New. Google Fonts and custom fonts may fall back to system defaults in Outlook and many webmail clients. Apple Mail is the most permissive. If you need a specific custom font, contact support to get it uploaded.
  </Accordion>

  <Accordion title="Design Editor or HTML — which gets committed?">
    Whichever tab is **active when you click Commit**. They save independently. Always verify you're on the right tab before committing.
  </Accordion>

  <Accordion title="What's the difference between the three editors?">
    **Drag & Drop** — visual layout with blocks, rows, merge tags for arrays, and display conditions. **HTML Editor** — full control with pasted or hand-written HTML and Handlebars. **Plain Text** — the text part of the MIME message; always sent with HTML, either auto-generated from HTML or customised.
  </Accordion>

  <Accordion title="What happens if Plain Text is blank?">
    SuprSend auto-generates it from the HTML on every commit. Click **Fetch from HTML** to preview what it looks like. Once you edit the plain text manually, auto-generation stops.
  </Accordion>

  <Accordion title="How do Merge Tags work with arrays?">
    Associate a row with an array variable — the row repeats for each item. Inside the row, variables refer to array item properties (e.g., `{{product_name}}`). This works on rows and columns. Don't associate both a row and a column inside it with the same array.
  </Accordion>

  <Accordion title="Can I use variables in image URLs and alt text?">
    Yes. The Image URL field supports variables like `{{product_image_url}}`. Alt text also supports variables — use `{{product_name}}` for dynamic alt text or a static string for fixed descriptions.
  </Accordion>

  <Accordion title="Why does my email look different in Gmail vs Outlook?">
    Each email client has different CSS support. Gmail strips `<style>` blocks; Outlook uses Word's rendering engine (no border-radius, max-width, div layouts). Use inline styles, table-based layouts, and web-safe fonts. Check [Can I Email](https://www.caniemail.com/) for specifics.
  </Accordion>

  <Accordion title="How do I test on mobile before publishing?">
    In the Drag & Drop editor, use the **Desktop / Mobile** toggle and the **Preview** (eye) control. For HTML you paste yourself, use a real device or a service that renders email HTML — the HTML editor does not simulate every client.
  </Accordion>

  <Accordion title="How do I add an unsubscribe link?">
    Use the **Tenant** block or `$brand` variables. `{{$brand.$hosted_preference_url}}` is the hosted preference/unsubscribe URL for the tenant. You can also link to your own preference centre if you host one.
  </Accordion>

  <Accordion title="Can I use Handlebars inside the HTML block?">
    Yes. The HTML content block in the Design Editor supports Handlebars variables — write them directly in the HTML source.
  </Accordion>

  <Accordion title="How do Saved Blocks work?">
    Save any row as a reusable block from the row header. Saved blocks are available in the **Blocks** panel across all templates. They're a copy-on-insert — editing the original doesn't update existing templates. Saved blocks work at the row level only, not individual columns or content blocks.
  </Accordion>

  <Accordion title="What happens if a variable is missing or has the wrong value at send time?">
    SuprSend skips that notification for the affected user. Other channels in the same template group are still sent.
  </Accordion>

  <Accordion title="Can I use this channel alongside other channels in the same workflow?">
    Yes. Email is one channel in a template group — add SMS, push, and others; each channel renders independently.
  </Accordion>

  <Accordion title="How do I pass variable values when triggering the workflow?">
    Put data in the workflow trigger payload or event properties so paths match your Handlebars (e.g. `{{order_id}}`). Configure sample data in the **Variables panel**. See [The Variables panel](/docs/templates#the-variables-panel) and your SDK docs.
  </Accordion>
