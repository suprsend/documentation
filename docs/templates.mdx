## What is a Template?

A **template** is where you author the notification content that gets sent to your users. It is a named, versioned container that holds channel content — Email, SMS, WhatsApp, Push, In-App Inbox, Slack, MS Teams — all in one place.

You reference a template in a [workflow](/docs/workflows) by its **slug**. When the workflow runs, SuprSend picks the right variant for the recipient, renders the content with live data, and routes it across the appropriate channels.

Templates are **decoupled from your code**. Once integrated, your engineers never need to touch notification content again — product and marketing teams can create, update, and ship changes entirely from the dashboard, CLI, or via MCP.

---

## Key Concepts

Before building templates, it helps to understand three things that shape how they work:

### Channels live inside a template

A single template holds content for every channel you want to reach users on. If your _Order Shipped_ notification goes out over Email, SMS, and Push, all three are authored inside one template — not three separate ones. This keeps related content together and lets you manage a notification holistically.

### Everything is version-controlled

Every time you commit a template, SuprSend creates an immutable, numbered version (V1, V2, V3…). The most recently committed version is always the **live** version — the one actually used when a notification sends. Previous versions are retained indefinitely in history for auditing and reference.

You always edit in an isolated working copy. Your changes are invisible to live traffic until you explicitly commit.

### Variants control what gets sent to whom

Within a template, you can have multiple **variants** of the same channel content — each targeting a different locale, tenant, or runtime condition. SuprSend evaluates all variants at send time and delivers the first one that matches. If none match, it falls back to the `default` variant. This is how you build multi-lingual, multi-tenant, or A/B-tested notifications without maintaining separate templates.

---

## Template Lifecycle

```
Create template → Add channels → Author content → Commit → Live
                                       ↑                      |
                                  Edit again  ←──── (new edit session)
```

A template starts as a **Draft** — it has no committed version yet. The first commit makes it **Live**. After that, every edit session starts from the current live version, and changes only take effect on the next commit.

## Creating a Template

Go to **Templates** in the left sidebar and click **+ New Template**.

Give it a **Name** and a **Slug**. The name is a display label you can change anytime. The slug is the identifier used in your workflow and API calls — it is set at creation and **cannot be changed afterwards**, so pick something stable and descriptive (e.g. `order-shipped`, `password-reset`).

After creation, you select which **channels** to enable: Android Push, Email, In-App Inbox, iOS Push, MS Teams, Slack, SMS, Web Push, or WhatsApp. SuprSend creates a `default` variant for each channel you pick, and you land in the editor ready to start.

You can add or remove channels at any time later without touching any code.

<Tip>
  If you create a template from inside a Workflow node, it is automatically linked to that workflow and its slug is pre-filled. This is the fastest path when building a new notification from scratch.
</Tip>

## Authoring Content

### The editor

The template editor has a **Variants** panel on the left and the **channel editor** on the right. The channel editor is where you write content — visually for Email, or with form fields for SMS, Push, and the other channels.

Every channel in the Variants panel expands to show its variants. Click a variant to open it as a tab in the editor. You can have multiple variants open at once, making it easy to work across locales or configurations side by side.

### Static vs dynamic content

Template content can be static (fixed for all users) or dynamic (personalised per recipient). For dynamic content, SuprSend uses **Handlebars** syntax for Email, SMS, WhatsApp, and Inbox, and **JSONNET** for Slack and MS Teams.

The most important habit: before writing any `{{variable}}` in your template, define it in the **Variables panel** (`{}` in the left sidebar). This gives you autocomplete, a consistent preview, and catches missing data before you commit.

### Variable sources

Variables in your template can come from four places:

**1. Your trigger payload** — data you send when you trigger the workflow, or data shaped by workflow nodes (transforms, batch/digest, webhook fetch).

| What you're referencing | Handlebars | JSONNET |
| --- | --- | --- |
| Top-level key | `{{name}}` | `data.name` |
| Nested key | `{{order.address.city}}` | `data.order.address.city` |
| Array item | `{{items.[0].name}}` | `data.items[0].name` |
| URL with special characters | `{{{tracking_url}}}` | `data.tracking_url` |
| Key with spaces or capitals | `{{[First Name]}}` | `data['First Name']` |
| Batched event count | `{{$batched_events_count}}` | `data['$batched_events_count']` |

**2. Recipient properties** — pulled automatically from the user's profile. No need to pass these in your payload.

| Handlebars | JSONNET |
| --- | --- |
| `{{$recipient.name}}` | `data['$recipient'].name` |
| `{{$actor.name}}` | `data['$actor'].name` |

**3. Tenant properties** — available when the notification is sent in a [tenant](/docs/tenants) context. Used for white-labelled notifications.

| Handlebars | JSONNET |
| --- | --- |
| `{{$brand.brand_name}}` | `data['$brand'].brand_name` |
| `{{$brand.properties.address}}` | `data['$brand'].properties.address` |

**4. Batching data** — when events are batched in a workflow, SuprSend injects `$batched_events` (array of all events) and `$batched_events_count` automatically.

For conditionals, loops, and helpers, see [Handlebars Helpers](/docs/handlebars-helpers).

### The Variables panel

The **Variables `{}`** panel in the left sidebar is your development environment for variables. It has two modes:

- **Input Payload** — define sample values that stand in for real trigger data. Enable batching here to simulate how batched content renders.
- **Recipient** — search for a real user by name. Their live profile properties load as the variable context, letting you preview exactly what that user would receive.

Variables defined here power the live preview in the editor, the Test feature, and autocomplete while you type `{{`.

## Variants

Variants are the mechanism for sending different content to different recipients from the same template. Each variant has its own channel content, a locale, an optional tenant scope, and optional conditions.

### How SuprSend picks a variant

At send time, SuprSend evaluates variants from top to bottom in the order they appear in the panel. The **first variant whose conditions all match** is the one that gets sent. If no variant matches, it falls back to the `default` variant.

This means **order matters**. Put your most specific variants at the top.

### What you can target

| Target | How |
| --- | --- |
| **Language / locale** | Set the `Locale` field on the variant. SuprSend matches it against the recipient's `$preferred_language` profile property. |
| **Tenant** | Set the `Tenant` field. The variant only matches when the notification is sent for that specific tenant. |
| **Any runtime property** | Add **Conditions** — rules that evaluate recipient properties, tenant properties, or workflow data against a value using operators like `=`, `!=`, `contains`, `<`, `>`. |

Multiple conditions on a variant use AND logic — all must match. Click **+ OR** to add a condition group; the variant matches if any group passes.

### Creating a variant

In edit mode, click the **Add Variant** button in the top bar. Set:
- **Channels** — which channels this variant covers (one variant can span multiple channels)
- **ID** — a unique name for this variant within the template (e.g. `hindi`, `enterprise-tier`, `experiment-b`)
- **Locale** — defaults to `en`
- **Tenant** — optional; restricts matching to a specific tenant
- **Conditions** — optional; additional matching rules

The `default` variant is created automatically for every channel and cannot be deleted. It is always the fallback.

### Managing variants

You can **edit**, **duplicate**, or **delete** variants from their context menu in the Variants panel. Use duplicate when creating a new locale or experiment variant that shares structure with an existing one.

<Warning>
Deleted variants and their content cannot be recovered.
</Warning>

## Committing

When your content is ready, click **Commit** in the top-right corner of the editor.

Committing does two things simultaneously:
1. Snapshots the current state of every channel and variant into a new numbered version.
2. Makes that version live — all notifications triggered from this point forward use the new content.

There is no separate "publish" step. Commit is publish.

While you are in edit mode, the live version is unaffected. Recipients continue receiving the previous committed version until you commit. The yellow banner at the top of the editor reminds you of this: _"You're in edit mode. Changes you make here won't affect published content."_

Clicking **Exit** discards your uncommitted changes and returns the template to its last committed state.

---

## Version History

Every commit is recorded in the **History** panel (clock icon in the left sidebar). You get:

- A chronological list of versions — V1, V2, V3 — with author and timestamp. The current live version is marked **Live**.
- A **diff view** for each version showing which channel–variant combinations were `Updated` or `Unchanged` in that commit.
- A **Preview** of the full rendered content for any historical version.

History is read-only. You cannot roll back to a previous version directly, but you can use a historical version as reference while editing.

---

## Testing Before You Commit

Use the **Test** button (top-right, available in both view and edit mode) to send a real notification to a real device before committing.

1. Enter a user's `distinct_id` and search — SuprSend loads their profile and shows available channels.
2. Select the channels to test.
3. Click **Trigger Test using mock data** — the notification sends immediately using values from your Variables panel.
4. Check [Logs](/docs/logging) for delivery status.

<Warning>
Every variable in the template must have a value in the Variables panel before testing. Missing values cause that channel's notification to fail rendering and not send.
</Warning>

## Managing Templates

### Metadata

Every template has a **Name**, **Slug**, **Description**, and **Tags**. Access these via the **ⓘ icon** next to the template name in the editor breadcrumb, or from **⋮ → Edit Metadata**.

- Use **Description** to document what event triggers this template, who owns it, and any business rules. Future teammates (and AI agents) will thank you.
- Use **Tags** to group related templates on the listing page and in the [Templates API](/reference/get-template-list).

The slug is the only immutable field — it cannot be changed after creation.

### Cloning

Click **Clone Template** (duplicate icon in the top bar) to copy a template — all its channels, variants, conditions, and content. The clone is created as a Draft with a new name and slug.

Cloning works within a workspace and across workspaces. Use cross-workspace cloning to promote a staging template to production.

### Importing content

In edit mode, the **Import Content** button (arrow icon in the top bar) lets you import an HTML file directly into the current channel editor. Use this when your design team delivers polished email HTML from an external tool.

### Deleting

Go to **⋮ → Delete** in the editor top bar to delete a template.

<Warning>
Deletion is permanent. Before deleting, check the **Linked Workflow** column on the listing page and remove the template from any active workflows to prevent send failures.
</Warning>

### Managing via CLI

You can also manage templates entirely from the command line — list, pull, edit locally, push, and commit without opening the dashboard. See [CLI Template Commands](/reference/cli-template-overview) for the full reference.

## Finding Templates

The **Templates listing page** shows all templates in the workspace with their status, linked workflow, enabled channels, last updated timestamp, and last used timestamp.

Use the **Search** bar to find templates by name, slug, or description.

Use **Filters and Sort** to narrow by channel, status (`Live` / `Draft`), linked workflow slug, or tags, and to sort by last updated or last used.

The **Approvals tab** shows templates with commits pending review. When approvals are enabled in your workspace, team members without publish rights can commit changes that land here for a reviewer to approve before going live.

---

## Using Templates in Workflows

Templates are referenced in workflows by their **slug**. You can copy the slug from the listing page (clipboard icon) or from the ⓘ metadata popup in the editor.

When you create a template directly from a Workflow's template node, the link is set automatically — no manual configuration needed.

For API-triggered workflows, pass the slug in your payload. See [Trigger Workflow](/docs/trigger-workflow).
