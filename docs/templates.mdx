## What is a template?

A **template** is where you author all the notification content your users receive — subject lines, body copy, images, buttons — across every channel. Every notification in SuprSend is powered by a template.

Two things about SuprSend templates are worth understanding upfront, because they shape everything else:

**One template covers all your channels.** You don't maintain a separate email template, a separate SMS template, and a separate push template for the same notification. You add all the channels you need to a single template. When the workflow fires, SuprSend sends across every enabled channel in one shot. Adding or dropping a channel is a change inside the template — your workflow and code don't need to change.

**Templates are decoupled from workflow logic.** Your workflow decides *when* to send and *to whom*. Your template decides *what to say*. Content can be updated, redesigned, or translated at any time without touching the workflow. The same template can also be reused across multiple workflows.

The **Templates** page in the sidebar is your workspace-level view of all templates. For each template it shows:

## Building a template

### Create

There are two ways to create a template:

- **From the Templates page** — click **+ New Template** in the sidebar. You'll link it to a workflow later.
- **From a workflow node** — click **Create Template** inside a delivery node on the canvas. The name and slug are pre-filled from the workflow and node names, and the template is automatically linked. Use this when you're building a workflow and need a new template at the same time.

The creation modal asks for two things:

- **Name** — a display label you can change anytime.
- **Slug** — the permanent identifier your workflow uses to reference this template. It's auto-derived from the name. Verify it before saving because **the slug cannot be changed after creation**. Renaming the template later has no effect on the slug, so existing workflow references keep working.

<Frame caption="New Template — name and slug">
  <img src="/images/docs/templates-create-modal-new.png" />
</Frame>

Then select the channels this template sends on: Email, SMS, WhatsApp, Android Push, iOS Push, Web Push, In-App Inbox, Slack, or MS Teams. You can add or remove channels at any time from inside the editor.

### The editor

After creation, the editor opens on your first channel. Each channel has its own editor and a live device preview on the right. Switch between channels using the tabs at the top.

**View mode vs. Edit mode.** The editor opens in View mode — read-only, showing the last published version. Click **Edit** to open a draft. Content auto-saves as you type. Live traffic is never affected until you commit. If you close the editor mid-edit, your draft is preserved exactly where you left it.

Each channel has a dedicated editor suited to its format:

| Channel | Editor |
|---|---|
| Email | Drag-and-drop designer, raw HTML, or plain text |
| SMS | Single text field; carrier approval template ID field for India |
| WhatsApp | Header, body, footer, and buttons |
| Android Push | Title, body, image, and action buttons |
| iOS Push | Title, body, image, and action URL |
| Web Push | Title, body, image, and buttons |
| In-App Inbox | Cards with avatar, action buttons, and expiry |
| Slack | Plain text or Block Kit (JSONNET) |
| MS Teams | Markdown or Adaptive Card (JSONNET) |

### Variables — personalising content

Variables are placeholders like `{{order_id}}` or `{{$recipient.name}}` that SuprSend replaces with real values at send time. Before using them in your content, set up sample data in the **Variables panel** — the `{}` tab in the left sidebar. This panel drives the editor's auto-complete dropdown, the live preview, and the test flow.

<Frame caption="Variables panel — Input Payload, Recipient, Tenant, Actor, and batching">
  <img src="/images/docs/templates-variables-panel-new.png" />
</Frame>

#### Data sources

**Input Payload** — the event data your workflow trigger sends. Paste a sample JSON that reflects your actual trigger payload:

```json
{
  "order_id": "ORD-1234",
  "order": {
    "total": "$49.99",
    "address": { "city": "San Francisco" }
  },
  "tracking_url": "https://yourapp.com/track/ORD-1234"
}
```

If the template is linked to a workflow, click **Pre-fill from last workflow run** to load real data from the most recent trigger automatically.

Toggle **Enable batching** to bring `$batched_events` and `$batched_events_count` into your context — required to preview [batched](/docs/batch) or [digest](/docs/digest) notification content.

**Recipient** — search for a user by name, email, or distinct ID. Their profile loads into `$recipient`. Selecting a recipient also renders the live preview with their actual data so you see exactly what they'd receive.

| Variable | Value |
|---|---|
| `{{$recipient.name}}` | User's name |
| `{{$recipient.email}}` | User's email |
| `{{$recipient.phone}}` | User's phone number |
| `{{$recipient.distinct_id}}` | User's unique ID |
| `{{$recipient.<property>}}` | Any custom property on their profile |

> Use `$recipient` in templates, not `$user`. Both refer to the same data, but `$recipient` is the standard.

**Tenant** — select a [tenant](/docs/tenants) to load its branding into `$brand`. Selecting a tenant renders the preview with that brand's actual data.

| Variable | Value |
|---|---|
| `{{$brand.brand_name}}` | Tenant's display name |
| `{{$brand.logo}}` | Tenant's logo URL |
| `{{$brand.primary_color}}` | Brand colour (used in email tenant blocks) |
| `{{$brand.properties.<key>}}` | Any custom tenant property (address, support email, etc.) |
| `{{$brand.$hosted_preference_url}}` | Hosted unsubscribe / preference page link |
| `{{$brand.$embedded_preference_url}}` | Embedded preference widget link |

> Use `$brand` for tenant data — not `$tenant`. The `$tenant` namespace is not exposed to templates.

**Actor** — the person who *performed* the action that triggered the notification, distinct from the recipient who *receives* it. In "Alice commented on Bob's post," Alice is `$actor` and Bob is `$recipient`. If no actor is passed in the trigger, these variables render as empty strings.

| Variable | Value |
|---|---|
| `{{$actor.name}}` | Actor's name |
| `{{$actor.email}}` | Actor's email |

#### Writing variables in content

Type `{{` in any text field — a dropdown appears showing all available variables grouped by source. Variables with missing values are highlighted in red so you catch gaps before going live.

| Syntax | When to use |
|---|---|
| `{{variable}}` | Default — HTML-escaped. Use for most values. |
| `{{{variable}}}` | Triple braces — no HTML-escaping. Use for URLs or values containing `&`, `?`, `=`, `'` to prevent broken links. |
| `{{object.key}}` | Dot notation for nested JSON — e.g. `{{order.address.city}}` |
| `{{array.[0].name}}` | Array index access — e.g. first item in a list |
| `{{[first name]}}` | Square brackets for keys with spaces, capitals, or special characters |

In the Email design editor, use the **Merge Tags** button in the toolbar rather than typing `{{`.

### Templating languages

SuprSend uses two templating languages depending on the channel.

#### Handlebars (Email, SMS, Push, WhatsApp, In-App Inbox)

Beyond simple variable substitution, Handlebars supports a set of helpers for logic and formatting:

**`{{default variable "fallback"}}`** — renders a fallback value when the variable is null, empty, or undefined.

**`{{#compare var '==' value}} … {{else}} … {{/compare}}`** — conditional blocks. Supported operators: `==`, `===`, `!=`, `!==`, `>`, `>=`, `<`, `<=`. For the Email design editor, use Display Conditions on blocks instead of `compare` in text.

**`{{#each array_object}} … {{/each}}`** — loops over an array. Use `{{this}}` or `{{key}}` inside the block to access each item's properties.

**`{{datetime-format variable "format" "timezone"}}`** — formats a date or timestamp. Format strings follow [Moment.js conventions](https://momentjs.com/docs/#/displaying/format/). The timezone parameter is optional. Use `"now"` as the variable to get today's date at render time.

**`{{jsonStringify variable}}`** — converts a JSON object or array to a string. Useful for the In-App Inbox's custom JSON field.

**`{{lowercase "string"}}`** / **`{{uppercase "string"}}`** — case conversion helpers.

**`{{t "key" var=value}}`** — translation key lookup for multi-lingual templates (see [Localisation](#localisation) below).

> **Important:** `{{#compare}}` and `{{#each}}` are **not supported in SMS in India (carrier approval) and WhatsApp templates** because those channels require pre-approved static content. Helpers work normally for SMS sent via Twilio, MessageBird, or other vendors without this approval requirement.

Full reference: [Handlebars helpers](/docs/handlebars-helpers)

#### JSONNET (Slack, MS Teams)

JSONNET is a data templating language used to build dynamic Slack Block Kit and MS Teams Adaptive Card payloads. All trigger payload data, recipient, actor, and tenant properties are available under the `data` object.

Key differences from Handlebars: **`{{variable}}` syntax does not work in JSONNET.** Use `data.key` instead.

| Variable | JSONNET syntax |
|---|---|
| Trigger payload key | `data.order_id` |
| Nested object | `data.order.address.city` |
| Key with special characters | `data['$recipient'].name` |
| Array element | `data.items[0].product_name` |
| Recipient property | `data['$recipient'].name` |
| Tenant property | `data['$brand'].brand_name` |
| Batched event count | `data['$batched_events_count']` |
| Batched event item | `data['$batched_events'][0].title` |

Use JSONNET `for` loops to iterate over arrays, `if/then/else` for conditional content, and `+` or `%` for string formatting. Design in the [Slack Block Kit Builder](https://app.slack.com/block-kit-builder/) first, then adapt the JSON into JSONNET by replacing hardcoded values with `data.key` references.

Full reference: [JSONNET templates](/docs/jsonnet-templates)

### Variants — different content for different audiences

Every template starts with a **default** variant. Add more when different people should get different content from the **same template slug** — e.g. per [tenant](/docs/tenants), per segment in your trigger data, or A/B copy ([Analytics](/docs/analytics)). Each variant has **conditions**; SuprSend picks the **first match** in list order, otherwise the default.

If only **translated text** changes between languages (same layout everywhere), use **[Localisation](#localisation)** (translation files). Use **variants** when structure, assets, or channels genuinely differ per audience or locale.

**Everything else** — creating variants, condition operators, soft vs hard rules, ordering, testing with **Template Group**, duplicate/delete, and disabling a channel — is covered step by step in **[Template Variants](/docs/template-variants)**.

### Localisation

SuprSend supports two ways to send notifications in each recipient’s language. Pick based on **what changes** between locales — text only, or the whole layout.

| Approach | Use when | How it works |
|---|---|---|
| **[Translations](#translations-recommended)** *(recommended)* | Copy changes per language; **structure stays the same** (same blocks, images, buttons). | Translation keys (`{{t "key"}}`) in the template; strings live in JSON files per language. |
| **[Language variants](#language-variants)** | **Structure differs** per language (different images, layout, buttons, RTL, or channel mix). | One [variant](/docs/template-variants) per language with a locale condition; full content per variant. |

For most products, **Translations** is simpler and easier to maintain. Use **language variants** only when you truly need different designs or content per locale.

#### Setting the user's language

Both approaches need the recipient’s locale on their profile (`$locale`). Set it from any backend SDK or the API — for example [Python](/docs/python-create-user-profile#set-preferred-language), [Node.js](/docs/node-create-user-profile#set-preferred-language), or [REST](/reference/edit-user-profile). Use standard locale codes: `en`, `es`, `fr`, `hi`, `de`, `pt-BR`, etc.

#### Translations (recommended)

Keep **one template** and store copy in **per-language JSON files** (uploaded in the dashboard, via [CLI](/reference/cli-translation-overview), or [API](/reference/add-translation)). In the template, use the `t` helper instead of hard-coded sentences.

**How it works**

1. Upload translation files — one JSON per language (`en.json`, `es.json`, …).
2. Reference keys in the template:

<CodeGroup>
```handlebars Handlebars (Email, SMS, Push, Inbox)
{{t "order_shipped" order_id=order_id}}
```
```jsonnet JSONNET (Slack, MS Teams)
t("order_shipped", {order_id: data.order_id})
```
</CodeGroup>

3. At send time, SuprSend resolves the key using the user’s locale and interpolates variables.

**Example**

```json en.json
{
  "order_shipped": "Your order #{{order_id}} has been shipped!",
  "track_button": "Track Order"
}
```

```json es.json
{
  "order_shipped": "Tu pedido #{{order_id}} ha sido enviado!",
  "track_button": "Rastrear Pedido"
}
```

Template (same for every language):

```handlebars
{{t "order_shipped" order_id=order_id}}
```

**Fallback order:** exact locale (e.g. `es-MX`) → language (`es`) → default (`en`). Keep an `en.json` (or your chosen default) as the final fallback.

**When Translations fit best**

- Layout, assets, and CTAs are identical across languages — only wording changes.
- You want one template and many languages without duplicating editor content.
- You want translators or automation to own JSON files (CLI/API) instead of clicking through variants.

For pluralisation, namespaces, and operational detail, see **[Translations](/docs/translations)**.

#### Language variants

Use variants when **the message itself is different per locale** — not just translated text: e.g. RTL email, market-specific hero image, or a different button set.

**Create a language variant**

1. In the template editor, open **Variants** → **New Variant**.
2. Set **Locale** to the target language and a clear **ID** (e.g. `default-es`).
3. Author that locale’s content (use [Import](/docs/templates#import-content) to copy from the default, then adapt).
4. Commit.

At send time, SuprSend matches the recipient’s locale to a variant; if none match, the **default** variant is used.

**Tenant + language**

Combine locale with [tenant](/docs/tenants) when branding and language interact — e.g. locale `es` and tenant `acme`. Order variants so specific combinations sit **above** broader ones. Fallback order: tenant+locale → tenant+default locale → default tenant+locale → default.

You can still use `{{t "…"}}` **inside** a tenant variant so copy is translated while layout stays variant-specific.

<Tip>
  **Prompt for translators:** *Translate this notification into [language]. Channel: [email/SMS/push/WhatsApp]. Paste content. Keep every Handlebars variable path unchanged. Adapt tone and formats (dates, currency) for the locale. Respect segment/character limits.*
</Tip>

#### Which approach should I use?

<AccordionGroup>
  <Accordion title="Same layout everywhere — only strings change">
    Use **Translations** and `t` keys. One template, JSON files per language.
  </Accordion>
  <Accordion title="Different layout, images, or structure per language">
    Use **language variants** with a locale condition, or mix variants + `t` keys if only part of the copy is shared.
  </Accordion>
  <Accordion title="Many languages (5+) long term">
    Prefer **Translations** for maintainability unless you have a hard structural reason for variants.
  </Accordion>
</AccordionGroup>

### Commit

Click **Commit** in the top bar to publish your draft. The commit modal shows all pending changes across all variants and channels — you can **deselect specific variants** you're not ready to publish yet, so you can publish some variants while keeping others as work-in-progress. Add an optional description to note what changed.

<Frame caption="Commit — review pending changes per variant and channel before publishing">
  <img src="/images/docs/templates-commit-modal.png" />
</Frame>

Once committed, every workflow trigger immediately renders and sends the new content.

- **Drafts never affect live traffic.** Commit is the only action that changes what users receive. You can iterate freely without production impact.
- **Every commit creates a new version.** See [Version history](#version-history) below.
- **WhatsApp and SMS in India (carrier approval) require vendor approval.** Committing these channels puts the version into **Approval Pending** — it goes live only after the vendor approves. Each language variant is approved separately. If a fallback vendor is configured, each vendor requires its own approval.

---

### Version history

Every commit creates an immutable version of the template. Open the **History** tab (clock icon in the left panel) to see the full audit trail — who committed each version, when, and a per-channel diff showing exactly what changed in that version.

<Frame caption="Version history — timeline, authors, and per-channel diffs">
  <img src="/images/docs/templates-version-history-full.png" />
</Frame>

To roll back: click any previous version and select **Rollback**. It becomes the live version immediately. Newer versions are never deleted — you can always roll forward again.

## Testing

After committing, send a real notification to a real device to confirm everything works end-to-end. Click **Test** in the top-right corner of the editor.

> **Need a test user?** You need a user with at least one channel identity — email address, phone number, or device token. Create one from the [Users page](https://app.suprsend.com/users), via [API](/docs/users), or ask the AI copilot in the dashboard.

  </Tab>
  <Tab title="Template group">

**Single channel** — pick the channel, enter a recipient (email or distinct ID), optionally select a **Notification Category** (determines which vendor config is used — e.g. transactional vs. promotional SMS sends through different vendor credentials) and a **Tenant** (loads that tenant's `$brand` properties and selects the matching tenant variant), then click **Send Test**.

**Template Group** — switch to the Template Group tab, enter a recipient, select the channels to include, and send. This mode runs the full variant selection logic exactly as production does. Use this — not the single-variant test — to verify that your variant conditions, ordering, and tenant/locale fallbacks are working correctly.

After sending, go to **[Logs](/docs/logging)** to confirm delivery and see which variant was selected. If a variable was missing or a channel failed to render, the exact error appears there.

> WhatsApp and SMS in India (carrier approval) templates must be committed *and* vendor-approved before you can test them.

## Template actions

Everything you can do to a template from the editor or the listing page:

**Import content** — the **Import** button (arrow icon) in the editor toolbar copies content into the current draft from another variant in this template, or from any other template in your workspace. Preview content before importing. The most common use: creating a language variant — import the default English content, then translate in place. Import is a one-time copy; source and destination are fully independent afterwards.

<Frame caption="Import content — copy from another variant or template">
  <img src="/images/docs/templates-import-content-modal.png" />
</Frame>

**Clone** — copies the entire template (all channels, all variants, all content) to the same workspace or a different one. The standard way to promote templates from Staging to Production. The cloned template is independent — changes to one don't affect the other.

<Frame caption="Clone template to another workspace or duplicate within the same workspace">
  <img src="/images/docs/templates-clone-modal.png" />
</Frame>

**Edit metadata** — click the info icon next to the template name to edit Name, Description, and Tags. The Slug is immutable after creation.

**Archive** — removes the template from active use. Available from the overflow (three-dot) menu on the listing page. Archived templates cannot be recovered. Only archive what you're certain you no longer need.

**API and CLI** — manage templates programmatically via the [Template Management API](/reference/list-templates-v2) or [CLI](/reference/cli-template-overview). Useful for syncing templates across environments or automating template creation as part of a deployment pipeline.

## Template approval (WhatsApp and SMS)

WhatsApp and SMS in India (carrier approval) templates require external vendor approval before they can go live or be tested. When you commit one of these channels, the version enters **Approval Pending** status and is submitted to the vendor. You can track all pending approvals from the **Approvals tab** on the Templates listing page.

### WhatsApp approval

WhatsApp only approves message templates that are transactional or service-related. Templates that include promotional language, discount codes, re-engagement messaging, surveys, or cold-call language will be rejected. Review the content guidelines before submitting:

- Keep names clear and descriptive (e.g., `bus_ticket_details` not `template_014`)
- Avoid promotional language, upsells, or marketing content
- No floating variables (lines containing only a variable with no surrounding text)
- No spelling or grammatical errors
- Variables must use the correct format: `{{1}}`, `{{2}}`, etc. — two curly brackets on each side

Full guidelines: [WhatsApp approval guidelines](/docs/whatsapp-template#whatsapp-approval-guidelines)

### Carrier approval for SMS in India

The Telecom Regulatory Authority of India (TRAI) requires all commercial SMS sent in India to use pre-registered templates on the carrier approval platform. Templates are registered under one of four categories:

| Category | When to use |
|---|---|
| **Transactional** | OTPs for banking transactions only — restricted to banks and RBI-approved entities |
| **Service Implicit** | Messages triggered by a user action (order confirmation, delivery update, appointment reminder) — no explicit consent needed |
| **Service Explicit** | Service messages requiring verified user consent — must be linked to a consent template |
| **Promotional** | Marketing and promotional messages to opted-in users |

Key carrier approval rules (India SMS): the organisation name must appear in the template; variable length is capped at 30 characters; Trans/Service templates must contain at least one variable; double spaces are not allowed; the entire template cannot be a variable.

Full guidelines: [India SMS carrier approval guidelines](/docs/sms-template#india-sms-carrier-approval-guidelines)
