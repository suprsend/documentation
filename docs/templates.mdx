## Finding templates

Go to **Templates** in the left sidebar. The listing shows all templates in the workspace.

<Frame caption="Template listing page">
  <img src="/images/docs/templates-listing.png" />
</Frame>

| Column | Description |
|---|---|
| **Name / Slug** | Display name and slug. Click the clipboard icon to copy the slug. |
| **Status** | `Live` — at least one published version exists. `Draft` — no version published yet. |
| **Linked workflow** | Workflow this template is attached to, if any. |
| **Enabled channels** | Channels with content in this template. |
| **Last updated** | Timestamp and author of the most recent change. |
| **Last used** | Timestamp of the last notification sent using this template. |

Use the search bar to find by name, slug, or description. Use **Filters** to narrow by channel, status, linked workflow, or tags.

## Creating a template

Go to **Templates** and click **+ New Template**.

<Frame caption="Create template dialog">
  <img src="/images/docs/templates-create-dialog.png" />
</Frame>

**Name** — a human-readable display label. Can be changed at any time.

**Slug** — the unique identifier used in workflow nodes and API calls (e.g. `order-shipped`, `password-reset`). Auto-generated from the name at creation time.

> **The slug cannot be changed after creation.** Any workflow or API reference using the old slug will break if you recreate the template under a new one. Choose it carefully.

After creation, select one or more channels to enable: [Email](/docs/email-template), [SMS](/docs/sms-template), [WhatsApp](/docs/whatsapp-template), [Android Push](/docs/android-push-template), [iOS Push](/docs/ios-push-template), [Web Push](/docs/web-push-template), [In-App Inbox](/docs/in-app-inbox-template), [Slack](/docs/slack-template), [MS Teams](/docs/ms-teams-template). SuprSend creates a `default` variant for each selected channel and opens the editor.

<Frame caption="Channel selection">
  <img src="/images/docs/templates-channel-selection.png" />
</Frame>

You can add or remove channels at any time without touching code.

> **Creating from a workflow node:** If you create a template from inside a workflow's delivery node, the template is automatically linked to that workflow and its name and slug are pre-filled from the workflow and node names. This is the fastest path when building a new notification from scratch.

## Authoring content

### Static and dynamic content

Template content can be static (the same for all recipients) or dynamic (personalised per recipient). For dynamic content, define variables in the **Variables panel** before writing them in the template — this gives you autocomplete, a consistent live preview, and catches missing data before you publish.

SuprSend uses two templating languages depending on the channel:

- **[Handlebars](/docs/handlebars-helpers)** — Email, SMS, WhatsApp, In-App Inbox, Android Push, iOS Push, Web Push
- **[JSONNET](https://jsonnet.org/learning/tutorial.html)** — [Slack](/docs/slack-template), [MS Teams](/docs/ms-teams-template)

### The Variables panel

The Variables panel (left sidebar, `{}` icon) has three sections:

**Input Payload** — define sample values that simulate your trigger payload. These power the live preview and the Test flow. Toggle **Enable batching** to simulate batched event data — SuprSend computes `$batched_events` and `$batched_events_count` automatically. You can pre-fill this from the last workflow run on the linked workflow.

**Recipient** — search for a real user by name or email. Their live profile properties load as the variable context, so you preview exactly what that specific recipient would receive.

**Tenant** — select a tenant to load its properties into the preview context. Used when testing tenant-specific content.

Variables defined here are shared across all channels in the template group.

### Variable sources and syntax

Variables can come from four sources:

**1. Trigger payload** — data sent when the workflow is triggered.

| Value | Handlebars | JSONNET |
|---|---|---|
| Top-level key | `{{name}}` | `data.name` |
| Nested key | `{{order.address.city}}` | `data.order.address.city` |
| Array item | `{{items.[0].name}}` | `data.items[0].name` |
| URL or string with `&`, `<`, `>` | `{{{tracking_url}}}` | `data.tracking_url` |
| Key with spaces or capitals | `{{[First Name]}}` | `data['First Name']` |
| Batched event count | `{{$batched_events_count}}` | `data['$batched_events_count']` |

> **Triple braces `{{{...}}}`** output the value without HTML-escaping. Use them for URLs with query parameters, raw HTML, or any string where `&`, `<`, or `>` must be preserved literally. For plain text like names or order IDs, double braces are correct.

**2. Recipient properties** — pulled from the user's profile automatically.

| Handlebars | JSONNET |
|---|---|
| `{{$recipient.name}}` | `data['$recipient'].name` |
| `{{$user.name}}` | `data['$user'].name` |
| `{{$actor.name}}` | `data['$actor'].name` |

**3. Tenant properties** — available when a notification is sent in a [tenant](/docs/tenants) context.

| Handlebars | JSONNET |
|---|---|
| `{{$brand.brand_name}}` | `data['$brand'].brand_name` |
| `{{$brand.properties.address}}` | `data['$brand'].properties.address` |

**4. Batching data** — when events are [batched](/docs/batch) in a workflow, SuprSend injects `$batched_events` (array of all batched events) and `$batched_events_count` automatically.

For conditionals, loops, and helper functions, see [Handlebars Helpers](/docs/handlebars-helpers).

### JSONNET for Slack and MS Teams

Slack and MS Teams use JSONNET — a superset of JSON that adds variables, conditionals, and functions. Payload data is available under `data`.

```jsonnet
{
  text: "Order " + data.order_id + " has shipped to " + data['$recipient'].name + ".",
  blocks: [
    {
      type: "section",
      text: {
        type: "mrkdwn",
        text: "*Order " + data.order_id + "* has shipped.\nExpected: " + data.delivery_date
      }
    }
  ]
}
```

For the full JSONNET language reference, see [jsonnet.org](https://jsonnet.org/learning/tutorial.html). For Slack Block Kit structure, use [Slack's Block Kit Builder](https://app.slack.com/block-kit-builder).

## Publishing

Click **Publish Changes** in the top-right corner of the editor when your content is ready.

You'll be prompted for:
- **Version name** — auto-generated (V1, V2, V3…) but editable.
- **Version description** — optional, useful for changelogs and audit trails.

Publishing does two things at once: snapshots every channel and variant into a new numbered version, and makes that version live. All notifications triggered after this point use the new content.

**Editing never affects live traffic.** Editing always works on the draft version. The live version is unaffected until you publish. If you exit the editor without publishing, your draft changes are preserved — they are not discarded.

> **In-flight notifications are not affected by a new publish.** Any notification already queued at the moment you publish will complete using the previous version's content. Only notifications triggered after the publish use the new version.

### WhatsApp and SMS: approval before going live

WhatsApp and SMS ([DLT](/docs/dlt-guidelines)) templates require [vendor](/docs/vendors) approval before they can be sent. Publishing creates the version, but it enters **Approval Pending** state rather than going live immediately.

**How approval works:**

When a template is in Approval Pending state, an **Approve / Reject** button appears when you hover on that variant. Clicking it opens a modal:

1. Select whether the template has already been approved at the vendor portal, or needs to be uploaded for approval.
   - If already approved: enter the approved template ID and name from the vendor portal.
   - If not yet approved: the modal shows the template name and content to upload at the vendor portal.
2. Select **Approved** or **Rejected**.
   - If rejected: enter the rejection reason.
3. For [multi-lingual templates](/docs/multi-lingual-template), approval is handled at each language level — templates are uploaded and approved separately per language at the vendor end.
4. If a [fallback vendor](/docs/vendor-fallback) is configured, approval must be confirmed for each vendor.

The template goes live as soon as it is approved with the primary vendor.

## Version history and rollback

Click the **History** tab (clock icon) in the left panel to see every published version.

<Frame caption="Version history">
  <img src="/images/docs/templates-version-history.png" />
</Frame>

Each entry shows the version number, status (Live / Draft), author, timestamp, and a per-channel per-variant breakdown of what was **Updated** or **Unchanged** in that version.

**To roll back:** click any previous version, then click **Rollback**. A confirmation modal appears. Rolling back moves the live pointer to that version — newer versions are not deleted and can be re-activated.

> **WhatsApp and SMS:** Rollback is only available for versions published after the current template system was introduced. If the vendor auth of the active configuration differs from the rollback version, you'll see a warning that the template will re-enter approval state after rollback.

## Testing before you publish

The **Test** button (top-right corner) sends a real notification to a real device so you can verify rendering end-to-end before publishing. See [Testing a Template](/docs/testing-the-template) for the full guide.

> Every `{{variable}}` in the template must have a value in the Variables panel. A variable with no value causes that channel's notification to fail rendering — other channels are unaffected. Check [Logs](/docs/logging) for a rendering error on the specific channel if a test does not arrive.

## Managing templates

### Metadata

Every template has a **Name**, **Slug**, **Description**, and **Tags**. Access via the **ⓘ icon** next to the template name, or **⋮ → Edit Metadata**.

- **Description** — document what event triggers this template, who owns it, and any business rules.
- **Tags** — group related templates for filtering on the listing page.
- **Slug** — immutable after creation.

### Adding and removing channels

Open a template and click **+** next to the channel icons to add a new channel.

<Frame caption="Add channels to an existing template">
  <img src="/images/docs/templates-channel-picker.png" />
</Frame> Removing a channel deletes its content and all its variants permanently — this cannot be undone.

### Cloning within the workspace

Click **⋮ → Clone Template** to copy a template — all channels, variants, conditions, and content — as a new Draft with a new name and slug. Useful when creating a new template that shares structure with an existing one.

When cloning, you can also select **Create a copy** for individual linked workflow steps — this creates a new template from the same content with a `(copy)` suffix, useful for reminders or follow-up messages that share most of their content.

### Promoting to another workspace

From the template view, click **Promote** to clone the template to another workspace (e.g. from Staging to Production).

- Default target is **Production** (or **Staging** if you're already in Production).
- Target channels and template slug default to match the source — you can change these before promoting.

Promoting clones the template and all its variants. It does not affect the source workspace.

### Deleting

**⋮ → Delete** permanently removes the template and all its versions. This cannot be undone.

> Before deleting, check the **Linked Workflow** column on the listing page and remove the template from any active workflows to prevent send failures.

## Using templates in workflows

Templates are referenced in [workflows](/docs/workflows) by their slug.

- **Created from a workflow node** — slug is pre-filled and the template is automatically linked. The template can be changed later from the node using the **Change Template** option, which opens the full template list.
- **Linked manually** — enter the slug in the workflow's template node.
- **Existing template, different step** — use **Select Existing Template** and choose either "Use same template" (shared content) or "Create a copy" (independent content with minor differences).

To copy the slug, click the clipboard icon on the listing page or in the editor breadcrumb.

## Approvals workflow (for teams)

When template approvals are enabled in your workspace, team members without publish permission can author and draft changes — but cannot publish them directly. Their changes land in the **Approvals** tab for a reviewer to inspect.

<Frame caption="Approvals tab">
  <img src="/images/docs/templates-approvals-tab.png" />
</Frame>

- **Authors** draft and submit for review. Live traffic is unaffected.
- **Reviewers** (with publish permission) open the Approvals tab, inspect the diff, then **Approve** or **Reject**.
- **Approved** changes go live immediately.
- **Rejected** changes return to Draft. The author can revise and resubmit.

This gives teams a content governance gate — useful for regulated industries, multi-brand setups, or any team that separates content authorship from publishing.
