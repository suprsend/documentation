SuprSend provides comprehensive analytics and observability features for your notifications, enabling you to track user engagement, monitor workflow performance, and understand how your messaging is performing across channels and templates.

<Note>
  **📘 Analytics vs Logs:**

  This page covers **aggregated analytics** (metrics, trends, performance dashboards). For raw event-level logs and detailed debugging information, see the [Logs documentation](/docs/logging). Analytics are derived from logs but provide aggregated insights rather than individual event inspection.
</Note>

## Analytics overview

Analytics give you real-time insights into your notification system's performance at every level. Each analytics view highlights key metrics over your selected time range, helping you identify what's working, what needs improvement, and where to focus your optimization efforts.

The key capabilities include:

- **Real-time insights** → Trends update as messages go out. Track performance across channels and spot dips in engagement instantly.
- **Workflow-level comparisons** → Compare workflows, templates, channels, and categories side by side to spot underperformers and validate experiments.
- **Opt-out tracking** → See which channels/categories drive opt-outs so you can adjust before churn sets in.
- **Over-messaging detection** → Track average notifications per user, find patterns by category, and identify fatigue triggers to keep communications helpful—not noisy.
- **Granular filtering** → Multi-select filters for workflow, tenant, template, channel, category, and time range.
- **Centralized error tracking** → All API, workflow, and provider delivery errors in one place. Filter by tenant/workflow/template/channel, open the exact log, and debug in seconds.

## Key metrics

Analytics measure user interaction based on notification status. When using SuprSend's tracking, these status events are handled automatically based on channel capabilities and vendor callbacks.

### Metric definitions

Each metric is computed at the message level (one notification = one message) and aggregated for reporting. Here are the formal definitions:

#### Delivered

**Definition:** A notification is marked as "delivered" when the vendor confirms successful delivery to the user's device or inbox.

**Computation:**
- **Source:** Vendor webhook callbacks to SuprSend's tracking URL (`https://hub.suprsend.com/webhook/*`)
- **When emitted:** After vendor accepts the notification request and confirms delivery
- **Aggregation:** Count of unique messages with delivered status within the time window
- **Deduplication:** Each message is counted once, even if multiple delivery callbacks are received

**Channel-specific behavior:**
- **Email:** Delivery confirmed when email service provider (ESP) accepts the message
- **SMS:** Delivery confirmed when carrier confirms receipt
- **Push (Android/iOS/Web):** Delivery confirmed when push service (FCM/APNs) confirms delivery to device
- **Inbox:** Delivery confirmed when message is stored in user's inbox

#### Seen

**Definition:** A notification is marked as "seen" when the user views or opens it, as defined by channel-specific engagement signals.

**Computation:**
- **Source:** Vendor webhook callbacks or client-side tracking events
- **When emitted:** Varies by channel (see table below)
- **Aggregation:** Count of unique messages with seen status within the time window
- **Uniqueness:** One "seen" event per message per user

**Channel-specific behavior:**
- **Email:** Triggered when email client loads tracking pixel (opened)
- **WhatsApp:** Triggered when message is read (double blue check)
- **Push (Android/iOS/Web):** Triggered when notification is clicked/tapped
- **Inbox:** Triggered when message is marked as read or clicked

<Warning>
  **Email open tracking limitations:**

  Email "seen" metrics rely on tracking pixels. Some email clients (Apple Mail with Mail Privacy Protection, Gmail with image blocking) may not load tracking pixels, resulting in underreported seen rates. This is an industry-wide limitation, not a SuprSend issue.
</Warning>

#### Clicked

**Definition:** A notification is marked as "clicked" when the user interacts with a link, button, or actionable element within the notification.

**Computation:**
- **Source:** Click tracking URLs in notification content or client-side interaction events
- **When emitted:** When user clicks a tracked link or button
- **Aggregation:** Count of unique messages with at least one click within the time window
- **Uniqueness:** Multiple clicks on the same message are counted as one "clicked" event for the message

**Channel-specific behavior:**
- **Email:** Click tracking via URL parameters in email links
- **Push (Android/iOS/Web):** Click event when notification is tapped/clicked
- **Inbox:** Click event when user clicks links or buttons in inbox message
- **SMS/WhatsApp:** Not tracked (no clickable elements)

#### Opt-out

**Definition:** A user is marked as "opted out" when they unsubscribe from notifications via channel-specific opt-out mechanisms.

**Computation:**
- **Source:** User-initiated unsubscribe actions (clicking unsubscribe link, replying STOP, etc.)
- **When emitted:** Immediately upon opt-out action
- **Aggregation:** Count of unique users who opted out within the time window
- **Uniqueness:** One opt-out event per user per channel/category combination

**Channel-specific behavior:**
- **Email:** Unsubscribe link clicks or list-unsubscribe headers
- **SMS:** Reply with STOP, UNSUBSCRIBE, or similar keywords
- **Push:** User disables notifications in device settings (tracked separately)
- **Inbox:** User preference changes in preference center

### Average notifications per user

**Definition:** The mean number of notifications sent to each active user per day.

**Computation:**
- **Formula:** `Total notifications sent / Unique users who received notifications / Number of days`
- **Aggregation window:** Daily, then averaged over selected time range
- **Uniqueness:** Each notification is counted once, even if sent to multiple channels
- **User scope:** Only users who received at least one notification in the time window

### Channel performance percentages

**Definition:** Engagement rates calculated as percentages of delivered messages.

**Computation:**
- **Seen rate:** `(Messages with seen status / Messages with delivered status) × 100`
- **Click rate:** `(Messages with clicked status / Messages with delivered status) × 100`
- **Aggregation:** Calculated per channel, then aggregated over time window
- **Precision:** Percentages are rounded to 2 decimal places for display

| Channel     | Delivered | Seen | Clicked | Notes                                    |
| ----------- | --------- | ---- | ------- | ---------------------------------------- |

| SMS         | ✓         | -    | -       | Delivery only                             |
| WhatsApp    | ✓         | ✓    | -       | Seen = read                               |

## How analytics are computed

Understanding the data pipeline helps you interpret metrics accurately and trust the numbers you see.

### Data flow

Analytics are computed through the following pipeline:

1. **Event generation** → When a notification is sent, SuprSend generates a message event
2. **Vendor delivery** → Notification is sent to vendor (SendGrid, Twilio, FCM, etc.)
3. **Vendor callbacks** → Vendor sends webhook callbacks to SuprSend's tracking URL with delivery/engagement status
4. **Event processing** → SuprSend processes callbacks and updates message status
5. **Aggregation** → Events are aggregated into time windows (hourly, daily) for analytics display
6. **Dashboard display** → Aggregated metrics are displayed in real-time or near real-time

### Data freshness and aggregation

**Real-time vs delayed:**

- **Real-time updates:** Metrics update as vendor callbacks are received, typically within seconds to minutes of user engagement
- **Aggregation delay:** Time-series charts aggregate data into hourly or daily buckets. Recent data (last hour) may be incomplete
- **Eventual consistency:** Vendor callbacks may arrive out of order or with delays. Analytics reflect final state after all callbacks are processed

**Aggregation windows:**

- **Hourly:** Data aggregated into 1-hour buckets for time-series views
- **Daily:** Daily totals calculated at end of day (UTC)
- **Custom ranges:** Aggregated based on selected time range

**Deduplication:**

- Each message is counted once per metric, even if multiple status updates are received
- Late-arriving callbacks update historical data within the retention window
- Duplicate events from vendor retries are automatically deduplicated

**Backfills:**

- If vendor callbacks are delayed, metrics are updated retroactively when callbacks arrive
- Historical data may change slightly as late callbacks are processed
- **Data finality:** Analytics are considered final after 48 hours. Data older than 48 hours should not change, as vendor callback windows have closed

**Data freshness expectations:**

- **Real-time (0-1 hour):** Metrics may be incomplete as callbacks are still arriving. Expect up to 5-10% variance.
- **Near real-time (1-24 hours):** Most callbacks have arrived. Expect <2% variance from final numbers.
- **Final (48+ hours):** Data is stable and should not change.

<Note>
  **📘 Data accuracy:**

  Analytics reflect vendor-reported status. If a vendor fails to send callbacks or sends incorrect status, analytics will reflect that. Always verify vendor callback configuration is working correctly.
</Note>

### SuprSend dashboard

You can view analytics directly in the SuprSend dashboard:

1. Navigate to **Analytics** in your environment.
2. Use the tabs to switch between **Performance Overview** and **Workflow Level Breakdown**.
3. Apply filters at the top to narrow down your view by workflow, tenant, template, channel, category, or time range.

At the top of the Analytics page, you'll find:

- **Relative and absolute range filters** → Choose from preset time ranges (last 7 days, last 30 days) or set a custom date range.
- **Refresh icon** → Manually refresh data to see the latest updates.
- **Workflow and tenant filters** → Narrow down your view to specific workflows or tenants.

### Data export

Analytics data can be exported for deeper analysis:

- **Outbound webhooks** → Configure [outbound webhooks](/docs/outbound-webhook) to receive real-time analytics updates in your system.
- **Amazon S3 sync** → Set up [Amazon S3 sync](/docs/amazon_s3_v2) to export analytics data to your data warehouse for analysis with tools like Athena, Redshift, Snowflake, or ClickHouse.

## Performance Overview

The Performance Overview tab gives you a high-level view of your notification system's health and user engagement patterns.

### Channel performance

Compare delivery and engagement across channels to see where users are most responsive.

**How to read this chart:**

- Use the tabs above to switch between channels — the totals reflect overall delivery, seen, and click percentages for that channel.
- Clicking a tab updates the line chart below to show the time series trend for that specific channel.
- If any channel has tracking issues, a warning sign will appear next to it. Hover over it to understand and fix the warning.

This view helps you quickly identify which channels are driving the most engagement. For instance, if email shows a 45% seen rate while SMS shows 95% delivery, you might want to investigate why email engagement is lower or consider SMS for time-sensitive notifications.

### Average notifications per user

Track how often users receive notifications each day to catch over-messaging patterns early.

**How to read this chart:**

- The count reflects the average number of notifications a user receives per day.
- Bar + heatmap shows how users are distributed across different notification volume ranges — darker areas indicate more users in that range.
- If you notice darker areas higher on the y-axis, it means a segment of users is receiving a high volume of notifications. Consider drilling down by category or channel to identify what's contributing to this spike.

This metric is crucial for preventing notification fatigue. If you see users receiving 10+ notifications per day, they're likely to start ignoring or unsubscribing from your messages. Use the category and channel filters to identify which types of notifications are contributing most to this volume.

### Unsubscription trends

Monitor unsubscription trends and track opt-outs by channel and category.

**How to read this chart:**

- The count shows the total number of users who opted out during the selected time range.
- Heatmap visualizes opt-outs across different category and channel volume ranges — darker areas indicate higher concentrations of opt-outs.
- If opt-out numbers are unusually low, it may mean that an accessible opt-out option is missing from some notifications.

**Benchmark guidelines:**

These benchmarks are based on industry observations across transactional and marketing notification programs. Your actual benchmarks may vary based on your industry, user base, and notification types.

- **Below 0.2%** → Excellent opt-out rate (typical for well-targeted transactional notifications)
- **0.2-0.5%** → Acceptable opt-out rate (common for marketing or promotional notifications)
- **Above 0.5%** → Requires attention — investigate which channels or categories are driving opt-outs

When you see a spike in opt-outs, drill down by category or channel to understand what's causing users to leave. This might indicate over-messaging, irrelevant content, or issues with notification timing.

## Workflow Level Breakdown

The Workflow Level Breakdown tab provides detailed performance metrics for individual workflows, helping you identify exactly where improvements are needed.

### Workflow performance comparison

Compare performance across workflows and templates to spot what's driving engagement and what needs fixing.

This view gives you a comprehensive breakdown showing:

- **Channel performance by workflow** → See how each workflow performs across different channels. For example, if your email channel isn't performing well overall, you can drill down to see which specific workflows are dragging down the average.
- **Template-level insights** → Identify which templates are resonating with users and which need optimization.
- **Vendor performance** → See which vendors are causing delivery issues or performing exceptionally well.
- **Category analysis** → Understand how different notification categories (transactional, marketing, etc.) are performing.

**Example use case:**

If you notice that your email channel has a low seen rate (20%), you can:

1. Filter by email channel in the Workflow Level Breakdown
2. See that "Order Confirmation" workflow has 80% seen rate, but "Weekly Newsletter" has only 5%
3. Investigate the newsletter template, timing, or content to improve engagement
4. Compare with the order confirmation workflow to understand what's working

This granular view helps you make data-driven decisions about where to invest your optimization efforts.

### Error tracking

The Workflow Level Breakdown includes centralized error tracking across three categories:

#### API Request Failures

Errors due to which API requests were not successfully completed.

If you're actively making requests, this means your integration is working as expected. Any issues in API or SDK calls will appear here, helping you quickly identify integration problems.

#### Workflow / Broadcast Execution Failures

Errors encountered during workflow or broadcast run due to which one or more nodes in the flow would have failed.

When no errors are found, you'll see: "All workflow and broadcast executions have completed without errors. If issues occur during execution in the future, they'll be listed here for investigation."

This helps you catch workflow configuration issues, data transformation problems, or node-level failures before they impact too many users.

#### Notification Delivery Failures

Errors reported by vendors for failed notification deliveries.

These are vendor-specific delivery failures. Click on any error to see detailed information and jump directly to the relevant log entry for debugging.

## Limitations and caveats

Understanding what analytics cannot tell you is crucial for accurate interpretation and decision-making.

### Email tracking limitations

**Email open tracking (seen metric):**

- **Apple Mail Privacy Protection:** iOS 15+ and macOS 12+ users with Mail Privacy Protection enabled will show false "opened" events. Apple pre-loads tracking pixels, making it impossible to distinguish real opens from privacy-protected opens.
- **Gmail image blocking:** Some Gmail clients don't load images by default, resulting in underreported seen rates.
- **Email client variations:** Different email clients handle tracking pixels differently, leading to inconsistent seen rates across providers.

**Impact:** Email "seen" rates may be artificially inflated (Apple Mail) or underreported (Gmail) depending on your user base. Use seen rates as directional indicators, not absolute truth.

### Push notification limitations

**Delivery vs display:**

- **Delivered ≠ displayed:** Push delivery confirmation means the notification reached the device, not that it was displayed to the user.
- **Do Not Disturb:** Notifications delivered during Do Not Disturb mode are delivered but may not be seen.
- **App uninstalls:** If a user uninstalls your app, push delivery may still be marked as "delivered" by the push service, but the notification never reaches the user.

**Impact:** Push "delivered" rates are higher than actual user visibility. "Seen" rates (clicked) are more accurate indicators of user engagement.

### SMS limitations

**Delivery confirmation:**

- **Carrier delays:** SMS delivery confirmations may be delayed by hours or days, especially for international messages.
- **No engagement tracking:** SMS only tracks delivery. There's no way to know if a user read the message unless they reply or click a link.
- **Carrier filtering:** Some carriers filter or block SMS messages, which may not be reflected in delivery status.

**Impact:** SMS analytics are limited to delivery metrics. Engagement must be measured through link clicks or user responses.

### Inbox limitations

**Read vs clicked:**

- **Read tracking:** Inbox "read" status is based on explicit user actions (marking as read) or implicit actions (clicking). It may not capture all views.
- **Offline viewing:** Users viewing inbox messages offline may not trigger read events until they reconnect.

**Impact:** Inbox seen rates may underreport actual views if users don't explicitly mark messages as read.

### Data accuracy limitations

**Vendor callback dependency:**

- Analytics accuracy depends entirely on vendor webhook callbacks. If vendors fail to send callbacks or send incorrect status, analytics will reflect that.
- Some vendors have callback delays (hours to days), especially for international deliveries.
- Vendor API outages may result in missing or delayed analytics data.

**Sampling and aggregation:**

- **Sampling threshold:** Time ranges exceeding 90 days may use sampled data for performance optimization. Sampling is applied only to time-series charts, not to summary totals.
- **Sampling behavior:** When sampling is active, charts show directional trends rather than exact counts. Summary metrics (totals, percentages) always use full data.
- **Data exports:** Exports via S3 sync or webhooks use raw, unsampled data regardless of time range.
- Aggregation windows (hourly/daily) mean recent data may be incomplete.
- Historical data may change as late-arriving callbacks are processed (within 48-hour window).

### What analytics cannot tell you

Analytics cannot answer:

- **Why a user didn't engage:** Analytics show what happened, not why. User interviews and surveys are needed for qualitative insights.
- **Content effectiveness:** Analytics show engagement rates, not whether content resonated or drove desired actions.
- **Optimal send times:** Analytics show when you sent, not when users are most receptive. A/B testing is needed for timing optimization.
- **User intent:** High click rates don't guarantee positive user sentiment. Users may click to unsubscribe or report spam.
- **Cross-channel attribution:** Analytics show per-channel performance, not how channels work together in a user journey.

### Best practices for accurate interpretation

1. **Verify vendor callbacks:** Regularly check that vendor webhook callbacks are configured and working correctly
2. **Account for channel limitations:** Understand that email seen rates and push delivery rates have inherent limitations
3. **Use multiple metrics:** Don't rely on a single metric. Combine delivery, seen, and clicked rates for a complete picture
4. **Compare relative trends:** Focus on trends and relative performance rather than absolute numbers
5. **Correlate with business metrics:** Link notification analytics to business outcomes (conversions, revenue, retention) to validate effectiveness

## Debugging with analytics

When you spot anomalies in analytics, follow this systematic debugging flow:

### Engagement drop

**If you see:** Seen or click rates declining across channels

**Debugging steps:**

1. **Check channel performance** → Filter by channel to see if the drop is channel-specific
2. **Review workflow breakdown** → Identify which workflows are driving the decline
3. **Check vendor status** → Review delivery failures to see if vendor issues are causing delivery problems
4. **Verify callback configuration** → Ensure vendor webhooks are configured correctly (see [vendor integration docs](/docs/vendors))
5. **Review recent changes** → Check if template, workflow, or timing changes correlate with the drop

### Delivery drop

**If you see:** Delivery rates declining

**Debugging steps:**

1. **Check vendor errors** → Review "Notification Delivery Failures" in Workflow Level Breakdown
2. **Filter by vendor** → Identify if a specific vendor is causing issues
3. **Check API request failures** → Verify your integration isn't sending invalid requests
4. **Review workflow execution failures** → Check for configuration errors in workflows
5. **Jump to logs** → Click on specific errors to view detailed logs and execution traces

### Vendor errors

**If you see:** High delivery failure rates from a specific vendor

**Debugging steps:**

1. **Click on error** → Opens detailed error information and links to specific log entries
2. **Review error message** → Check vendor-specific error codes and messages
3. **Check vendor status page** → Verify vendor isn't experiencing outages
4. **Review vendor credentials** → Ensure API keys and credentials are valid
5. **Check vendor documentation** → Refer to [vendor-specific error guides](/docs/error-guides) for resolution steps

### No errors but low engagement

**If you see:** High delivery but low seen/click rates

**Debugging steps:**

1. **Account for channel limitations** → Review limitations section (email privacy protection, push display issues)
2. **Check timing** → Review if notifications are being sent at optimal times
3. **Compare workflows** → Identify high-performing workflows and compare templates/content
4. **Review category performance** → Check if specific categories (marketing vs transactional) are underperforming
5. **Consider A/B testing** → Test different templates, content, or send times

### From analytics to logs

When you need to investigate specific messages or events:

1. **Use filters** → Narrow down to specific workflow, tenant, template, or channel in analytics
2. **Identify time range** → Note the time period of the issue
3. **Jump to logs** → Navigate to [Logs page](/docs/logging) and apply the same filters
4. **Inspect individual messages** → Review detailed execution traces, payloads, and error details
5. **Copy execution ID** → Use execution ID from logs to share with support for deeper investigation

## Best practices

1. **Regular monitoring** → Check analytics weekly to catch trends early
2. **Compare workflows** → Use side-by-side comparisons to identify best practices from high-performing workflows
3. **Filter strategically** → Start broad, then narrow down using filters to find specific issues
4. **Track opt-out correlation** → When you see opt-out spikes, check the average notifications per user metric to see if over-messaging is the cause
5. **Vendor performance** → Regularly review delivery failures by vendor to catch provider issues early
6. **Category analysis** → Compare performance across notification categories to ensure transactional messages aren't being impacted by marketing volume
7. **Account for limitations** → Understand channel-specific tracking limitations when interpreting metrics
8. **Follow debugging flow** → Use the systematic debugging approach above when investigating issues
