Use the SuprSend CLI in a pipeline to release notification changes the way you release code: keep workflows, templates and the rest as files in Git, review them in pull requests, and push them to production when you merge. The CLI is the right tool here because a pipeline has no person to sign in. It runs with a service token, while the [MCP server](/reference/mcp-overview) needs someone to sign in with a SuprSend account.

## What you need

- A [service token](/docs/developer/service-tokens), saved as a secret in your CI system, for example `SUPRSEND_SERVICE_TOKEN` in GitHub Actions.
- Node.js 18 or later on the runner, to run the CLI with `npx`. You can also [install the CLI](/reference/cli-installation) another way.
- Your notification assets in the repo, in the folder layout the CLI uses (default `./suprsend/`).

<Warning>
  Service tokens are account-wide: a token can act on every workspace in your account. Keep it in your CI system's secret store, and limit who can run jobs that use it, for example with GitHub environment protection rules.
</Warning>

## Keep your assets in Git

Pull the current live state from your staging workspace into the repo, then commit it:

```bash
npx --yes suprsend@1.1.0 category pull -w staging -F
npx --yes suprsend@1.1.0 schema pull -w staging -F
npx --yes suprsend@1.1.0 event pull -w staging -F
npx --yes suprsend@1.1.0 template pull -w staging -F
npx --yes suprsend@1.1.0 workflow pull -w staging -F
npx --yes suprsend@1.1.0 translation pull -w staging -F
```

Each command writes to its own folder under `./suprsend/`, for example `./suprsend/workflows/<slug>/workflow.json`, and overwrites the files it pulls. `-F` uses the default folder without asking; without it, a pull asks for the folder in a terminal and fails in a non-interactive shell. From then on, change the files in pull requests, or pull again after building in the dashboard.

## Release to production on merge

This GitHub Actions workflow pushes the assets in `./suprsend/` to production and commits them when changes reach `main`. It pushes them in the same order [`suprsend sync`](/reference/cli-sync) uses, so categories and schemas exist before the templates and workflows that use them.

```yaml .github/workflows/suprsend-release.yml
name: Release SuprSend notifications

on:
  push:
    branches: [main]
    paths: ["suprsend/**"]

# Run one release at a time, so an older commit can't overwrite a newer one.
concurrency:
  group: suprsend-production
  cancel-in-progress: false

jobs:
  release:
    runs-on: ubuntu-latest
    # Add required reviewers to this environment to approve each release.
    environment: production
    env:
      SUPRSEND_SERVICE_TOKEN: ${{ secrets.SUPRSEND_SERVICE_TOKEN }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Push and commit to production
        run: |
          npx --yes suprsend@1.1.0 category push -w production --commit
          npx --yes suprsend@1.1.0 schema push -w production --commit
          npx --yes suprsend@1.1.0 event push -w production
          npx --yes suprsend@1.1.0 template push -w production --commit
          npx --yes suprsend@1.1.0 workflow push -w production --commit
          npx --yes suprsend@1.1.0 translation push -w production --commit
```

Without `--commit`, workflows, templates, schemas, categories and translations are saved as drafts in the destination. Events have no draft state, and `category push` sends preference-category translations live straight away. Leave `--commit` off if you want someone to review and commit the drafts in the dashboard. In that case `event push` fails for events linked to schemas that aren't live yet.

The step stops at the first command that fails, because GitHub Actions runs `run` scripts with `bash -e`. A release isn't all-or-nothing: the asset types pushed before the failure, and the items that succeeded in the failing command, are already live. Fix the cause and re-run the job.

Keep only the commands for asset types you store in the repo. A push fails with exit code 2 when its folder, for example `./suprsend/templates`, doesn't exist.

## Check files in pull requests

`--dry-run` reads and parses the local files without calling SuprSend, so it catches broken JSON before merge. A file that doesn't parse fails the check with exit code 2. The CLI still needs a token value to start, but a dry run never uses it, so a placeholder works and keeps your real token out of pull-request jobs.

```yaml .github/workflows/suprsend-check.yml
name: Check SuprSend files

on:
  pull_request:
    paths: ["suprsend/**"]

jobs:
  check:
    runs-on: ubuntu-latest
    env:
      # --dry-run makes no API calls, but the CLI needs a token value to start.
      SUPRSEND_SERVICE_TOKEN: dry-run-placeholder
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Parse local files
        run: |
          npx --yes suprsend@1.1.0 schema push --dry-run
          npx --yes suprsend@1.1.0 template push --dry-run
          npx --yes suprsend@1.1.0 workflow push --dry-run
```

A dry run checks only local files: that they parse, and for schemas that `payload_schema.json` compiles as a JSON Schema. SuprSend validates the content itself when you push.

## Promote staging to production with sync

If you build in the staging workspace instead of in files, promote everything at once with [`suprsend sync`](/reference/cli-sync). Run it from a manual job so a person decides when to release:

```yaml .github/workflows/suprsend-promote.yml
name: Promote SuprSend staging to production

on: workflow_dispatch

jobs:
  promote:
    runs-on: ubuntu-latest
    environment: production
    env:
      SUPRSEND_SERVICE_TOKEN: ${{ secrets.SUPRSEND_SERVICE_TOKEN }}
    steps:
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Sync staging to production
        run: npx --yes suprsend@1.1.0 sync --from staging --to production --dir ./sync-tmp
```

<Warning>
  `sync` pushes **and commits** every synced asset, so the changes go live in production immediately. It also pushes any asset already in its local directory, not only what it pulled from staging. Use a fresh `--dir`, as above, so only assets from staging are pushed. Template variants that fail validation are skipped with a warning, which CI logs hide, and the command still exits with 0, so check the destination after a sync.
</Warning>

## Keep generated types in step

If your code uses [types generated](/docs/type-generation) from your payload schemas, regenerate them in CI and fail the build when they're out of date. This needs your real service token, not the placeholder.

```bash
rm -f ./types/suprsend-types.ts
npx --yes suprsend@1.1.0 generate-types typescript --workspace staging --output-file ./types/suprsend-types.ts
git diff --exit-code ./types/suprsend-types.ts
```

Deleting the file first matters: if generation fails, for example on an expired token, the command still exits with 0, and the missing file then shows up in `git diff`.

## How the CLI behaves in CI

- **No prompts.** Confirmation prompts appear only in an interactive terminal. In CI, `--commit`, `sync` and `workflow disable` run straight away, so check `-w` before you run them.
- **Logs are hidden.** When output isn't a terminal, as in most CI runners, the CLI hides its log lines and prints only command output and a JSON error. Rely on the exit code.
- **Re-runs are safe.** When there's nothing new to commit, the command exits with 0. In a terminal, it also logs "no changes to commit".
- **Self-hosted or BYOC.** Point the CLI at your deployment with the `SUPRSEND_BASE_URL` and `SUPRSEND_MGMNT_URL` environment variables, or use a [CLI profile](/docs/self-hosted/cli-profiles).

| Exit code | Meaning |
|---|---|
| `0` | Success |
| `1` | General or API error, including a partial failure |
| `2` | Validation error, for example a file that doesn't parse |
| `3` | Authentication failed, for example a missing token. A bulk push that the API rejects with a 401 exits with `1`. |
| `4` | Resource not found |
| `5` | Reserved for rate limiting. CLI 1.1.0 reports a rate-limit error as `1`. |
| `64` | Invalid usage, such as a missing flag |
