**Use this skill when** you want your AI agent to create, modify, or edit a template variant - "build an SMS variant", "add a French locale", "create a tenant-specific welcome email" - without making up brand variable keys or missing the per-channel content shape.

The skill loads the variant envelope, per-channel content schemas, and Handlebars/JSONNET syntax references into your agent's context whenever it detects a template task. Every generated variant validates against `https://schema.suprsend.com/template/v2/variant_schema.json` and is ready to push with the [`suprsend-cli`](/reference/agent-skill-cli) skill.

## Install

```bash
npx skills add https://github.com/suprsend/skills --skill suprsend-template-schema
```

## Try it

Paste this into your agent:

```text
Write the English email for our welcome-email template. Add a
footer with the tenant name and an unsubscribe link.
```

Enabling a channel on a template creates its reserved `default` variant (`id: "default"`, `locale: "en"`, `tenant_id: null`, no conditions). You can edit only its content. So your agent fills in the `content` of the `default` variant instead of adding a new one. A second variant with the same locale, tenant and conditions, such as `id: "default-en"`, is rejected as a duplicate.

```json
{
  "$schema": "https://schema.suprsend.com/template/v2/variant_schema.json",
  "channel": "email",
  "id": "default",
  "tenant_id": null,
  "locale": "en",
  "conditions": null,
  "content": {
    "subject": "Welcome to Shipfast, {{{first_name}}}",
    "body": {
      "type": "raw",
      "preheader": "Your workspace is ready. Invite your team next.",
      "raw": {
        "html": "<!DOCTYPE html><html lang=\"en\"><head><meta charset=\"utf-8\"><meta name=\"viewport\" content=\"width=device-width, initial-scale=1\"></head><body style=\"margin:0;\"><!--[if mso]><table role=\"presentation\" width=\"600\" cellpadding=\"0\" cellspacing=\"0\" border=\"0\"><tr><td><![endif]--><table role=\"presentation\" width=\"100%\" cellpadding=\"0\" cellspacing=\"0\" border=\"0\" style=\"width:100%; max-width:600px; font-family:Arial,Helvetica,sans-serif;\"><tr><td style=\"padding:32px;\"><h1 style=\"margin:0; font-size:24px;\">Welcome, {{first_name}}</h1><p style=\"font-size:16px;\">Your Shipfast workspace is ready.</p></td></tr><tr><td style=\"padding:0 32px 32px; font-size:12px; color:#475467;\">{{$tenant.name}} · <a href=\"{{{$hosted_preference_url}}}\">Unsubscribe or manage preferences</a></td></tr></table><!--[if mso]></td></tr></table><![endif]--></body></html>",
        "text": "Welcome, {{{first_name}}}. Your Shipfast workspace is ready.\n\n{{{$tenant.name}}} · Unsubscribe or manage preferences: {{{$hosted_preference_url}}}"
      }
    }
  }
}
```

A few things the skill got right here:

- The HTML is a full `<html><head></head><body>…</body></html>` document, so the `preheader` has a `<body>` tag to attach to.
- The content table is fluid (`width:100%; max-width:600px`), and an Outlook-only ghost table keeps Outlook at 600px. The skill's [email design guide](https://github.com/suprsend/skills/blob/main/skills/suprsend-template-schema/references/channel-email.md#designing-a-responsive-cross-client-email-raw-body) has the full skeleton.
- It writes `{{$tenant.name}}`, not the legacy `{{$brand.brand_name}}`.
- It keeps `{{ }}` in the HTML body and uses `{{{ }}}` in the subject and plain-text part. See [Templating syntax](#templating-syntax).
- It leaves out `seq_no` and `vendor_approvals`. Both are read-only: `seq_no` comes from the variant order.

Push it live:

```bash
suprsend template push --slug welcome-email --commit=true
```

<Tip>
  Templates live under `./suprsend/templates/` locally and are pushed as a unit - variants are not managed separately. See [Template Commands](/reference/cli-template-overview).
</Tip>

## How variants work

Every SuprSend template is modeled as a collection of **variants**. A variant pairs a channel, locale, optional tenant, and optional condition with channel-specific content.

Enabling a channel auto-creates its reserved `default` variant (`id: "default"`, `locale: "en"`, `tenant_id: null`, no conditions). A simple template is just that one variant with its content filled in. Adding more locales, more tenants, or conditional content means adding more variants under the same template.

The `content` object inside a variant validates against a channel-specific schema selected by the `channel` field.

The skill also teaches your agent how SuprSend picks a variant at send time:

- **Conditions.** Entries in `conditions[]` are combined with OR. The `args` inside one entry are combined with AND.
- **String literals need inner quotes.** Write `"\"enterprise\""`. A bare word like `"enterprise"` is read as a variable path.
- **Locales are case-sensitive.** Use `en-US`, not `en-us`.
- **Selection order.** Locales are tried as exact locale, then base language, then `en`. Within a locale, non-`default` variants come before `default`, and the first match wins.

## Tenant variables

Templates can reference tenant properties. There are three shapes - the skill teaches your agent which to use for each case.

<Note>
  `$tenant` is the canonical name. `$brand` is the legacy name for the same object, so the skill emits only `$tenant.*`.
</Note>

<Tabs>
  <Tab title="Reserved $tenant.* keys">
    These are the only keys valid directly under `$tenant.`. Any other key under `$tenant.` fails the render - put it under `$tenant.properties.` instead.

    `id` and `name` replace `brand_id` and `brand_name`. The old keys still work as aliases.

    | Variable | Renders |
    |---|---|
    | `{{$tenant.id}}` | Tenant slug / id |
    | `{{$tenant.name}}` | Tenant display name |
    | `{{$tenant.logo}}` | Tenant logo URL |
    | `{{$tenant.primary_color}}` | Primary brand color |
    | `{{$tenant.secondary_color}}` | Secondary brand color |
    | `{{$tenant.tertiary_color}}` | Tertiary brand color |
    | `{{$tenant.timezone}}` | Tenant timezone |
    | `{{$tenant.embedded_preference_url}}` | Brand-level embedded preference URL |
    | `{{$tenant.hosted_preference_domain}}` | Brand-level hosted preference domain |
    | `{{$tenant.blocked_channels}}` | List of channels blocked at the brand level |
    | `{{$tenant.parent_id}}` | Parent tenant id for a [sub-tenant](/docs/sub-tenants). Empty for a root tenant |
    | `{{$tenant.level}}` | Depth in the sub-tenant tree, `0` (root) to `4` |
    | `{{$tenant.ancestors}}` | Array of ancestor tenant ids, root first. Doesn't include the tenant itself |
    | `{{$tenant.social_links.<network>}}` | Brand social link. Built-in `<network>` keys: `x`, `twitter`, `facebook`, `instagram`, `linkedin`, `youtube`, `tiktok`, `discord`, `telegram`, `medium`, `website` |
  </Tab>

  <Tab title="Custom tenant properties">
    Any property the customer adds on the tenant object that is **not** in the reserved list is a custom property, and the correct shape is `{{$tenant.properties.<key>}}`. Common examples:

    - `{{$tenant.properties.address}}`
    - `{{$tenant.properties.unsubscribe_url}}`
    - `{{$tenant.properties.support_url}}`
    - `{{$tenant.properties.support_email}}`

    If you don't recognise the key from the reserved list, default to `$tenant.properties.<key>`.
  </Tab>

  <Tab title="Preference URLs">
    Both preference URLs are top-level variables. They are never nested under `$tenant`:

    - `{{$hosted_preference_url}}` - link to the hosted preference and unsubscribe page. SuprSend substitutes it in email and SMS content only.
    - `{{$embedded_preference_url}}` - the tenant's embedded preference page URL, falling back to the organization setting. It isn't per-recipient.

    `{{$tenant.$hosted_preference_url}}` is the wrong form and doesn't resolve.
  </Tab>
</Tabs>

## Common anti-patterns

These are the mistakes the skill is built to prevent.

| Wrong | Correct |
|---|---|
| `{{$tenant.support_url}}` | `{{$tenant.properties.support_url}}` |
| `{{$tenant.unsubscribe_url}}` | `{{$tenant.properties.unsubscribe_url}}` |
| `{{$tenant.address}}` | `{{$tenant.properties.address}}` |
| `{{$tenant.$hosted_preference_url}}` | `{{$hosted_preference_url}}` (hosted preference page link) _or_ `{{$tenant.hosted_preference_domain}}` (brand config) - pick based on intent |

<Warning>
  Templates render in strict mode. An unknown `$tenant.<key>`, a missing custom property, or any other missing variable fails the render with a missing-variable error. It doesn't render blank. For an optional custom property, use `{{default $tenant.properties.<key> "…"}}` as a fallback. This works only when the tenant's `properties` is an object; if `properties` is `null`, the render still fails.
</Warning>

## What you can build

A few real things people generate with this skill:

- **Welcome email in English** - single variant, default tenant, default locale. The skill writes responsive, cross-client email HTML in a `raw` body: a fluid layout up to 600px that stays fixed-width in Outlook, accessible markup, dark-mode support, and a visible unsubscribe link. For any feature it isn't sure every email client supports, it checks [Can I Email](https://www.caniemail.com/).
- **French locale variant** - add a `locale: "fr"` variant to an existing template.
- **Tenant-specific welcome email** - one variant per tenant, sharing the same template slug.
- **Multi-channel template** - email + SMS + push variants for the same notification.
- **Slack message with JSONNET `body_block`** - JSONNET Block Kit is the default for Slack messages. Text mode is sent as a Slack `plain_text` section, so formatting, mentions and links show up literally.
- **Email paired with a send recipe** - the [email reference](https://github.com/suprsend/skills/blob/main/skills/suprsend-template-schema/references/channel-email.md) pairs each email with the flow that sends it: transactional (`workflows_trigger` or `events_track`), welcome series (`send_email` + `delay`), promotional (`lists_upsert` + `broadcasts_trigger`), and digest (`digest` node + `{{#each}}`).

## Templating syntax

The skill carries both supported templating syntaxes:

| Syntax | When it's used |
|---|---|
| **Handlebars** | Default for every channel. Variables, conditionals, comparisons, date/array helpers. [Reference](https://github.com/suprsend/skills/blob/main/skills/suprsend-template-schema/references/handlebars-helpers.md). |
| **JSONNET** | Always used for Slack `body_type: "block"` (`body_block`) and MS Teams `body_type: "card"` (`body_card`). These body types force `templating_language: "jsonnet"`, and variables are read as `data.key`. Handlebars `{{ }}` inside them is sent as literal text. [Reference](https://github.com/suprsend/skills/blob/main/skills/suprsend-template-schema/references/jsonnet-syntax.md). |
| **Escaping** | `{{ }}` HTML-escapes its output in every channel, and nothing un-escapes it. Keep `{{ }}` in the email HTML body and the Inbox body. Use `{{{ }}}` in plain-text outputs: SMS, push, WhatsApp, Slack text, Inbox header, subtext and URLs, and the email `subject`, `preheader` and plain-text part. |
