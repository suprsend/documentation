When you run [`suprsend template pull`](/reference/cli-template-pull), the CLI writes each template to disk using a predictable directory structure. [`suprsend template push`](/reference/cli-template-push) reads that same structure back when uploading changes. This page documents the directory shape, file naming conventions, and the behaviour you can expect during a push.

The supported channels are: `email`, `sms`, `whatsapp`, `inbox`, `slack`, `ms_teams`, `androidpush`, `iospush`, and `webpush`.

---

## Directory structure

```
suprsend/templates/
└── <template-slug>/
    ├── template.json                # template metadata + variant order
    ├── mock_data.json               # optional mock payload for previews and tests
    └── <channel>/
        ├── <variantID>/             # one directory per variant
        │   ├── variant.json
        │   │
        │   │   # email only (read based on content.body.type):
        │   ├── body.raw.html
        │   ├── body.raw.txt
        │   ├── body.designer.html
        │   ├── body.designer.txt
        │   ├── body.plain_text.txt
        │   ├── design.json
        │   │
        │   │   # slack only (when content.body_type is "block"):
        │   └── body.block.json
        └── _tenants/                # tenant overrides — same shape inside
            └── <tenantID>/
                └── <variantID>/
                    ├── variant.json
                    └── ...extracted files if any...
```

A couple of conventions are worth highlighting:

- **One shape per channel.** Every variant lives under `<channel>/<variantID>/`, including templates that have only a single default variant. In that case, the directory is simply `<channel>/default/`.
- **Body extraction is channel-specific.** Only **email** body content and **Slack Block Kit** bodies are extracted into separate sidecar files. SMS, inbox, push (Android, iOS, and Web), MS Teams, and WhatsApp keep their full `content` inline within `variant.json`.

Please note that `_tenants/` is a reserved directory name, so it cannot also be used as a variant name.

## `template.json`

Each template has a single `template.json` at its root. This file holds the template's metadata along with the per-channel variant order.

```json
{
  "$schema": "https://schema.suprsend.com/cli/template/v2/schema.json",
  "slug": "welcome",
  "name": "Welcome",
  "enabled_channels": ["email", "sms"],
  "variant_order": {
    "email":                ["default"],
    "email/tenant-xyz":     ["en", "es"],
    "sms":                  ["default"]
  }
}
```

The `variant_order` field lists every channel and every channel + tenant pair that has overrides:

- Bare channel keys (for example, `"email"`) refer to the `<channel>/` directory.
- Slash-separated keys (for example, `"email/tenant-acme"`) refer to a tenant override at `<channel>/_tenants/<tenantID>/`.
- An empty `variant_order` (`{}`) is valid and is what you'll see for a freshly-created template that doesn't yet have any variants.

---

## `mock_data.json` (optional)

`mock_data.json` sits alongside `template.json` at the template root. It's a free-form JSON fixture used for template previews and tests.

```json
{ "user": { "name": "Alice" }, "order": { "id": "A-123", "total": "$42.00" } }
```

This file is optional both on disk and during push. If it isn't present, the template simply runs without a mock fixture.

## Variant rules

### Identity is path-based

A variant's `id`, `channel`, and `tenant_id` appear in two places: the directory path and the corresponding fields inside `variant.json`. When you push, the directory path is treated as the source of truth — the CLI updates the matching fields in `variant.json` from the path before sending the payload upstream.

| Identity field | Source on push                                  |
|----------------|-------------------------------------------------|
| `channel`      | The immediate parent channel directory          |
| `id`           | The variant directory name                      |
| `tenant_id`    | `<tenantID>` if under `_tenants/`, otherwise `null` |

To rename a variant, rename its directory. Editing only the JSON field will not take effect, since the path takes precedence.

### `variant.json` content

`variant.json` contains the variant object itself. For email and Slack-block variants, body content is extracted into sidecar files (described in the next section). All other channels keep their `content` inline.

Here's an example of an email variant in `designer` mode:

```json
{
  "id": "default",
  "channel": "email",
  "tenant_id": null,
  "locale": "en",
  "conditions": null,
  "content": {
    "subject": "Welcome!",
    "from_name": "Acme",
    "from_address": "hello@acme.com",
    "body": {
      "type": "designer"
    }
  }
}
```

`content.body.type` remains in `variant.json` because it acts as a discriminator that tells push which body files to expect. The actual `content.body.designer` payload is not stored on disk — instead, the CLI reassembles it on push by reading `body.designer.html`, `body.designer.txt`, and `design.json`.

## Content extraction

### Email

Email body extraction is driven by `content.body.type`. Only the files matching the active body type are read on push; any others are quietly ignored.

| Source field (JSON path)              | File                  | Active when `content.body.type` is |
|---------------------------------------|-----------------------|------------------------------------|
| `content.body.raw.html`               | `body.raw.html`       | `raw`                              |
| `content.body.raw.text`               | `body.raw.txt`        | `raw`                              |
| `content.body.designer.html`          | `body.designer.html`  | `designer`                         |
| `content.body.designer.text`          | `body.designer.txt`   | `designer`                         |
| `content.body.designer.design_json`   | `design.json`         | `designer`                         |
| `content.body.plain_text.text`        | `body.plain_text.txt` | `plain_text`                       |

Short scalar fields — `subject`, `preheader`, `from_name`, `from_address`, `extra_to`, `cc`, `bcc`, `reply_to`, `email_markup`, and `templating_language` — stay inline under `content` within `variant.json`.

### Slack

| Source field (JSON path) | File              | Active when `content.body_type` is |
|--------------------------|-------------------|------------------------------------|
| `content.body_block`     | `body.block.json` | `block`                            |

When `content.body_type` is `"text"`, the `content.body_text` field stays inline in `variant.json`.

To switch a variant from one body type to another, update the discriminator in `variant.json` and add the matching files for the new type. The CLI does not automatically clean up sidecar files from the previous body type, so you may want to delete the stale files yourself to keep the directory tidy.

## What happens on push

### Reconciling `variant_order`

When you push, the CLI compares the `variant_order` declared in `template.json` against what's actually present on disk:

- A variant directory that's new on disk but missing from `variant_order` will be appended automatically, and the CLI logs a warning so you know it happened.
- A variant listed in `variant_order` but missing from disk causes the push to fail, with the missing path called out in the error.
- Order changes between disk and `variant_order` are not auto-detected — `variant_order` remains the authoritative source for ordering, so update it explicitly when you want to rearrange variants.

### Missing body files

If `variant.json` declares a body (for example, `content.body.type: "designer"`) but the corresponding file (`body.designer.html`) isn't present on disk, the push will fail immediately and the rest of the operation is cancelled. The error message names the file the CLI was looking for so you can resolve it quickly.

### `enabled_channels` and the disk contract

The CLI also reconciles `enabled_channels` against the channel directories on disk:

- If a channel directory exists but the channel isn't listed in `enabled_channels`, the push fails. This prevents accidentally publishing to a channel the template doesn't claim to support.
- If a channel is listed in `enabled_channels` but its directory is missing, the CLI logs a warning and skips that channel — useful when you've enabled a channel but haven't authored its variants yet.

### Error messages

Push-time error messages are prefixed with the variant path so the affected variant is easy to identify. For example:

```
email/en: missing body.designer.html (required by content.body.type: "designer")
```

## Schema validation

The SuprSend template payloads are formally specified in the [`suprsend/schema`](https://github.com/suprsend/schema/tree/main/template/v2) repository — `schema.json`, `variant_schema.json`, and the per-channel `<channel>_schema.json` files. The CLI uses these directly.

`template.json` carries a CLI-specific wrapper schema published at `https://schema.suprsend.com/cli/template/v2/schema.json`, which is referenced via the `$schema` field to enable editor IntelliSense. `variant.json`, on the other hand, deliberately does not reference a schema — because body fields are extracted into sidecar files, the on-disk file is a partial payload, and attaching the upstream schema directly would surface validation errors that aren't actually problems. The CLI runs full validation on push, once the variant has been reassembled with its body content.

Both the CLI wrapper schema and a snapshot of the upstream schemas are embedded in the CLI binary, so push-time validation works offline.
